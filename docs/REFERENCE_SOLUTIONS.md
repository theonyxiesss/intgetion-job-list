# Готовые решения перед новым элементом

Это рабочий порядок по D570. Перед новой функцией, модулем, кабинетом или визуальным элементом он всплывает через раздел **Reuse first** в корневом `AGENTS.md`. Для конкретного домена первым остаётся его ТЗ.

## Короткая запись сравнения

1. Найти существующий модуль, сервисный API, компонент `src/components/ui/`, токены и тексты проекта. Отметить, что можно расширить.
2. Проверить текущие официальные сценарии 1–3 сопоставимых продуктов и поддерживаемые открытые репозитории. Записать прямые ссылки и дату проверки.
3. Сопоставить цель пользователя, структуру данных и права, дизайн и доступность, стек, зависимости, лицензию, активность поддержки и цену внедрения.
4. Выбрать: переиспользовать свой код, адаптировать проверенный паттерн или создать новое решение. Назвать причину выбора, компромиссы и критерии проверки. Чужие исходники и ресурсы переносить только после проверки лицензии.

Для общего аккаунта пример этого сравнения находится в [ТЗ 30 §30.7](tz/30-one-account.md): Upwork — сценарии работы с одним логином, GitHub — личный аккаунт и членство в компаниях, Vercel Platforms — пример tenant-маршрутизации. Вывод для INTGETION: развивать `users`/`user_profiles` и `company_members`, сохраняя данные сервисов в своих модулях.

Для инфраструктуры: [сравнение Supabase, Cloudflare D1 и Neon](DB_PLATFORM_COMPARISON.md) учитывает тарифы и цену переноса действующего PostgreSQL/Auth/Storage, а не только бесплатный объём базы.

Для диагностики: [схема ошибок](ERROR_DIAGNOSTICS.md) сопоставляет существующий HTTP/UI/Sentry слой с `systematic-debugging`, `react-error-boundary` и RFC 9457; отдельно отмечает потерю причины при текущем сбое входа.

Для UGC: [сравнение с Insense, Billo, JoinBrands и Collabstr](UGC_MARKET_BENCHMARK.md) отделяет уже работающий креативный тест от полного цикла производства контента и фиксирует архитектурные пробелы.

## billion-context — оценка 2026-10-29 (D571)

[billion-context](https://github.com/ranxianglei/billion-context/blob/master/README.md) — внешний прокси для истории разговоров кодового агента, а не модуль сайта. Его [документация для Codex](https://github.com/ranxianglei/billion-context/blob/master/CLIENTS.md#codex-openai-codex-cli) описывает полный путь через запуск `bili codex` для Codex CLI. Установка только MCP добавляет инструменты, но не направляет запросы модели через прокси. Совместимость этого пути с текущим Codex Desktop и входом через ChatGPT в нашем окружении не подтверждена.

OpenAI уже поддерживает [сжатие контекста](https://developers.openai.com/api/docs/guides/compaction) в своих агентных сценариях. У проекта также есть короткий горячий путь `CURRENT.md` → `OPEN_TASKS.md` → доменное ТЗ, а долговременные факты лежат в `DECISIONS.md` и `MISSION_LOG.md`. Эти файлы решают задачу передачи состояния между сессиями; прокси сжимает историю одной сессии.

**Вывод:** сейчас `billion-context` не устанавливать и не менять маршрутизацию Codex Desktop. Если длинная отдельная сессия Codex CLI начнёт терять существенные факты, провести изолированное сравнение с обычной сессией: сохранность требований и решений, число повторных чтений, расход токенов и сбои инструментов. Только после такого результата рассматривать подключение; прокси получает содержимое модельных запросов, поэтому его конфигурация требует отдельного решения по доступу к данным.

### Web3 в «Моём аккаунте» (2026-11-02)

**Неподвижная модель продукта (ТЗ 30): один человек = один аккаунт `users` = один общий профиль `user_profiles` для вакансий, найма, фриланса, UGC, событий и Spoki.** Почта, Google, Telegram и возможный вход через кошелёк — способы открыть тот же аккаунт, а не отдельные личности. Аккаунт хранит личные настройки и подтверждённый адрес; действия от компании идут через `company_members` и выбранный `company_id`. Ни кошелёк, ни DAO, ни Web3-профиль не создают вторую регистрацию или глобальную роль.

Сейчас `/account` содержит один подтверждённый EVM-адрес (`user_wallets`) на пользователя. SIWE-подпись подтверждает владение адресом, но ещё не является способом входа в Supabase Auth. В предложениях ниже этот единственный адрес остаётся текущей моделью, пока основатель отдельно не решит иначе.

| --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Вход через кошелёк](https://supabase.com/docs/guides/auth/auth-web3) | Кнопка входа по EIP-4361 рядом с почтой, Google и Telegram; использовать существующий Supabase Auth и WalletConnect.                                                                                  | Сперва связать кошелёк с существующим `users`, иначе появятся два аккаунта одного человека. Проверить совместимость с уже привязанным `user_wallets`. Нужны лимиты и CAPTCHA против массовых регистраций. Не обходит текущую блокировку Supabase Auth 402. |
| Несколько кошельков с назначением                                     | Только возможное будущее расширение одного аккаунта: личные адреса могли бы иметь разные назначения. | ENS в профиле                                                         | Показать проверенное имя рядом с адресом, не заставляя пользователя покупать имя.                                                                                                                     | [Проверять обратное и прямое разрешение](https://docs.ens.domains/web/reverse/); имя может сменить владельца и не подтверждает личность.                                                                                                                   |
| История Web3-расчётов                                                 | В аккаунте показать оплаченные тарифы, заказы, выплаты, возвраты и ссылки на транзакции из существующих записей billing/freelance/UGC.                                                                | Повторно использовать текущие журналы и проверенные хэши; публичная сеть показывает перевод, но не доказывает исполнение работы. | Переносимые достижения                                                | По согласию пользователя выдавать [EAS-аттестации](https://docs.attest.org/docs/core--concepts/attestations) по завершённым заказам.                                                                  | Сначала проверить спрос; внутренние отзывы остаются источником истины. | Смарт-кошелёк компании                                                | Связать существующий Safe с компанией, которой управляют пользователи через `company_members`, и показать ожидающие подтверждения оплаты.                                                             | [ERC-1271](https://eips.ethereum.org/EIPS/eip-1271) проверяет подпись контракта; нужны проверка полномочий компании и ожидание нескольких подписантов. Практичный порядок для единого аккаунта: 1) история проверенных расчётов и ENS у текущего адреса; 2) поддержка ERC-1271 по спросу; 3) вход через кошелёк только после безопасного связывания с существующим `users` и сценария восстановления доступа. Несколько личных кошельков остаются отдельной гипотезой. Почта или другой способ восстановления остаётся полезным при потере кошелька. Это предложение, не разрешение на изменение Auth или данных.

### Ещё две гипотезы для единого аккаунта (2026-11-02)

Один и тот же человек может рекомендовать кандидата, нанимать и выполнять заказ через свой существующий аккаунт. Новая личность или глобальная роль для этого не нужна. Следующие варианты пока не входят в продуктовый план:

| Гипотеза                       | Пользовательский сценарий                                                                                                    | Реализация и цена адаптации                                                                                                                                                                                                                                                                                                                                                                          | Вывод                                                                              |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Вознаграждение за рекомендацию | Пользователь рекомендует кандидата компании и после подтверждённого найма получает оговорённую сумму в USDC.                 | Связать рекомендацию с вакансией, согласие кандидата, защиту от повторов и подтверждение результата компанией; для выплаты можно переиспользовать проверку USDC-транзакции, но сам процесс выплаты придётся построить. Найм происходит вне блокчейна, поэтому смарт-контракт сам не определит, состоялся ли он. Новый протокол и библиотека не нужны; требуются правила споров, налогов и антифрода. | Отдельная продуктовая гипотеза только при спросе компаний на платные рекомендации. |

Блокировка средств ухудшит вход для части заказчиков.                                                                                                                                                                                          | Проверять в пилоте эскроу, не вводить как обязательное условие публикации задачи.  |

[ERC-7715](https://eips.ethereum.org/EIPS/eip-7715) предлагает ограниченные по сроку разрешения кошелька на действия от имени пользователя, но стандарт пока Draft и поддержка зависит от кошелька. Автоматическая оплата через Spoki противоречила бы текущему требованию подтверждать его действия, изменяющие данные. Поэтому делегирование платежей не предлагается к внедрению. Разделение оплаты между участниками команды также не подходит текущему фриланс-сервису: ТЗ 28 описывает работу одного исполнителя.

После этих гипотез нет нового Web3-протокола с очевидным ближайшим выигрышем для единого аккаунта. Приоритет остаётся у понятных расчётов и проверяемой истории работы; новые финансовые сценарии требуют отдельного решения основателя.
