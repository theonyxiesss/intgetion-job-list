# Готовые решения перед новым элементом

Это рабочий порядок по D570. Перед новой функцией, модулем, кабинетом или визуальным элементом он всплывает через раздел **Reuse first** в корневом `AGENTS.md`. Для конкретного домена первым остаётся его ТЗ.

## Короткая запись сравнения

1. Найти существующий модуль, сервисный API, компонент `src/components/ui/`, токены и тексты проекта. Отметить, что можно расширить.
2. Проверить текущие официальные сценарии 1–3 сопоставимых продуктов и поддерживаемые открытые репозитории. Записать прямые ссылки и дату проверки.
3. Сопоставить цель пользователя, структуру данных и права, дизайн и доступность, стек, зависимости, лицензию, активность поддержки и цену внедрения.
4. Выбрать: переиспользовать свой код, адаптировать проверенный паттерн или создать новое решение. Назвать причину выбора, компромиссы и критерии проверки. Чужие исходники и ресурсы переносить только после проверки лицензии.

Для общего аккаунта пример этого сравнения находится в [ТЗ 30 §30.7](tz/30-one-account.md): Upwork — сценарии работы с одним логином, GitHub — личный аккаунт и членство в компаниях, Vercel Platforms — пример tenant-маршрутизации. Вывод для INTGETION: развивать `users`/`user_profiles` и `company_members`, сохраняя данные сервисов в своих модулях.

Для инфраструктуры: [сравнение Supabase, Cloudflare D1 и Neon](DB_PLATFORM_COMPARISON.md) учитывает тарифы и цену переноса действующего PostgreSQL/Auth/Storage, а не только бесплатный объём базы.

Для диагностики: [схема ошибок](ERROR_DIAGNOSTICS.md) сопоставляет существующий HTTP/UI/Sentry слой с `systematic-debugging`, `react-error-boundary` и RFC 9457; отдельно отмечает потерю причины при текущем сбое входа.

Для UGC: [сравнение с Insense, Billo, JoinBrands и Collabstr](UGC_MARKET_BENCHMARK.md) отделяет уже работающий креативный тест от полного цикла производства контента и фиксирует архитектурные пробелы.

## Когда нужен REA

Пользовательский навык `reverse-engineer-anything` установлен для анализа поставленного приложения, сборки или наблюдаемого поведения, которое невозможно подтвердить открытым кодом и документацией. Для открытого репозитория сначала читать код обычными инструментами. Установка навыка сама по себе не подключает REA MCP; подключение проверяют только для конкретной задачи такого анализа.

## billion-context — оценка 2026-10-29 (D571)

[billion-context](https://github.com/ranxianglei/billion-context/blob/master/README.md) — внешний прокси для истории разговоров кодового агента, а не модуль сайта. Его [документация для Codex](https://github.com/ranxianglei/billion-context/blob/master/CLIENTS.md#codex-openai-codex-cli) описывает полный путь через запуск `bili codex` для Codex CLI. Установка только MCP добавляет инструменты, но не направляет запросы модели через прокси. Совместимость этого пути с текущим Codex Desktop и входом через ChatGPT в нашем окружении не подтверждена.

OpenAI уже поддерживает [сжатие контекста](https://developers.openai.com/api/docs/guides/compaction) в своих агентных сценариях. У проекта также есть короткий горячий путь `CURRENT.md` → `OPEN_TASKS.md` → доменное ТЗ, а долговременные факты лежат в `DECISIONS.md` и `MISSION_LOG.md`. Эти файлы решают задачу передачи состояния между сессиями; прокси сжимает историю одной сессии.

**Вывод:** сейчас `billion-context` не устанавливать и не менять маршрутизацию Codex Desktop. Если длинная отдельная сессия Codex CLI начнёт терять существенные факты, провести изолированное сравнение с обычной сессией: сохранность требований и решений, число повторных чтений, расход токенов и сбои инструментов. Только после такого результата рассматривать подключение; прокси получает содержимое модельных запросов, поэтому его конфигурация требует отдельного решения по доступу к данным.
