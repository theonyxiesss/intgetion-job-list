Основатель 2026-10-21: ТЗ «Spoki Core Upgrade, этап 1». **Только анализ и проект. Код, миграции, коммиты и выкладка — после отдельного «да».** Исходный аудит — [31-spoki-core.md](31-spoki-core.md); ниже его утверждения перепроверены по коду (master `094707f`).

Обозначения: **[факт]** — проверено в коде или базе; **[замер]** — измерено; **[оценка]** — расчёт; **[не проверено]**.

> **Статус 2026-10-21:** реализовано в ветке `claude/spoki-core-stage1` (не в master, не выложено): D520 (подтверждения), D521 (журнал; миграция 0070 написана и не применена), D522 (маршрутизация). Решения основателя: порядок — безопасность, журнал, маршрутизация; лишний клик приемлем; хранение 180 дней через `BOT_ACTIONS_RETENTION_DAYS`; только бесплатные модели и локальные eval; «Мои действия Spoki» — позже; полный набор не отдавать при неуверенности.

## 1. Что сейчас реализовано

- **[факт]** Реестр `TOOLS` (`src/modules/bot/service/tools.ts`) — 98 инструментов; `toolsFor(userId, state)` отбирает набор по входу и теме нити; `runTool` проверяет вход (`access`), схему, подтверждение (`confirm` + `hashArgs`).
- **[факт]** Провайдер на сервере сверяет каждый вызов модели с инструментами **этого** запроса (`src/lib/llm/provider.ts`, `LLMOutputError("Unknown tool …")`): модель не может вызвать то, что ей не дали в раунде.
- **[факт]** Ход — `handleMessage` (`conversation.ts`): лимиты по тарифу → извлечение фактов профиля (отдельный вызов модели, кроме черновика вакансии) → до 3 раундов с инструментами → запасной ответ. Пишущий инструмент с карточкой останавливает ход; `confirmAction` выполняет его после «Подтвердить» (одноразовое `decideConfirmation`), D515 добавляет ход Spoki после карточки.
- **[факт]** Журналы: `bot_confirmations` (стирается через 24 ч), `bot_messages.tool_call` (обнуляется через 24 ч, строки с токенами живут 180 дней), `audit_logs` (365 дней, пишут отдельные сервисы: кошелёк, UGC, админка).
- **[факт]** Eval: 76 записанных случаев в `evals/*` (account 11, adversarial 18, freelance 11, memory 8, onboarding 20, pitch 3, ugc 5), прогон без сети — `pnpm eval` (`eval-ci.test.ts`), живой прогон — `pnpm eval:live` (нужен ключ модели, он только в Vercel).

## 2. Проблемы, подтверждённые кодом

### 2.1 Размер набора инструментов — исправление моей оценки

| Нить              | Инструментов | Схемы, символов | Весь запрос, символов | Токенов на вызов                            |
| ----------------- | ------------ | --------------- | --------------------- | ------------------------------------------- |
| Гость, общая      | 11           | 10 611          | 26 545                | **7 240** [замер, среднее по базе]          |
| Вошедший, UGC     | 25           | 15 988          | 34 383                | **8 669 (сред.), 10 142 (медиана)** [замер] |
| Вошедший, общая   | 97           | 66 337          | 84 732                | ~23 500 [оценка]                            |
| Вошедший, фриланс | **97**       | 66 337          | 84 732                | ~23 500 [оценка]                            |
| Черновик вакансии | 3            | 2 119           | 20 514                | ~5 700 [оценка]                             |

- Символы — **[замер]** точного тела запроса `toOpenRouterRequest` (временный тест, удалён). Токены для гостя и UGC — **[замер]** провайдера из `bot_messages.tokens_in` за 7 дней; соотношение ~3,6 символа на токен перенесено на остальные строки.
- В аудите 31 стояло «~25,7 тыс. токенов на инструменты» — **завышено**: я тогда мерил внутренние объекты схем. Верно: **схемы ~18 тыс., весь запрос ~24 тыс. токенов** в общей нити.
- **Нить фриланса не сужает набор** — получает все 97 (отбор есть только для `ugc`, черновиков и гостя).
- Ход целиком **[замер, 75 ходов, 7 дней, бесплатные модели]**: ~1,8 вызова модели (ответ + извлечение), в среднем 21,4 тыс. токенов, максимум 76 тыс.; время ответа медиана 11 с, p90 34 с. Вызовов общей нити с 97 инструментами за неделю не было — для неё только оценка.

### 2.2 Отправка брифа UGC и услуги фрилансера на модерацию

- **[факт]** Обработчики: `confirm_brief` → `confirmBriefDraft` (`src/modules/ugc/service/drafts.ts`) → `createCampaign`; `confirm_service_draft` → `confirmServiceBriefDraft` (`src/modules/freelance/service/drafts.ts`) → `createService` + `submitService`. Оба — `confirm: read` (без карточки).
- **[факт]** Сервер проверяет: вход, режим черновика, полноту черновика, и что **последнее сообщение человека начинается со слова согласия** (`isExplicitBriefConfirmation`, `isExplicitServiceDraftConfirmation`). Поправка к аудиту 31: проверка на сервере есть, решает не только модель.
- **[факт, проверено на образцах]** Проверка слабая:

  | Ответ человека            | Бриф UGC     | Услуга                                    |
  | ------------------------- | ------------ | ----------------------------------------- |
  | «да, но не запускай пока» | **проходит** | нет                                       |
  | «ок, добавь ещё пример»   | **проходит** | **проходит**                              |
  | «давай поменяем бюджет»   | **проходит** | **проходит**                              |
  | «да, исправь цену»        | **проходит** | **проходит**                              |
  | «да, конечно»             | проходит     | нет (ложный отказ: «не» внутри «конечно») |

  У брифа отрицание по-русски не работает совсем: `\b` в JS не видит границ кириллических слов. Если модель на такой ответ вызовет инструмент, сервер отправит бриф или услугу на модерацию. Ответ «да» на любой вопрос Spoki («добавить пример?») неотличим от согласия на отправку — класс ошибки D515.

- **[факт]** Повтор: черновик превращается в бриф или услугу, затем удаляется — не одной транзакцией и без блокировки. Два одновременных вызова создадут два брифа или две услуги. Карточка закрывает это: `decideConfirmation` одноразовая.
- **[факт]** Последствия ограничены: бриф идёт на модерацию (не публичен до админа; есть `withdraw_ugc_campaign`), услуга — тоже на модерацию. Денег не касается.
- **[факт]** Попутно: `confirmAction` не сохраняет `outcome.state` инструмента — после подтверждённой карточки `confirm_job_draft` нить остаётся в режиме черновика до следующей правки.

### 2.3 Журнал действий

- **[факт]** Какое действие Spoki выполнил по чьему подтверждению и с каким итогом — через сутки восстановить нельзя: карточки и вызовы стираются, `audit_logs` пишут не все сервисы и не знают, что действие пришло от Spoki.

## 3. Сравнение вариантов маршрутизации

| Критерий                       | A. По контексту                                                 | B. Динамическое обнаружение                                            | Гибрид: A + догрузка                                           |
| ------------------------------ | --------------------------------------------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------- |
| Точность выбора                | Высокая внутри раздела; промах при просьбе «из другого раздела» | Зависит от модели: лишний шаг выбора, бесплатные модели ошибаются чаще | Высокая: раздел + слова сообщения + догрузка по запросу модели |
| Межсервисные задачи            | Плохо, если раздел не угадан                                    | Хорошо                                                                 | Хорошо: догрузка нужных доменов в тот же ход                   |
| Токены                         | Минимум                                                         | Каталог + догрузка; на межсервисной задаче — как гибрид                | Близко к A; рост только при догрузке                           |
| Задержка                       | Как сейчас или меньше (короче запрос)                           | **+1 вызов модели почти всегда** (сначала выбрать, потом выполнить)    | +1 вызов только при догрузке (редко)                           |
| Доп. вызовы модели             | 0                                                               | ~1 на ход                                                              | 0, иногда 1 (лимит 1 догрузка на ход)                          |
| Сложность                      | Малая                                                           | Средняя–высокая                                                        | Средняя                                                        |
| Устойчивость к ошибке маршрута | Нет запасного пути                                              | Есть                                                                   | Есть (догрузка; повтор с полным набором при «нет инструмента») |
| Безопасность                   | Не меняется                                                     | Не меняется, если догрузка идёт через `toolsFor`                       | Не меняется: тот же `toolsFor`, проверка провайдера, `runTool` |
| Совместимость                  | Полная                                                          | Меняет цикл хода                                                       | Полная: поверх `toolsFor` и раундов                            |
| Масштаб                        | Растёт с числом разделов, но по ключевым словам                 | Хорошо                                                                 | Хорошо: новый модуль = новый домен с описанием в каталоге      |

- Нативный поиск инструментов Anthropic (`tool_search` + `defer_loading`) — это вариант B на стороне провайдера, но только для Claude API. Проект по умолчанию на OpenRouter (D317), поэтому серверный механизм должен быть свой.
- **Промпт-кэш меняет расчёт для платной модели.** У Claude стабильный префикс (инструменты + системный промпт) читается из кэша по $0,20 за миллион вместо $2. Полный набор в 97 инструментов из кэша стоит ~$0,004 за вызов; меняющийся набор кэш ломает. Поэтому гибрид должен держать **стабильный порядок**: сначала ядро, потом домены в фиксированном порядке. Тогда префикс ядра кэшируется. Для бесплатных моделей OpenRouter кэш не управляется — там выигрыш маршрутизации прямой (точность, скорость, контекст).

**Вывод: гибрид.** Чистый B медленнее на каждом ходе: лишний вызов модели при текущей медиане 11 с — плохой обмен. Чистый A не держит межсервисные просьбы.

## 4. Рекомендуемая архитектура

```
сообщение ─► лимиты ─► определить домены ─► собрать набор ─► раунд модели ─┬─► ответ
              (как сейчас)  │                  (toolsFor + домены)          ├─► вызов инструмента ─► runTool (права, карточка)
                            │                                               └─► use_tools(домены) ─► добавить домены ─► следующий раунд того же хода
                            └─ режим/тема нити, страница (from=…), ключевые слова сообщения, домены прошлого хода, ядро
```

- **Домены** — поле `domain` у каждого инструмента: `core`, `jobs`, `account`, `employer`, `company`, `ugc`, `freelance`, `events`, `reminders`, `billing`. В `core`: `offer_step`, `get_my_cards`, `get_my_standing`, `remember_fact`, `forget_fact` и мета-инструмент `use_tools`.
- **Определение доменов без вызова модели** (`src/modules/bot/service/routing.ts`, новый): режим черновика → только его инструменты (как сейчас); тема нити (`ugc`, `services`, `freelance`, `job`) → её домен; словарь ключевых слов ru/en по доменам (вакансия, отклик, бриф, ролик, креатор, услуга, заказ, фрилансер, тариф, оплата, компания, напоминание, событие…); домены прошлого хода (`state.domains`, «липкие» на 2 хода); пустой результат → `core` + `jobs` (как основной сценарий).
- **`use_tools`** — гостевой инструмент `core` без карточки: `{ domains: [...] }`. В описании — каталог: одна строка на домен. Вызов добавляет домены в набор **следующего раунда этого хода**; не больше одной догрузки и не больше 3 доменов за ход; ход не тратит лишнее сообщение лимита. Набор всегда строится через `toolsFor`: гость не получит инструменты вошедшего, черновик не получит чужие.
- **Запасной путь**: если модель ответила «нет подходящего инструмента» или вызвала неизвестный (`LLMOutputError`), и догрузки ещё не было — один повтор раунда с набором `toolsFor` целиком (поведение как сегодня).
- **Выключатель**: `SPOKI_TOOL_ROUTING=off` в окружении → набор как сейчас (полный `toolsFor`). Откат без отката кода.
- **Порядок набора стабильный**: ядро → домены в фиксированном порядке → внутри домена порядок реестра. Префикс ядра кэшируется на Claude.
- Телеметрия: в `bot_messages.tool_call` раунда — `domains` и число инструментов (рядом с `promptVersion`); метрика в админке — токены на ход по доменам.

## 5. Устранение рисков подтверждения

Минимальное исправление в существующем механизме карточек:

1. `confirm_brief` и `confirm_service_draft` → `confirm: write` (карточка) + `preview`: название продукта или услуги; заодно проверка полноты черновика до карточки (как D515).
2. Проверка «явного да» переезжает до карточки: общее поле инструмента `requiresExplicitYes(text)`, его проверяет `callTool` до `createConfirmation` (сейчас так сделано только для `confirm_job_draft`). Без явного «да» — «карточка не показана, дождитесь согласия».
3. Регулярные выражения согласия — одна общая функция для трёх черновиков: границы слов через `\p{L}` с флагом `u`; отрицание целым словом («не», «нет», «пока нет», «not», «no»); «да» + просьба что-то поменять («да, исправь…», «давай поменяем…») — не согласие на отправку.
4. `confirmAction` сохраняет `outcome.state` инструмента (выход из режима черновика после подтверждения).
5. Тексты карточек: «Отправить бриф на модерацию?», «Отправить услугу на модерацию?» на 7 языках; в Telegram — как у других карточек, ссылкой на сайт.

UX: на одно нажатие «Подтвердить» больше — как у вакансии сегодня. Повтор невозможен: карточка одноразовая.

## 6. Журнал действий Spoki

**Почему новая таблица, а не `audit_logs`**: у действия меняется состояние (ждёт → выполняется → итог), нужна уникальность для защиты от повтора и выборка «мои действия» по пользователю. `audit_logs` — только добавление строк, без этих свойств; он остаётся журналом сервисов и админки.

Миграция `0070_bot_actions.sql` (черновик, **не создана и не применена**):

```sql
CREATE TABLE IF NOT EXISTS public.bot_actions (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL REFERENCES public.users(id) ON DELETE CASCADE,
  conversation_id uuid REFERENCES public.bot_conversations(id) ON DELETE SET NULL,
  channel text NOT NULL DEFAULT 'web',            -- web | telegram
  tool text NOT NULL,
  kind text NOT NULL,                              -- card | direct
  status text NOT NULL,                            -- awaiting_confirmation | executing | completed | failed | cancelled | expired | interrupted
  confirmation_id uuid UNIQUE,                     -- одна карточка = одно действие
  args_hash text,                                  -- хеш, не аргументы
  entity_type text,                                -- job | ugc_campaign | freelance_service | application | …
  entity_id text,
  error_code text,                                 -- код HttpError, без текста и деталей
  confirmed_at timestamptz,
  finished_at timestamptz,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT bot_actions_channel_check CHECK (channel IN ('web', 'telegram')),
  CONSTRAINT bot_actions_kind_check CHECK (kind IN ('card', 'direct')),
  CONSTRAINT bot_actions_status_check CHECK (status IN ('awaiting_confirmation', 'executing', 'completed', 'failed', 'cancelled', 'expired', 'interrupted'))
);
CREATE INDEX IF NOT EXISTS bot_actions_user_idx ON public.bot_actions (user_id, created_at DESC);
SELECT public.enable_rls_deny_all('public.bot_actions');
GRANT SELECT, INSERT, UPDATE, DELETE ON public.bot_actions TO app_rw;
```

Жизненный цикл:

- **Карточка**: при `createConfirmation` — строка `awaiting_confirmation` (`confirmation_id`). «Отмена» → `cancelled`. Истёкшая карточка → `expired` (крон `retention`, который уже стирает карточки). «Подтвердить» → `decideConfirmation` (одноразовая) → `executing` → `run` → `completed` с `entity_*` или `failed` с `error_code`.
- **Без карточки** (только пишущие: `save_job`, `hide_job`, `remember_fact`, `forget_fact`, `reset_*`; черновые `patch_*` не пишутся — их много и они правят только черновик): одна строка `completed` или `failed` после выполнения.
- Чтение не пишется.
- **Согласованность**: бизнес-операция и журнал — в разных транзакциях (сервисы владеют своими). `executing` пишется до `run`, итог — после. Строка, застрявшая в `executing` дольше 10 минут, помечается `interrupted` (крон `retention`); сущность проверяется по `entity_*`, если она записана. Повтор действия невозможен: карточка одноразовая, `confirmation_id` уникален.
- **Данные**: без аргументов, текстов, контактов, адресов кошельков — только инструмент, хеш, тип и id сущности, код ошибки.
- **Доступ**: RLS deny-all; чтение только сервером. `GET /api/me/actions` — свои строки по `user_id` из сессии (позже, этап 1б); админка — позже.
- **Хранение**: 365 дней, как `audit_logs` (`src/config/retention.ts`, крон `retention`); входит в выгрузку данных и удаляется вместе с аккаунтом (`src/modules/privacy`).
- Инструмент сообщает сущность через необязательное поле результата `ToolOutcome.audit = { entityType, entityId }`; без него строка пишется без ссылки.

## 7. Экономия токенов и как её проверить

**[оценка]** на один вызов модели, вошедший в общей нити:

|                | Сейчас  | Гибрид, обычный ход | Гибрид с догрузкой |
| -------------- | ------- | ------------------- | ------------------ |
| Инструментов   | 97      | 12–25               | до ~40             |
| Схемы, токенов | ~18 000 | ~3 000–6 000        | ~9 000             |
| Запрос целиком | ~24 000 | ~9 000–12 000       | ~15 000 (+1 вызов) |

Стоимость хода на Claude Sonnet 5.5 ($2 / $10 за миллион; извлечение — Haiku 4.5 по умолчанию проекта, $1 / $5) **[оценка, без кэша]**:

| Сценарий                | Вызовов        | Сейчас  | Гибрид                |
| ----------------------- | -------------- | ------- | --------------------- |
| Простой вопрос          | 1 + извлечение | ~$0,055 | ~$0,025               |
| Действие с инструментом | 2 + извлечение | ~$0,105 | ~$0,045               |
| Межсервисная задача     | 3 + извлечение | ~$0,16  | ~$0,075 (с догрузкой) |

С промпт-кэшем на Claude разница меньше (полный набор из кэша дёшев), но остаются точность, задержка и место в контексте. Сейчас модели бесплатные ($0) — главный выигрыш в точности выбора и скорости, не в деньгах.

Методика, воспроизводимая:

1. **Без ключа (детерминированно)**: новый `routing.test.ts` — для каждого из 76 случаев `evals/*` и 20 новых (простые, сложные, межсервисные: «найди монтажёра, помоги создать заказ и проверь тариф») проверить, что ожидаемый инструмент попадает в набор маршрутизатора; посчитать число инструментов и символов набора.
