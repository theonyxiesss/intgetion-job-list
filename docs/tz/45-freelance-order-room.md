## 2. Архитектура: одна лента событий заказа

Главная идея: у заказа одна **лента** — сообщения людей и события системы в одном порядке времени. Каждый будущий этап добавляет в неё свой вид события, а не новый экран.

| Вид записи                                                                            | Источник                      | Этап |
| ------------------------------------------------------------------------------------- | ----------------------------- | ---- |
| `message` — сообщение стороны (текст и до 5 ссылок `https://`)                        | новая таблица сообщений       | A1   |
| `status` — смена статуса (запрос, принят, в работе, сдан, правка, завершён, отменён…) | `freelance_order_history`     | есть |
| `delivery` — ссылка на результат                                                      | заказ                         | есть |
| `payment` — оплата подтверждена                                                       | платежи D463                  | есть |
| `escrow` — создан, оплачен, спор открыт, решение арбитра, возврат                     | состояние и события контракта | B1   |
| `dispute` — спор: причина, ответы сторон, решение                                     | будущая таблица споров        | B2   |
| `review` — отзыв стороны                                                              | отзывы                        | A2   |

Слой:

- **Модуль:** `src/modules/freelance` (свой модуль, без нового). Вызовы из других модулей — только через `service/index.ts`.
- **Чистое ядро (без базы, сделано в этом шаге):** `service/order-room.ts` — правила сообщений и сборка ленты из любых источников. Тестируется без базы.
- **Хранилище (после «да»):** таблица сообщений, привязанная к **нити**, а не прямо к заказу: `freelance_threads(id, subject_type, subject_id)` и `freelance_messages(id, thread_id, author_id, body, links, created_at, hidden_at, hidden_by)`. `subject_type` сейчас `order`; позже `proposal` (A3, переписка по отклику до заказа; при выборе отклика нить переходит к заказу) и `dispute` (B2). Это одно место хранения для всех будущих переписок.
- **Права:** читать и писать могут только две стороны заказа; чужой заказ — 404 (как §28.4). Модератор читает только по жалобе, чтение пишется в `audit_logs`. Модель Spoki текст сообщений получает только своей стороны и без контактов (12.4).
- **Доставка:** без веб-сокетов. Страница опрашивает ленту раз в 15 с, пока открыта и видима (как прочие части сайта без realtime); уведомление о новом сообщении — через уведомления D456 (сайт, почта сводкой не чаще раза в 30 мин на заказ, Telegram).
- **Лимит:** новое правило `freelanceMessage` в `rateRules` (предложение: 30 сообщений в час на аккаунт).
- **Модерация:** жалоба на сообщение — общая `reports` (D462) с типом `freelance_message`; модератор скрывает сообщение (`hidden_at`), текст не удаляется до срока хранения.
- **Приватность:** экспорт аккаунта включает свои сообщения; при удалении аккаунта сообщения другой стороны остаются, автор — «удалённый аккаунт» (§28.10).

## 3. Правила сообщения (A1)

- Писать можно в `sent`, `accepted`, `in_progress`, `delivered`. В конечных статусах лента только для чтения (кроме будущего спора B2).
- Текст 1–2 000 знаков после обрезки пробелов; до 5 ссылок, только `https://`; повторы ссылок убираются.
- Контакты: в `sent` (до принятия запроса) — запрещены, как в тексте запроса и отзыва (`hasContacts`), ошибка с понятным текстом. С `accepted` контакты сторон и так открыты (§28.7) — фильтр не применяется. Это повторяет текущее правило D447; другое — вопрос §8.
- Загрузка файлов не делается (§28.12): только ссылки.
- Редактирование и удаление своих сообщений — нет (для споров нужна неизменная история); исправление — новым сообщением.

## 4. Фронтенд: страница «комната заказа»

Та же адресация `/freelance/orders/[id]`, одна страница для обеих сторон. Компоненты — из `src/components/ui/`, токены — из `globals.css`, без теней и инлайн-стилей, один основной button на экран (D428).

```
Desktop (≥1024 px)                                   Телефон (<768 px)
┌───────────────────────────────────────────────┐    ┌───────────────────────┐
│ Название услуги · пакет · цена (mono) · статус│    │ Шапка + статус        │
│ Шаги: запрос → принят → оплачен → в работе →  │    │ Шаги (короткие)       │
│       сдан → завершён                          │    │ [Лента] [Детали]      │
├───────────────────────────────┬───────────────┤    │ (вкладки)             │
│ Лента                         │ Детали        │    │                       │
│  ─ событие статуса (тихо)     │  Задача       │    │ Лента …               │
│  ─ сообщение стороны          │  Результат    │    │                       │
│  ─ событие оплаты / эскроу    │  Контакты     │    │                       │
│  ─ …                          │  Оплата/эскроу│    │                       │
│ [поле ввода ............] [→] │  Действия     │    │ [поле ввода]  [→]     │
│                               │  Пожаловаться │    │                       │
└───────────────────────────────┴───────────────┘    └───────────────────────┘
```

- **Шапка:** что заказано, цена `font-mono`, статус — точка 6 px + текст (не только цвет, 1.4.1).
- **Шаги:** короткий список этапов заказа; текущий отмечен текстом и `aria-current="step"`.
- **Лента:** сообщения людей — обычным текстом с именем стороны («Исполнитель», «Заказчик», без личных имён до `accepted`); события системы — тихой строкой `text-fg-muted` с временем `font-mono`. `aria-live="polite"` для новых записей; дата-разделители.
- **Поле ввода:** 44 px высотой, подпись, счётчик знаков, ошибка `role="alert"` + `aria-describedby`; отправка Enter, перенос Shift+Enter; кнопка с `aria-label`.
- **Детали:** нынешние блоки страницы (задача, результат, контакты, оплата, действия, жалоба) переезжают в правую колонку без изменения логики.
- **Пустая лента:** короткая подсказка, что писать (D428: пустое состояние — приглашение к действию).
- **Telegram и Spoki:** ссылка «Открыть переписку» ведёт на страницу; ответ из Telegram — позже, отдельным решением.

Проверка вида: desktop и 375 px, Tab по ленте и полю, скрипт `scripts/layout-audit.browser.js`, axe.

## 6. Критерии приёмки A1

- [ ] Стороны пишут друг другу на странице заказа; третий человек получает 404.
- [ ] Контакты в `sent` отклоняются с понятной ошибкой; с `accepted` проходят.
- [ ] В конечных статусах писать нельзя (409), читать можно.
- [ ] Лента показывает сообщения и события в одном порядке времени, на desktop и 375 px; Tab и экранный диктор проходят поле и ленту.
- [ ] Лимит сообщений работает; жалоба на сообщение попадает в общую очередь; скрытое модератором видно как «скрыто».
- [ ] Уведомление о новом сообщении приходит второй стороне (без спама: сводка).
- [ ] `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build` — зелёные; интеграционные и e2e — в CI.

## 7. Что не входит

- Загрузка файлов, редактирование и удаление сообщений, звонки, ответ из Telegram.
- Споры (B2), эскроу-события (B1), отклики (A3) — только место в архитектуре.
- Изменение правила открытия контактов без решения основателя.

## 8. Решения основателя

1. **Срок хранения переписки.** Предложение: пока заказ открыт и 180 дней после конечного статуса (для споров и жалоб), затем удаление текста. Сейчас переписка Spoki живёт 24 часа (D471) — это другой случай. Нужно ваше решение (персональные данные).
2. **Контакты в переписке.** Оставить как сейчас (до принятия — запрещены, после — открыты) или, как на Upwork, держать общение на платформе дольше. Второе меняет D447.
3. **Лимит сообщений** — 30 в час на аккаунт подходит?
4. **«Да» на миграцию** таблиц §2 (облако общее с продакшеном, путь D438).
