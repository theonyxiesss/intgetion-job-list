## Часть 1. Реальное состояние

### 1.1 Где живёт Spoki

- **[факт]** Весь агент — модуль `src/modules/bot` внутри того же приложения Next.js, отдельного сервиса нет. Вход: `POST /api/bot/message` (SSE), `POST /api/bot/confirm`, `POST /api/bot/continue` (D515), `GET /api/bot/conversation`, `POST /api/bot/fill`, `/api/bot/memory*`, `/api/bot/feedback`; Telegram — `src/modules/bot/service/telegram-agent.ts` через `/api/telegram/webhook`.
- **[факт]** Цикл хода — `handleMessage` в `src/modules/bot/service/conversation.ts` (2156 строк): лимиты → запись текста (с `redactPii`) → извлечение фактов профиля (`extract.ts`, отдельный вызов модели) → системный промпт → до 3 раундов модели с инструментами (`MAX_TOOL_ROUNDS`) → запасные ответы. Пишущий инструмент останавливает ход карточкой подтверждения.
- **[факт]** Промпт — `src/modules/bot/prompts/system.ts`, версия 44, ~4,5 тыс. токенов для вошедшего **[оценка]**. Темы нитей (`job`, `services`, `ugc`, `freelance`, черновики) добавляют свои блоки: `job-focus.ts`, `service-focus.ts`, `ugc-focus.ts`, `freelance-focus.ts`, `job-draft-focus.ts`.
- **[факт]** Модели — `src/lib/llm/select.ts`: по умолчанию OpenRouter, бесплатные `nvidia/nemotron-3-super-120b-a12b:free` (чат) и `google/gemma-4-26b-a4b-it:free` (извлечение); переключатель `LLM_PROVIDER=anthropic` (Sonnet / Haiku с ценами из окружения). Бюджет: `MAX_OUTPUT_TOKENS = 800`, `MAX_INPUT_TOKENS = 6000`, `MAX_HISTORY_MESSAGES = 12` (`src/lib/llm/budget.ts`), дневной предохранитель `LLM_DAILY_BUDGET_USD`, проверка аномалий расхода за 14 дней, дневные лимиты сообщений по тарифу (15 / 100 / 300, гость 5).
- **[факт]** Защита от prompt injection: текст человека и результаты инструментов оборачиваются в `<untrusted_data>` (`src/lib/llm/untrusted.ts`), правило в промпте; утёкшая разметка вызовов вырезается (`leaked-tool.ts`); контакты и ссылки из карточек модели не передаются (`cardFields`); подтверждение привязано к инструменту, пользователю и хешу аргументов (`hashArgs`), сервер повторно проверяет его в `runTool`.

### 1.2 Инструменты

- **[факт]** Один реестр `TOOLS` в `src/modules/bot/service/tools.ts`: **98 инструментов** (13 гостевых, 85 для вошедших). **47 пишут только через карточку подтверждения**, 51 — без карточки: чтение, черновики (`patch_*_draft`, `patch_brief`), память (`remember_fact`, `forget_fact`), `save_job`, `hide_job`, `focus_ugc`, а также `confirm_brief` и `confirm_service_draft` (отправка на модерацию без карточки).
- **[факт]** Механизм общий для всех модулей: `BotTool` = схема zod + `access` (guest/user) + `confirm(ctx)` + `preview` (что назовёт карточка, проверка статуса до карточки — D515) + `run`. Модули несут свои инструменты сами: `src/modules/ugc/service/bot-tools.ts`, `src/modules/freelance/service/bot-tools.ts`; остальные лежат в модуле бота (`account-tools.ts`, `company-tools.ts`, `employer-job-tools.ts`, `job-tools.ts`, `reminders.ts`, `pitch.ts`, `my-cards-tool.ts`).
- **[факт]** Каждый инструмент — тонкая обёртка над той же функцией сервиса, что и маршрут сайта (`src/modules/<m>/service/index.ts`). Параллельных бизнес-процессов у Spoki нет.
- **[факт]** MCP-сервер `POST /api/mcp` (`src/modules/mcp/service/server.ts`, D480–D487) берёт из того же реестра только гостевые инструменты без карточек — только чтение.
- **[оценка]** Размер: в общей нити вошедший получает **97 инструментов, ~25,7 тыс. токенов схем на каждый вызов модели**; гость — 11 (~7,5 тыс.), нить UGC — 25 (~4,1 тыс.), черновик вакансии — 3 (~1 тыс.). Лимит `MAX_INPUT_TOKENS` считает только промпт и историю, не схемы инструментов.

### 1.4 Контекст, история, память

- **[факт]** Нить — `bot_conversations` (состояние `state` jsonb: тема, режимы черновиков, черновик профиля, `fillOffered` и др.), сообщения — `bot_messages`. **Текст переписки живёт 24 часа** (D471, `CHAT_TEXT_TTL_MS`, крон `retention` каждый час); строки с токенами и расходом — 180 дней.
- **[факт]** Память о человеке — `bot_memory_facts` (до 30 фактов по 200 знаков, `user-memory.ts`), пишется `remember_fact` **без карточки**; человек видит, добавляет и стирает её в «Настройки → Конфиденциальность» (`/api/bot/memory*`). Отдельного выключателя «не запоминать» нет.
- **[факт]** `KNOWN PROFILE` в каждом ходе — из общего профиля `user_profiles` с подробностями кандидата (D505, `readRemembered`); `MEMORY` — список фактов.
- **[факт]** Пользователь берётся из сессии Supabase (`getCurrentUser`); гостевая нить привязывается к аккаунту при входе (D324). В Telegram — через `telegram_accounts`.

### 1.5 Веб и Telegram

- **[факт]** Одна идентичность (`users`), одна память и общий профиль в обоих каналах. **Нити разные**: у Telegram своя нить на чат (`chatSessionToken`), состояние (режим черновика, тема) не общее; сами черновики — общие (на пользователя).
- **[факт]** Карточки подтверждения в Telegram не нажимаются: бот даёт ссылку `/chat?confirm=<id>` на сайт; ответ Spoki после карточки (D515) приходит в чат сайта. Кнопки «Принять/Отклонить» в Telegram есть только у заявок фриланса (`telegram-actions.ts`, D456).

### 1.6 Единый аккаунт

- **[факт]** `users` (вход, язык, роль платформы `user`/`admin`) + `user_profiles` (общее «Обо мне», один источник после D509) + `user_wallets` (кошелёк, D518) + способы входа (почта, Google, X, Telegram).
- **[факт]** Данные сервисов — у сервисов, по `user_id`: `candidate_profiles` (+ навыки, опыт, контакты, предпочтения), `company_members` + `employer_profiles`, `creator_profiles`, `freelance_sellers` и услуги, брифы, заказы. Один человек может быть всем сразу; типа аккаунта нет (D506, `account_type` удалён).
- **[факт]** Права: роль платформы; роль в компании (`owner`/`admin`/`recruiter`/`viewer`, `requireMembership`); тарифы — `purchases` пользователя (`candidate`: Plus, Pro) и компании (`company`: Hire, Team), читает `billingMe`.
- **[факт]** Согласия и настройки: `consent_records` (cookies), `notification_preferences` (тип × канал), скрытие профиля, утренние сводки, язык писем. Экспорт и удаление — `src/modules/privacy`.
- **[факт]** Остатки «категорий»: отклик требует профиль кандидата (`requireCandidate` → 404, 3 маршрута); «Беру заказы», услуги фриланса требуют профиль кандидата (4 места `CANDIDATE_PROFILE_REQUIRED`). Это этап В ТЗ 30, отложен основателем.
- **[факт]** История действий: `audit_logs` пишут не все сервисы (кошелёк, UGC, часть админки). Подтверждённые карточки (`bot_confirmations`) и вызовы инструментов в `bot_messages.tool_call` **стираются через 24 часа** — долгого журнала «что Spoki сделал по просьбе человека» нет.

### 1.7 Проактивность

- **[факт]** Кроны (`vercel.json`, 17 штук): подбор (`matching`, каждую минуту, очередь `matching_jobs`), уведомления, утренние сводки (LLM пишет только вступление — `brief-intro.ts`, с шаблоном при сбое), поиск-алерты, Telegram (напоминания, канал), фриланс, UGC (сроки, взносы), импорт, оплата, санкции, хранение.

- **[факт]** Все действия Spoki — обёртки над сервисами, у которых есть страницы и формы. Без модели (`BOT_UNAVAILABLE`, `BOT_BUDGET_EXCEEDED`) сайт работает: формы вакансии, брифа, услуги, профиля, оплаты. Утренние сводки откатываются на шаблон.

## Часть 3. Сильные стороны и недостатки

**Сделано правильно — не переписывать**

1. Инструменты как обёртки сервисов: Spoki не обходит бизнес-правила, права проверяет сервис.
2. Карточка подтверждения с привязкой к пользователю и хешу аргументов, повторная проверка на сервере, проверка статуса до карточки (D515).
3. Один реестр для Spoki и MCP; модули несут свои инструменты (UGC, фриланс).
4. Общий профиль и единая идентичность (D504–D509, D517, D518).
5. Защита от injection: untrusted-обёртка, контакты мимо модели, вырезание утёкшей разметки.
6. Бюджет: лимиты по тарифу, дневной предохранитель, аномалии; бесплатные модели.
7. Отказоустойчивость: всё доступно через формы без модели.
8. Кроны, уведомления, каталог и предпочтения каналов — готовая основа проактивности.

**Технический долг**

1. **Все 97 инструментов в каждом вызове** общей нити (~25,7 тыс. токенов **[оценка]**): дорого на платной модели, хуже выбор инструмента у бесплатной, медленнее. Больше всего мешает росту Spoki.
2. `conversation.ts` на 2156 строк смешивает лимиты, режимы, фильтры, запасные ответы и выбор вакансий; режимы нитей — набор флагов (`topic`, `ugcDraftMode`, `freelanceDraftMode`, `jobDraftMode`) и фильтры по подстроке имени инструмента (`call.name.includes("ugc")`).
3. Нет долгого журнала действий агента: карточки и вызовы стираются через 24 часа, `audit_logs` пишут не все сервисы.
4. Часть инструментов чужих доменов лежит в модуле бота (`employer-job-tools.ts`, `account-tools.ts`, `company-tools.ts`): бот становится «знающим всё» модулем.
5. Память без явного выключателя; `remember_fact` пишет без карточки.
6. `confirm_brief` (UGC) и `confirm_service_draft` (фриланс) отправляют на модерацию без карточки: «явное да» решает модель. У вакансии сервер сам проверяет фразу (`isExplicitJobDraftConfirmation`) и всё равно показывает карточку.
7. Нити веба и Telegram не делят режим работы; карточки в Telegram не нажимаются.
8. Промпт и бюджет на грани: ~4,5 тыс. токенов промпта при лимите 6 тыс. на промпт с историей (D497).

**Наибольшие риски зависимостей**

- Бесплатные модели OpenRouter: их снимают и меняют, рассуждающие модели съедали ответ (D513).
- Связка «бот ↔ все модули» через `import()` и прямые импорты сервисов: изменение сервиса может молча сломать инструмент — нужны тесты инструментов на каждый модуль (частично есть).

## Часть 4. Предлагаемая архитектура

Три варианта:

|                  | A. Чат-бот с инструментами                               | B. Spoki Orchestrator над модулями                   | C. Событийная агентная система                   |
| ---------------- | -------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------ |
| Совместимость    | Полная (это сейчас)                                      | Высокая: тот же реестр и сервисы, другой слой выбора | Низкая: очереди, воркеры, новая инфраструктура   |
| Сложность        | Низкая                                                   | Средняя, по частям                                   | Высокая                                          |
| Расходы          | Растут с числом инструментов (все схемы в каждом вызове) | Ниже: малый набор на ход                             | Выше: фоновые вызовы модели, хранение, очереди   |
| Масштабируемость | Упирается в контекст                                     | Новые модули — новый домен в реестре                 | Высокая, но избыточна сейчас                     |
| Безопасность     | Хорошая (карточки)                                       | Та же + журнал и согласия                            | Больше поверхность: агент действует без человека |
| Сопровождение    | Ухудшается с ростом `conversation.ts`                    | Лучше: домены, маршрутизатор, тесты по доменам       | Тяжело для небольшой команды                     |
| Развитие         | Ограничено                                               | Есть путь к проактивности через кроны                | Максимальное                                     |

**Рекомендация: B с элементами C на существующих кронах** (гибрид). Без новых сервисов и технологий: всё внутри `src/modules/bot` и текущих модулей.

Логические части (это обязанности, а не отдельные приложения):

- **Spoki Orchestrator** — `handleMessage`, разделённый на шаги: лимиты → определение намерения и домена (правила + дешёвый вызов модели только при неясности) → сбор контекста → выбор набора инструментов → раунды → ответ. Режимы нитей — одно поле `mode` вместо флагов.
- **Tool Registry** — тот же `TOOLS`, у каждого инструмента поле `domain` (`jobs`, `account`, `employer`, `ugc`, `freelance`, `events`, `billing`); модули владеют своими инструментами (перенос `employer-job-tools.ts` и др. в их модули — по мере правок).
- **User Context Service** — уже есть: `readSharedProfile`, `readRemembered`, `billingMe`, членство; собрать в одну функцию «контекст человека» с явным списком полей для модели.
- **Memory Layer** — `bot_memory_facts` + общий профиль; добавить выключатель памяти и «сохранить в профиль?» через существующие карточки `propose_*`.
- **Permission & Consent Layer** — уже есть: `access`, `confirm`, проверки сервисов, `notification_preferences`; добавить согласие на память и на проактивные сообщения (тип уведомления).
- **Business Services** — без изменений: `src/modules/<m>/service/index.ts`.
- **Event / Job Processing** — существующие кроны и уведомления; новые «подталкивания» (незаконченный черновик) — тип в каталоге уведомлений и шаг крона, с лимитом частоты; без очередей.
- **Audit & Observability** — `audit_logs` для каждого подтверждённого действия Spoki (кто, инструмент, объект, итог; без аргументов с личными данными), счётчики токенов на ход и по доменам в метриках админки, eval по доменам.

## Часть 5. План

**Этап 1 (минимальный, наибольшая польза) — «малый набор инструментов на ход и журнал действий»**

1. Цель: в каждом вызове модели только инструменты нужного домена; каждое подтверждённое действие Spoki записано надолго.
2. Компоненты: `tools.ts` (поле `domain`, `toolsFor` по домену), `conversation.ts` (выбор домена по теме нити, режиму, словам и предыдущему ходу; общий набор: `offer_step`, `get_my_cards`, `remember_fact`), `confirmAction` → `recordAudit`.
3. Зависимости: нет; миграции не нужны (`audit_logs` есть).
4. Риски: неверный домен → модель не видит нужный инструмент. Защита: запасной путь — повтор раунда с полным набором при «нет подходящего инструмента»; eval.
5. Готово, когда: в общей нити ≤ 25 инструментов на вызов (было 97), схемы ≤ ~6 тыс. токенов **[цель]**; все текущие eval зелёные; запись `audit_logs` на каждое подтверждение и отказ.
6. Тесты: модульные на выбор домена; eval по всем доменам (`pnpm eval`); проверка размера набора в тесте.
7. Сложность: средняя (2–3 сессии).
8. Без нарушения функций: да — инструменты и сервисы не меняются.

**Этап 2 — режимы нитей и разделение `conversation.ts`**

Цель: одно поле `mode` вместо флагов, шаги хода отдельными функциями. Компоненты: `conversation.ts`, `tools.ts`, тесты нитей. Зависимости: этап 1. Риски: регрессии нитей — закрываются существующими тестами и eval. Готово: файл хода < 800 строк, поведение eval не меняется. Сложность: средняя. Без нарушения: да, рефакторинг.

**Этап 3 — память с согласием и повторное использование**

Цель: выключатель памяти; «сохранить навыки в профиль?» после рассказа о себе через существующие карточки; профиль кандидата и фрилансера берут общее. Компоненты: `user-memory.ts`, настройки конфиденциальности, промпт. Зависимости: этап 1. Риски: навязчивые вопросы — одна подсказка на тему. Готово: сценарий 1 проходит в eval. Сложность: малая–средняя. Миграция: возможно одна колонка настройки — отдельное «да».

**Этап 4 — сервис не требует чужого профиля (ТЗ 30 В)**

Цель: отклик и фриланс без обязательного профиля кандидата; недостающее спрашивается в момент нужды. Компоненты: `auth-guards.ts` (`requireCandidate`), `freelance/service/listing-service.ts`, `drafts.ts`, `payment-service.ts`, маршруты откликов. Риски: работодатель видит неполный отклик — минимальный набор полей проверяется сервисом. Готово: фрилансер без профиля кандидата берёт заказы; отклик без профиля не даёт 404. Сложность: средняя.

**Этап 5 — разрешённые подталкивания**

Цель: «вы начали вакансию / бриф / услугу — продолжить?» не чаще одного раза на черновик, с выключением. Компоненты: каталог уведомлений (новый тип), крон `notifications` или `freelance`/`ugc`, `postSystemEvent`, `notification_preferences`. Риски: навязчивость — лимит частоты, тихие часы по поясу. Готово: сценарий 3 работает, выключается в настройках. Сложность: средняя. Миграция не нужна, если хватает существующих таблиц черновиков и уведомлений.

**Этап 6 — недостающие инструменты и Telegram**

Цель: инструменты работодателя для откликов (список, статус, «интерес» — через существующие `/api/applications/*`), карточки подтверждения кнопками в Telegram по образцу D456. Сложность: средняя. Риски: права работодателя — те же `requireMembership`.

**Не делать сейчас**: отдельный сервис оркестратора, очереди и воркеры, векторную память, автономные действия без карточки. Вернуться, когда этапы 1–5 упрутся в предел.

## Ответы на четыре вопроса

1. **Готовность.** Высокая по фундаменту: единая идентичность, общий профиль, один реестр инструментов над сервисами, карточки подтверждения, отказоустойчивость. Низкая по координации: все инструменты в каждом вызове, режимы флагами, нет журнала действий агента, нет разрешённой проактивности.
2. **Что использовать без изменений.** Сервисы модулей и их проверки прав; реестр `TOOLS`, `runTool`, карточки (`bot_confirmations`, `hashArgs`, `preview`); `untrusted`-обёртку; `user_profiles`, `bot_memory_facts`, `readRemembered`; `billingMe`, `requireMembership`; кроны, каталог уведомлений, `notification_preferences`, `postSystemEvent`; MCP-сервер; лимиты и бюджет.
3. **Что исправить первым.** Набор инструментов по домену (контекст и стоимость), журнал подтверждённых действий в `audit_logs`, затем разделение `conversation.ts` и согласие на память.
4. **Следующий этап.** Этап 1: малый набор инструментов на ход и журнал действий — без миграций, без изменения сервисов, с проверкой через eval.
