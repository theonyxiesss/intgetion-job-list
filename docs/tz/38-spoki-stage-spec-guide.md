# ТЗ 38 — как писать ТЗ для каждого этапа Spoki

**Статус:** правило для всех этапов ТЗ 35. Образец: [37-spoki-stage4.md](37-spoki-stage4.md). Это не продуктовое решение и не разрешение на выкладку, оплату или базу данных.

Главный принцип: ТЗ фиксирует, что уже есть, что доказано и что ещё не проверено. Оно не обещает результата, которого нет.

## 1. Когда писать ТЗ

- Перед кодом подфазы, которая трогает больше одного модуля, миграцию, auth, оплату, персональные данные или `src/proxy.ts` (AGENTS.md, «Before complex changes»).
- Перед закрытием этапа: ТЗ обновляется со статусом по каждому требованию.
- Если этап заблокирован внешним действием (вход, ключ, выбор провайдера), ТЗ всё равно пишется: оно фиксирует блокер и то, что можно сделать без него.

## 2. Обязательные разделы

Каждое ТЗ этапа содержит восемь разделов в этом порядке:

1. **Статус.** Дата, что сделано локально, что на сайте, что закоммичено. Одна строка: «аудит и офлайн-проверки выполнены, живая проверка не выполнена».
2. **Основа.** Ссылка на ТЗ-родитель (например, [ТЗ 35](35-spoki-agent-roadmap.md)) и D-номера, которые этап использует. Только те, что нужны.
3. **Что проверено.** Таблица: требование → файл или тест → статус. Статусы только такие:
   - «выполнено по коду» — есть код и тест;
   - «выполнено, живьём проверено» — проверено на сайте под нужным входом, с датой;
   - «не проверено» — с причиной.
4. **Что осталось.** Нумерованный список. У каждого пункта указано, что блокирует: вход, ключ, решение основателя или код.
5. **Критерии приёмки.** Проверяемые пункты, каждый с командой или шагом проверки.
6. **Что не входит.** Явный список, чтобы этап не расширялся «заодно».
7. **Правила выпуска.** Коммит, push и выкладка — только по «да» основателя. Миграции — отдельно.
8. **Обновления документов.** Какие файлы менять по итогам: `CURRENT.md`, `OPEN_TASKS.md`, `MISSION_LOG.md`, `DECISIONS.md`.

## 3. Как проводить аудит перед записью

Аудит только читает код и тесты. Правки кода на этом шаге не делаются.

1. Найти в коде сущности требования: компоненты, сервисы, схемы, тесты. Поиск через Grep по ключевым словам из требования.
2. Для каждого требования записать конкретный файл и строку или название теста. «Есть в коде» без ссылки не засчитывается.
3. Запустить офлайн-проверки: `pnpm typecheck`, `pnpm exec vitest run <папка модуля>`. Записать итог точной цифрой (прошло, пропущено, упало).
4. Если проверка упала — это не «почти готово». Статус этапа: «не выполнено», пока не исправлено.
5. Живую проверку не заявлять без результата. Если сайт или вход недоступны, пункт остаётся «не проверено» с причиной.

## 4. Как формулировать требования

- Требование — одно проверяемое утверждение. Плохо: «чат удобный». Хорошо: «на ширине 390 px поле ввода не перекрыто карточкой».
- Числа — только с источником: из отчёта, из инструмента, из тарифа. Порогов не выдумывать; если порога нет, пункт помечается «ждёт решения основателя».
- Для текстов в интерфейсе — ключи в `src/messages/*.json` во всех языках. Если тексты не согласованы, требование не закрывается.
- Персональные данные и секреты в ТЗ не пишутся. Ключи — только название переменной.

## 5. Что нельзя писать как готовое

- «Работает на сайте», если не открывали сайт под нужным входом.
- «Протестировано», если тест заглушка или пропущен (`.skip`, `skipIf`).
- «Закрыто», пока есть пункт «не проверено» в критериях приёмки.
- Обещания модели: точность, зарплаты, наличие вакансий, результат кампании.

## 6. Блокеры и решения основателя

Если для пункта нужно решение, которое мы принять не можем, в ТЗ пишется отдельный подраздел «Решения основателя»:

- вопрос одной строкой;
- варианты с последствиями;
- что будет сделано по каждому варианту.

Пока решения нет, соответствующий код не пишется. Это касается выбора провайдера, текстов ссылок, порогов качества, хранения данных и расходов.

## 7. Проверка самого ТЗ

Перед коммитом ТЗ перечитывается по списку:

- все восемь разделов на месте;
- каждый статус подкреплён ссылкой на код, тест или отчёт;
- в «что осталось» нет пунктов без блокера;
- нет обещаний без проверки;
- нет секретов и персональных данных;
- ссылки на соседние ТЗ и D-номера существуют.

Ссылки проверяются Grep или `ls`. Недействительная ссылка — дефект ТЗ.

## 8. Коммиты

- ТЗ коммитится отдельным коммитом, только свой файл.
- Сообщение: `docs: ТЗ NN — <название>`.
- Push не делается без «да» основателя. Выкладка — отдельно.

## 9. Минимальный чек-лист для каждого этапа

- [ ] Аудит по требованиям сделан, ссылки на код есть.
- [ ] Офлайн-проверки запущены, цифры записаны.
- [ ] Статусы: выполнено / проверено живьём / не проверено.
- [ ] Блокеры названы, решения основателя вынесены отдельно.
- [ ] Критерии приёмки проверяемые.
- [ ] «Что не входит» заполнено.
- [ ] Правила выпуска и обновления документов указаны.
- [ ] Ссылки проверены.
