## Задача A — живой ход работы в чате («как думает модель»)

### Цель

Пока Spoki работает, человек видит, что происходит: что понял из запроса, какие фильтры поставил, что ищет, сколько нашлось, что делает дальше. Вид — современный и спокойный, в стиле сайта (D428).

### Что есть сейчас

- Строка состояния `thinking-status-line.tsx`: ✦, слово с бликом и секунды (D490).
- Свёрнутый «Ход работы» (`work-progress-card.tsx`, `work-progress.ts`, D538): названия шагов и «Шаг завершён» по событиям `tool_start` / `tool_end`.
- Чат: `@assistant-ui/react` 0.15 (подсказки, D537), ответы `react-markdown`, прокрутка `use-stick-to-bottom`; сообщения и шаги идут через наш SSE, не через runtime assistant-ui.
- Сервер шлёт `tool_start`, `tool_end`, `tool_result`, `ui`, `token`, `job_goal`, `done`.

Не хватает: в шаге нет содержания, нет длительности, шаги появляются рывком, после ответа ход почти пустой, нет сигнала о запасной модели.

### Как это делают другие (аналоги)

- **Perplexity — Steps:** свёрнутый список шагов с поисковыми запросами и источниками, раскрывается по клику.
- **ChatGPT — «Thought for N s»:** одна свёрнутая строка с длительностью, раскрытие по клику.
- **Cursor — таймлайн вызовов инструментов:** каждый вызов — строка со статусом, раскрывается.
- **LangChain Deep Agents — todo list:** план из задач со статусами pending / in progress / completed; выделен один текущий пункт, готовые приглушены.
- **AWS Cloudscape — «Progressive steps»:** шаблон дизайн-системы для поэтапного вывода генеративного ИИ.
- Общие рекомендации паттерн-библиотек: свёрнуто по умолчанию; у шага есть время; без общих «Processing…»; ход не исчезает после ответа; не стримить непонятные человеку детали.

Для Spoki берём: свёрнутую строку с длительностью (ChatGPT), шаги с фильтрами и числом результатов (Perplexity), один выделенный текущий шаг (LangChain), сохранение хода после ответа.

### Главное ограничение — показываем ход, а не «мысли»

Сырые рассуждения модели не показываем: провайдер их не отдаёт (`reasoning: { exclude: true }`), у бесплатных моделей они ненадёжны и бывают на другом языке, D538 запрещает их показывать. Шаги описывает **сервер** по фактическому вызову инструмента и его результату; модель текст шагов не пишет, поэтому шаг не может соврать.

### Что показать

1. **Понял запрос** — строка из фильтров, которые реально ушли в инструмент: «Дизайн · удалённо · без страны».
2. **Шаг поиска** — инструмент, фильтры, итог: «Поиск вакансий: дизайн, удалённо → 5». Если слово запроса снято (D555): «„дизайнер“ ничего не дало — искал без него».
3. **Шаг сравнения или расчёта** — «Сравнение: Autodesk, Coinbase» (D560), «Расчёт UGC: 5 видео».
4. **Ожидание и ошибки** — «Ждёт вашего подтверждения», «Модель не ответила, пробую запасную» (D554).
5. **Таймлайн** — шаги друг под другом с линией, точкой статуса и временем шага; текущий шаг с бликом, готовые приглушены. После ответа сворачивается в «3 шага · 6 с».

### Сервер

- В `tool_end` — безопасная сводка `summary: { key, params }`: ключ текста из `src/messages` и параметры (фильтры, число результатов, длительность в мс). Без аргументов «как есть» (D490). Сводки только для инструментов из белого списка; для остальных — название шага.
- Новое событие `model_fallback` без имени модели и текста ошибки.
- Хранение не меняется: ход не восстанавливается после перезагрузки (D471, D538).

## Задача C — модель Jev для быстроты и переборов

### Что это

**Jev** — модель компании TypeSafe AI, первая из линейки «System One» (анонс 15.09.2026). Она **не пишет текст**: на вход — состояние (текст или JSON) и набор типизированных вопросов, на выход — сразу готовые решения с вероятностями:

- **Choice** — выбрать один вариант из списка (ответ, вероятности по вариантам, уверенность);
- **Score** — оценить по шкале (оценка, вероятности, уверенность);
- **Noul** — да/нет (вероятность «да»);
- **Box** — рамка объекта на картинке (Jev 1.14).

Вопросы одного запроса считаются параллельно, поэтому лишний вопрос почти не добавляет задержки. Заявлено: в 20–200 раз быстрее LLM, ответ за 70–500 мс, оплата только за вход (около $0.042 за 1 млн токенов по данным TypeSafe), выход бесплатный. **Это заявления компании, независимых замеров нет.**

Доступ: прямой API — по листу ожидания; **через OpenRouter — без отдельного аккаунта**, тем же ключом, что уже у Spoki: Decisions API `POST https://openrouter.ai/api/alpha/decisions`, модель `typesafe/jev-1.14` (или `~typesafe/jev-latest`). В общем списке моделей OpenRouter на 2026-10-27 виден только `typesafe/jev-router` с переменной ценой — точную цену подтвердить на странице модели до кода.

Не подходит: свободный текст, объяснения, задачи с долгим рассуждением. Языки в документации не указаны — **русский надо проверить первым делом**.

### Условия и решения основателя до кода

1. Jev платный (только вход). Нужен бюджет в месяц; расходы считаются в `LLM_DAILY_BUDGET_USD` / `budget.ts` (D213).
2. Подтвердить на странице OpenRouter модель, цену и формат Decisions API (он в статусе alpha — формат может меняться).
3. Ничего не делается молча: Jev включается переменной окружения (например `JEV_ROUTING=true`) по одному месту; откат — убрать переменную. Без неё — текущее поведение.
4. Персональные данные не уходят: в C1/C5 передаём текст сообщения (уже обёрнутый и без контактов, D490); в C3 — поля профиля без контактов.

### Приёмка

Замер «до/после» на одном наборе: доля верного сервиса и инструмента (eval маршрутизации и 10 случаев D548), время хода, стоимость. Отдельная проверка на русских сообщениях. Пороги уверенности подбираются для Jev отдельно (вероятности у разных моделей несравнимы).

### C4 — проверка перед кодом (2026-10-27)

Проверено без платных вызовов:

- **Цена** (публичный API OpenRouter `/api/v1/models/typesafe/jev-1.14/endpoints`): вход $0.000000042 за токен ($0.042 за 1 млн), выход $0, провайдер TypeSafe, контекст 262 144 токена. Так же у `jev-1.13`. Пример из документации: 476 входных токенов — $0.00002.
- **Формат** (OpenRouter Decisions API, `POST /api/alpha/decisions`, статус alpha): `model`, `state` (строка или JSON), `questions` — объект «имя → вопрос». Noul: `instructions` + `criteria: { "true": …, "false": … }` → ответ `noul` 0–1. Choice: варианты — ключи `criteria` → `choice`, `confidence`, `probabilities`. Score: `criteria` — массив уровней → `score`, `confidence`, `probabilities`, `legend`. Ответ: `answers`, `usage.input_tokens`, `usage.cost`. Ошибки 402 (нет кредитов), 429/529 (повтор с паузой).
- **Ограничения** (TypeSafe, «jaggedness» Jev 1.13): плохо считает и не точен с числами («не калькулятор»); читает отрицания и условия буквально; точность падает от лишнего текста в `state`; склоняется к первому варианту; даты читает как текст. Тело запроса до 32 МиБ.
- **Русский:** в документации списка языков нет. Для 1.14 TypeSafe пишет только, что ждёт наибольшего улучшения в поддержке многих языков, без цифр. **Проверяется только живым вызовом.**

### C4 — как устроено (предложение)

- Только в живом оценщике (`scripts/eval-answers.mjs`, `answer-eval-live.test.ts`); пользователи этого не видят, продакшен не меняется.
- **Числа и цены оставляем коду** (`pricesInText`): Jev для них ненадёжен.
- Jev задаёт смысловые вопросы Noul по паре «результат инструмента → ответ модели»:
  - пустая выдача: «ответ честно говорит, что ничего не найдено» и «ответ называет конкретную вакансию, услугу или событие как найденную»;
  - непустая выдача: «каждый требуемый факт есть в ответе» (по одному вопросу на факт: Jev плохо считает).
- В `state` — только результат инструмента и ответ, без системного промпта и истории (лишний текст снижает точность).
- Порог «да» подбирается на наших случаях; рядом пишется старая оценка регулярными выражениями, чтобы видеть расхождения.
- Включение: переменная `JEV_EVAL=true`; без неё оценщик работает как сейчас.

### C4 — живая проба русского (ждёт «да» основателя)
