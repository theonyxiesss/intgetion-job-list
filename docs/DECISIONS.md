## D31 — npm package name

The workspace directory name is not a valid npm package name (spaces and capitals). The package name is `intgetion-job-list`. The product name stays `INTGETION JOB LIST` (D1).

## D32 — облачный Supabase для разработки

Локальный Docker на машине разработчика невозможен: виртуализация недоступна. Разработка идёт на облачном проекте Supabase `intgetion-dev`. Ключи лежат только в `.env.local` и в git не попадают. Проверка «миграции с нуля» и интеграционные тесты выполняются в GitHub Actions через `supabase start` (на раннере Docker есть). Локальный Docker не требуется.

## D33 — автономный режим

Заменяет пункт 1 раздела 0 («одна подфаза = одна сессия») и пункт 6 в части остановки на внешнем ключе.

1. Подфазы раздела 22 выполняются подряд, без ожидания команды между ними.
2. Переход к следующей подфазе — только если DoD (раздел 23) текущей выполнен полностью: lint, typecheck, test, build с кодом 0, P-тесты подфазы зелёные, коммит запушен, CI на GitHub зелёный (`gh run watch`). Красный CI чинится до перехода.
3. После каждой подфазы — запись в `MISSION_LOG.md` по шаблону раздела 0 и отдельный коммит `<код подфазы>: <кратко>`. Отчёт в чат — 5–10 строк на подфазу.
4. Секреты, которые агент может создать сам, он создаёт сам и пишет только в `.env.local`: пароль роли `app_rw` (случайный; `ALTER ROLE` через `DATABASE_MIGRATION_URL`; `DATABASE_URL` — Session pooler, пользователь `app_rw.<ref>`), `CRON_SECRET`. Значения секретов в чат и в git не попадают.
5. Если подфаза требует внешнего ключа или решения пользователя (`ANTHROPIC_API_KEY` в 7A, `RESEND_API_KEY` в 9A, founder approval в 8B, любой пункт раздела 25): сделать всё, что возможно без него (интерфейсы, тестовые двойники, тесты); пометить подфазу `BLOCKED` в `MISSION_LOG` с тем, что нужно от пользователя; перейти к следующей подфазе, у которой все зависимости (колонка «Зависит от») в статусе DONE.
6. Полная остановка и ожидание пользователя — только если не осталось ни одной доступной подфазы; нужно действие с риском потери данных в облачной БД (кроме миграций вперёд); тесты не удаётся сделать зелёными после 3 честных попыток.
7. Запреты раздела 24 действуют: не ослаблять тесты, не делать код V2/V3, не выдавать заглушки за реализацию.

## D34 — роль миграций на хостинге

Пароль встроенной роли `postgres` на Supabase нельзя сменить SQL-ролью `postgres` (это может только superuser). `DATABASE_MIGRATION_URL` — session pooler, пользователь `migrator.<ref>`. `DATABASE_URL` — session pooler, пользователь `app_rw.<ref>`. Пароли только в `.env.local`. Для не-loopback TLS в клиенте `rejectUnauthorized: false`, потому что локальная цепочка сертификатов не доверяет пулеру.

## D37 — детали auth-потока (1A)

1. Регистрация — `POST /api/auth/register` на сервере через `@supabase/ssr`. Версия условий, время согласия и локаль хранятся в `user_metadata` до подтверждения email; строку `users` создаёт `/auth/callback` (`ON CONFLICT (auth_uid) DO NOTHING`). Нет согласия в metadata → выход из сессии и `/login?error=missing_terms`.
2. Вход паролем и magic link — на клиенте через supabase-js (раздел 7: «Supabase Auth на клиенте»). Magic link со страницы входа не создаёт пользователя (`shouldCreateUser: false`) и для неизвестного адреса показывает тот же экран (anti-enumeration).
3. `/[locale]/auth/callback` принимает `code` (PKCE, ссылка открывается в том же браузере) и `token_hash` + `type` (на случай своих шаблонов писем).
4. Неподтверждённый email, отсутствие строки `users` и статус не `active` считаются отсутствием сессии: 401 `UNAUTHENTICATED`. Новый код ошибки не вводится.
5. Дополнительный эндпоинт `POST /api/auth/password` `{ password }` — новый пароль после ссылки восстановления. Сервер применяет те же правила пароля; без сессии — 401.
6. `GET /api/me` дополнительно отдаёт `marketingOptIn` (своё поле, его меняет `PATCH /api/me`). `hasCandidateProfile: false` и `companies: []` — честный ответ, пока нет таблиц 2B и 3A; эти подфазы заполняют поля.
7. Блок-лист паролей — список SecLists `10k-most-common` (MIT), только записи длиной ≥ 10 (короче отсекает правило длины). Максимум — 72 символа (предел bcrypt).
8. `TERMS_VERSION = "2026-10-03"` в `src/config/legal.ts`. Тексты условий — OPEN QUESTION 25.4, поэтому чекбокс пока без ссылки на `/legal/*`.
9. Сессия обновляется в `src/proxy.ts` до next-intl, чтобы обновлённые cookie дошли до Server Components. Route Handlers под `/api` обновляют cookie сами.
10. Supabase нужен proxy и шапке, поэтому e2e, axe и Lighthouse перенесены в CI-job `database` (`supabase start` + Mailpit). Job `check` оставляет lint, format, typecheck, unit, build, gitleaks.
11. Локальный `supabase/config.toml`: подтверждение email включено, минимум пароля 10, redirect `http://127.0.0.1:3000/**`, лимиты писем и входов подняты для CI. Облачный проект настраивается так же в дашборде (MISSION_LOG 1A).

## D38 — вход на сервере и guards (1B)

1. Вход паролем и отправка magic link перенесены с клиента на сервер: `POST /api/auth/login` `{ email, password }` и `POST /api/auth/magic-link` `{ email, locale }`. Иначе лимиты раздела 6 (login по IP+email, magic link по email) нечем применить. Заменяет D37.2 в части «на клиенте»; браузерный клиент Supabase больше не нужен и удалён. Ошибка входа — 401 `UNAUTHENTICATED` с `details.reason` (`invalid_credentials` | `email_not_confirmed`), чтобы форма показала нужный текст.
2. Guards лежат в `src/lib/auth-guards.ts`. `requireCandidate` и `requireMembership` получают функцию поиска профиля/членства параметром: таблиц `candidate_profiles` (2B) и `company_members` (3A) ещё нет. Эти подфазы передают свои функции из своих сервисов. Поведение по 5.1: нет сессии → 401; не админ (и гость) → 404; нет профиля кандидата → 404; не член компании → 404; член без нужной роли → 403.
3. Аудит в 1B пишет только входы админа (`auth.admin_sign_in`, 16.1) — паролем и по ссылке. Остальные события аудита появляются в подфазах, где появляются сами действия.

## D39 — ключи лимитов, CSP, заголовки (1B)

1. Ключи `rate_limit_counters` и `audit_logs.ip_hash` — HMAC-SHA256 от IP/email с секретом `PRIVACY_HASH_SECRET` (новая переменная окружения, только сервер). SHA-256 без ключа от IPv4 перебирается за минуты. В CI секрет одноразовый.
2. Лимиты 1B: login 5/15 мин (IP+email), magic link + сброс пароля + регистрация без пароля 3/час (общий счётчик на email), регистрация 10/час (IP). Лимит считается после валидации входа. Глобальный лимит 300/мин на IP — в 11A (ревизия лимитов), чтобы не добавлять запись в БД на каждый запрос до замера нагрузки.
3. CSRF-проверка `Origin` — в `src/proxy.ts` для всех мутирующих `/api/*`; запрос без `Origin` тоже отклоняется (403 `FORBIDDEN`). Cron-эндпоинты вызываются `GET` и защищены `Authorization: Bearer CRON_SECRET`; без секрета — 404.
4. CSP для страниц — в proxy, nonce на запрос: раздел 16.1 плюс `style-src 'self' 'nonce-…'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`; `'unsafe-eval'` только в dev. Для `/api/*` — `default-src 'none'; frame-ancestors 'none'`. HSTS, `nosniff`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy` — для всех ответов через `next.config.ts`; `X-Powered-By` выключен.
5. `audit_logs` для `app_rw` только на добавление и чтение (UPDATE отозван); DELETE остаётся для retention-cron (10C).
6. `/api/cron/rate-limit-gc` удаляет окна старше 48 часов. Расписание Vercel Cron настраивается при деплое (11B).
7. Исправление 1A: matcher в `src/proxy.ts` содержал `\.` в обычной строке (то есть «любой символ»), и proxy работал только на `/`. Исправлено на `\\.`; `src/proxy.test.ts` проверяет matcher.

## D42 — нормализация навыков (2A)

Раздел 11.1 задаёт порядок поиска, но не механику строки. LLM-маппинг в 2A не делается.

1. `toAliasNormalized` (так хранится `skills_aliases.alias_normalized`): lower, trim; `c++`→`cpp`, `c#`→`csharp`, `f#`→`fsharp`, `.net`→`dotnet`; суффикс `.js` снимается; прочая пунктуация становится пробелом; выбрасываются токены версий (`18`, `v18`, `3.11`) и версия, приклеенная к основе из не меньше чем 3 букв (`html5`, `react18`, `python3`); токены склеиваются без разделителя.
2. `normalizeSkillText` — ключ поиска: форма из п.1, затем хвостовое `js`, если основа ещё не короче 2 символов (`reactjs`→`react`, `nodejs`→`node`). Голое `js` остаётся `js`.
3. Поиск по активному навыку: точный алиас, затем точный `slug`, затем `public.skill_similarity` ≥ 0.85 и ровно один навык. Иначе `skill_suggestions`. Пустой ключ не пишется. Повтор того же `normalized` увеличивает `occurrences` и не меняет `raw_text`, `source` и `status`.
4. `public.skill_similarity(text, text)` — SQL-обёртка над `similarity` из `pg_trgm`, чтобы роль `app_rw` не зависела от `search_path`. Расширение ставится как `CREATE EXTENSION IF NOT EXISTS pg_trgm WITH SCHEMA extensions`.
5. `normalizeSkill(raw, source = "user")`. `source` — `user | bot | import`. В `raw_text` попадает trim не длиннее 500 символов.
6. Повторный seed обновляет `name_en`, `name_ru`, `category` и цель алиаса. `is_active` не перезаписывается, лишние строки не удаляются. В миграции seed выполняется до RLS, чтобы роль миграции вставила строки без политики.
7. `id` — uuid, как у `users`. `name_en` и `name_ru` — NOT NULL. Алиас удаляется вместе с навыком (`ON DELETE CASCADE`). `mapped_skill_id` при удалении навыка становится NULL.

## D40 — расширения на хостинге

Роль `migrator` на облачном проекте не может создавать схемы и расширения и выдавать права на схему `extensions` (её владелец — `postgres`). Расширения, которые нужны миграциям (`pg_trgm` для 2A), и `GRANT USAGE ON SCHEMA extensions TO app_rw` один раз выполняет роль `postgres` (дашборд или Supabase MCP). Миграции делают эти шаги условно — только если их ещё нет, поэтому одна и та же миграция проходит и в CI от суперпользователя, и на облаке от `migrator`. Так исправлена `0003_skills.sql` до её первого применения на облаке. Новое расширение в будущих подфазах — тем же способом: условный шаг в миграции + запись в MISSION_LOG о ручной установке на облаке.

## D41 — замер LCP и отметка сессии

1. Lighthouse в CI считает LCP в режиме simulate: если страница грузится быстрее первого кадра, весь JS попадает в расчётный путь до LCP, и на общих раннерах GitHub значение прыгает между прогонами (1.9–2.9 с при наблюдаемом LCP около 0.1 с). Бюджет 2500 мс (3.4) остаётся, но применяется к медиане трёх прогонов; в лог пишутся все три значения LCP и FCP.
2. Proxy уже спрашивает Supabase о сессии; ответ передаётся Server Components в заголовке запроса `x-intgetion-session`, который proxy всегда перезаписывает, чтобы клиент не мог его подделать. Шапка больше не делает второй `getClaims()`. Заголовок влияет только на отображение кнопок «Войти» и «Выйти»; права проверяются через `getUser()` в API и guards.
3. JS главной — около 153 КБ gzip без `noModule`-полифилов при бюджете 150 КБ (3.4); почти всё — React, рантайм Next.js и next-intl. Пересмотр — в 11A.

## D50 — обнаружение дублей компаний (3A)

## D65 — правила tz: валидация зон и DST (4A-lib)

1. `isValidTimeZone` / `assertTimeZone` (`src/lib/tz.ts`) пропускают только то, что принимает `Intl.DateTimeFormat`, и дополнительно отклоняют записи с числовым смещением: `+03:00`, `+0300`, `UTC+3`, `GMT-5`, `Etc/GMT±h` — фиксированные смещения запрещены D6. Голые `UTC`, `GMT`, `Etc/UTC` остаются допустимыми ключами IANA. Хранить смещения вместо зоны запрещено разделом 24 ТЗ.
2. Несуществующее локальное время (переход «весной») интерпретируется смещением, действовавшим до перехода: часы перескакивают разрыв вместе с зоной (02:30 в Europe/Berlin 2026-03-29 → 01:30Z = 03:30 CEST; то же делает Java и Temporal «earlier»).
3. Повторяющееся локальное время («осенью») — первое вхождение, то же смещение до перехода (02:30 Berlin 2026-10-25 → 00:30Z).
4. Механика `localToUtc`: неподвижная точка t = wall − offset(t), стартовое смещение берётся с предыдущих суток и при несовпадении уточняется; если неподвижной точки нет — это разрыв, действует п.2. Смещение считается через `Intl.DateTimeFormat.formatToParts` на конкретный момент; кэш форматтеров по зоне.

## D66 — соглашения money (4A-lib)

1. DTO денег — строго раздел 6: `{ amountMinor, currency, period, basis }`. `amountMinor` — строка только из цифр (bigint сериализуется строкой), `currency` — 3 заглавные буквы ISO 4217. `parseMoneyDto` и конструкторы бросают `InvalidMoneyError` на мусоре: тихий ноль недопустим.
2. Ось конвертации — USD: `rate_to_usd` — единиц валюты за 1 USD, fixed point 8 знаков; numeric(18,8) приходит строкой (number для курса запрещён, D19). Курс USD — identity (10^8), строка за USD от функции не требуется. Порядок проверок нейтральности: basis → period → fx_missing → fx_stale; если у одной валюты курса нет, а у другой протух — сообщается `fx_missing`.
3. Свежесть курса: `now − as_of ≤ 7 суток` (ровно 7 суток — свежий, +1 мс — протух). История курсов (`fx_rates` ключуется по currency+as_of) разрешена: берётся самая свежая строка по валюте.
4. Все деления денег — `divRoundHalfEven` (банковское округление, x.5 к чётному). При period `hour` поля результата сравнения называются `jobMonthlyMinor`/`candMonthlyMinor` по разделу 6, но несут часовые минорные единицы: hour можно сравнить только с hour (D5).

## D67 — скор зарплаты, граничные случаи (4A-lib)

1. `salaryScore(J, C)` (10.4.4): J ≥ C → 1; иначе s = (10·J − 7·C) / (3·C) — то же, что max(0, (J/C − 0.7)/0.3), но как точное отношение BigInt; в number переводится один раз в конце (17 значащих цифр). При 10·J ≤ 7·C s = 0. Промежуточных float нет (D19).
2. Явные нейтральные случаи — `{ kind: "neutral", reason }`: нет J (`job_salary_missing`), нет C (`candidate_salary_missing`), C = 0 (`candidate_salary_zero` — нулевые ожидания считаются отсутствием данных, а не «устраивает всё»).
3. Выбор J = salary_max ?? salary_min вынесен в `jobSalaryReference`.

## D68 — механика workHoursOverlap (4A-lib)

1. Итерация — по календарным дням UTC от даты `from` включительно, длина `days ?? 14`. Календарный день UTC используется и как локальная дата кандидата для проверки `workDays` (ISO weekday этого дня), и как день привязки окон — так в 10.6: дни по UTC, workDays в зоне кандидата.
2. Окно вакансии по умолчанию 09:00–18:00. `end < start` — окно через полночь (end на следующем календарном дне); `end == start` — окно нулевой длины, а не 24 часа.
3. Если окно кандидата переходит полночь, оно может пересечься с окном вакансии следующего дня (ночная смена против 04:00–12:00): пересечение считается с окнами вакансии дня d и d+1. Дневные окна вакансии всегда не пересекаются между собой (каждое ≤ 24 ч и привязано к своему дню), поэтому сумма не задваивает.
4. Результат: среднее пересечение в минутах на рабочий день (если рабочих дней в диапазоне нет — 0) и разбивка по дням для отладки: дата UTC, ISO weekday, рабочий ли день, минуты.

## D69 — ошибки библиотек 4A-lib

`money.ts` и `tz.ts` сообщают о плохом вводе исключениями (`InvalidMoneyError`, `InvalidTimeZoneError`, `InvalidTimeError`; `RangeError` для длины диапазона и дней недели), а не тихими значениями. «Нейтральность» по D4/D5 — ответ только на семантическую несравнимость сумм (база, период, курс), не на мусор во входных данных: мусор должен падать, а не обнулять компонент скора.

## D55 — полнота профиля (2B)

Раздел 11.3 не говорит, что считать «подтверждёнными» часами и форматом: в таблице у этих колонок есть значения по умолчанию.

1. Баллы считает чистая `profileCompleteness`. Пустые массивы и пустые строки баллов не дают. Часы подтверждены, когда заданы начало, конец и хотя бы один день. Формат и тип занятости подтверждены, когда оба массива непусты. Сохранение формы и есть подтверждение: до сохранения строки профиля нет, и полнота 0.
2. Часовой пояс даёт 10 баллов только если это IANA-имя, которое принимает `Intl`. `UTC+3`, `GMT+1`, `+03:00` и `Etc/GMT*` не принимаются. `UTC` принимается.
3. Зарплата даёт 10 баллов только при `salary_min` вместе с валютой, периодом и базой. `missing[]` — ключи строк `profile.missing.*`, в порядке таблицы 11.3.
4. Сумма весов — 100.

## D56 — кто видит профиль до откликов (2B)

До подфазы 5A заявок нет, поэтому правило D24 сужается до владельца.

1. `PATCH /api/candidates/me` создаёт профиль, если его ещё нет. Часовой пояс обязателен. `GET /api/candidates/me` без строки — 404.
2. `GET /api/candidates/:id` отдаёт профиль только когда `:id` совпадает с пользователем сессии. Иначе 404, в том числе при чужом id и при не-uuid. Тело этой ошибки не содержит профиль.
3. Ключа `contacts` нет ни в одном ответе профиля, включая ответ владельцу. Контакты — только `GET/PUT /api/candidates/me/contacts`.
4. Страницы `/profile` и `/profile/edit` открыты любому подтверждённому пользователю, иначе первый профиль негде создать. Гость уходит на `/login`.

## D57 — длины, которые раздел 4.1 не задал (2B)

1. Город — до 80 символов. Название компании и должность в опыте — до 160. Описание опыта — до 2000, как summary.
2. Телефон — E.164 (`+` и 7–15 цифр). Telegram — 5–32 символа, латиница, цифры и `_`. LinkedIn и сайт — `http` или `https`, до 300 символов.

## D58 — навыки профиля (2B)

1. Сырые названия проходят только через `normalizeSkill` сервиса таксономии. Совпадение пишется в `candidate_skills`. Несовпадение остаётся в `skill_suggestions` и возвращается как `unrecognizedSkills`; в профиль не пишется.
2. Не больше 30 навыков. Повтор одного `skill_id` в одном сохранении оставляет одну строку.

## D59 — полнота и контакты в одной транзакции (2B)

`candidate_contacts` читает только `contactsService`, поэтому сервис кандидатов не импортирует `contacts/repo`, а сервис контактов не импортирует сервис кандидатов.

1. `PATCH /api/candidates/me` считает полноту по уже сохранённому email и пишет профиль вместе с `completeness` в одной транзакции.
2. `PUT /api/candidates/me/contacts` в одной транзакции пишет контакт и затем `completeness`. Счётчик собирает маршрут из `scoreStoredProfile` и `storeCompleteness`, чтобы модули не импортировали друг друга по кругу.
3. `GET /api/me` по-прежнему отдаёт `hasCandidateProfile: false`. После D46 это строка в `meContext` (`src/app/api/me/route.ts`): модуль auth кандидатов не импортирует. Её подставляет Claude Code вызовом `hasCandidateProfile(user.id)` из `@/modules/candidates/service`.

## D80 — админка без вакансий (10A, первая часть)

1. 10A разбита на две части. Первая (сейчас, не зависит от 3B): `/admin`, пользователи, журнал аудита, разбор `skill_suggestions`. Вторая (после 3B): модерация вакансий (`moderation_queue`), жалобы, блокировка компаний и снятие вакансий.
2. Права: каждая страница `/[locale]/admin/*` сама вызывает проверку админа (layout не перезапускается при каждой навигации); каждый `/api/admin/*` начинается с `requireAdmin()` до разбора ввода — гость и не-админ получают 404 (P7).
3. Поиск пользователей — по точному id и статусу: email входа хранится в Supabase Auth, а не в `users`; поиск по email потребует `SUPABASE_SERVICE_ROLE_KEY` (Auth admin API) и добавится, когда ключ появится.
4. Блокировка: только `active → suspended` и обратно; себя и другого админа заблокировать нельзя — 422 `ADMIN_PROTECTED`; неверный исходный статус — 409 `INVALID_TRANSITION`. Заблокированный теряет доступ со следующего запроса (`getCurrentUser` проверяет статус). Отзыв сессий в Supabase — тоже через service role, позже.
5. Разбор навыков: `map` одобряет предложение и добавляет его нормализованный текст алиасом навыка в одной транзакции, после этого `normalizeSkill` находит навык сам; алиас, уже указывающий на другой навык, — 409 `ALIAS_TAKEN`; повторное решение — 409 `ALREADY_DECIDED`. Новые коды ошибок — `ADMIN_PROTECTED`, `ALIAS_TAKEN`, `ALREADY_DECIDED`.
6. Каждое действие админа пишет `audit_logs` с админом как actor и хешем IP (P16); в выдаче журнала `ip_hash` нет. Назначение админа — только скриптом `pnpm admin:grant <email>` (D21), запись `admin.granted` без actor.

## D60 — деньги и временные зоны вакансий (3B)

После появления `src/lib/money.ts` в `origin/master` 3B использует `toMoneyDto` для зарплат; временный адаптер удалён.
