## D31 — npm package name

The workspace directory name is not a valid npm package name (spaces and capitals). The package name is `intgetion-job-list`. The product name stays `INTGETION JOB LIST` (D1).

## D32 — облачный Supabase для разработки

Локальный Docker на машине разработчика невозможен: виртуализация недоступна. Разработка идёт на облачном проекте Supabase `intgetion-dev`. Ключи лежат только в `.env.local` и в git не попадают. Проверка «миграции с нуля» и интеграционные тесты выполняются в GitHub Actions через `supabase start` (на раннере Docker есть). Локальный Docker не требуется.

## D33 — автономный режим

Заменяет пункт 1 раздела 0 («одна подфаза = одна сессия») и пункт 6 в части остановки на внешнем ключе.

1. Подфазы раздела 22 выполняются подряд, без ожидания команды между ними.
2. Переход к следующей подфазе — только если DoD (раздел 23) текущей выполнен полностью: lint, typecheck, test, build с кодом 0, P-тесты подфазы зелёные, коммит запушен, CI на GitHub зелёный (`gh run watch`). Красный CI чинится до перехода.
3. После каждой подфазы — запись в `MISSION_LOG.md` по шаблону раздела 0 и отдельный коммит `<код подфазы>: <кратко>`. Отчёт в чат — 5–10 строк на подфазу.
4. Секреты, которые агент может создать сам, он создаёт сам и пишет только в `.env.local`: пароль роли `app_rw` (случайный; `ALTER ROLE` через `DATABASE_MIGRATION_URL`; `DATABASE_URL` — Session pooler, пользователь `app_rw.<ref>`), `CRON_SECRET`. Значения секретов в чат и в git не попадают.
5. Если подфаза требует внешнего ключа или решения пользователя (`ANTHROPIC_API_KEY` в 7A, `RESEND_API_KEY` в 9A, founder approval в 8B, любой пункт раздела 25): сделать всё, что возможно без него (интерфейсы, тестовые двойники, тесты); пометить подфазу `BLOCKED` в `MISSION_LOG` с тем, что нужно от пользователя; перейти к следующей подфазе, у которой все зависимости (колонка «Зависит от») в статусе DONE.
6. Полная остановка и ожидание пользователя — только если не осталось ни одной доступной подфазы; нужно действие с риском потери данных в облачной БД (кроме миграций вперёд); тесты не удаётся сделать зелёными после 3 честных попыток.
7. Запреты раздела 24 действуют: не ослаблять тесты, не делать код V2/V3, не выдавать заглушки за реализацию.

## D34 — роль миграций на хостинге

## D37 — детали auth-потока (1A)

1. Регистрация — `POST /api/auth/register` на сервере через `@supabase/ssr`. Версия условий, время согласия и локаль хранятся в `user_metadata` до подтверждения email; строку `users` создаёт `/auth/callback` (`ON CONFLICT (auth_uid) DO NOTHING`). Нет согласия в metadata → выход из сессии и `/login?error=missing_terms`.
2. Вход паролем и magic link — на клиенте через supabase-js (раздел 7: «Supabase Auth на клиенте»). Magic link со страницы входа не создаёт пользователя (`shouldCreateUser: false`) и для неизвестного адреса показывает тот же экран (anti-enumeration).
3. `/[locale]/auth/callback` принимает `code` (PKCE, ссылка открывается в том же браузере) и `token_hash` + `type` (на случай своих шаблонов писем).
4. Неподтверждённый email, отсутствие строки `users` и статус не `active` считаются отсутствием сессии: 401 `UNAUTHENTICATED`. Новый код ошибки не вводится.
5. Дополнительный эндпоинт `POST /api/auth/password` `{ password }` — новый пароль после ссылки восстановления. Сервер применяет те же правила пароля; без сессии — 401.
6. `GET /api/me` дополнительно отдаёт `marketingOptIn` (своё поле, его меняет `PATCH /api/me`). `hasCandidateProfile: false` и `companies: []` — честный ответ, пока нет таблиц 2B и 3A; эти подфазы заполняют поля.
7. Блок-лист паролей — список SecLists `10k-most-common` (MIT), только записи длиной ≥ 10 (короче отсекает правило длины). Максимум — 72 символа (предел bcrypt).
8. `TERMS_VERSION = "2026-10-03"` в `src/config/legal.ts`. Тексты условий — OPEN QUESTION 25.4, поэтому чекбокс пока без ссылки на `/legal/*`.
9. Сессия обновляется в `src/proxy.ts` до next-intl, чтобы обновлённые cookie дошли до Server Components. Route Handlers под `/api` обновляют cookie сами.
10. Supabase нужен proxy и шапке, поэтому e2e, axe и Lighthouse перенесены в CI-job `database` (`supabase start` + Mailpit). Job `check` оставляет lint, format, typecheck, unit, build, gitleaks.
11. Локальный `supabase/config.toml`: подтверждение email включено, минимум пароля 10, redirect `http://127.0.0.1:3000/**`, лимиты писем и входов подняты для CI. Облачный проект настраивается так же в дашборде (MISSION_LOG 1A).

## D38 — вход на сервере и guards (1B)

1. Вход паролем и отправка magic link перенесены с клиента на сервер: `POST /api/auth/login` `{ email, password }` и `POST /api/auth/magic-link` `{ email, locale }`. Иначе лимиты раздела 6 (login по IP+email, magic link по email) нечем применить. Заменяет D37.2 в части «на клиенте»; браузерный клиент Supabase больше не нужен и удалён. Ошибка входа — 401 `UNAUTHENTICATED` с `details.reason` (`invalid_credentials` | `email_not_confirmed`), чтобы форма показала нужный текст.
2. Guards лежат в `src/lib/auth-guards.ts`. `requireCandidate` и `requireMembership` получают функцию поиска профиля/членства параметром: таблиц `candidate_profiles` (2B) и `company_members` (3A) ещё нет. Эти подфазы передают свои функции из своих сервисов. Поведение по 5.1: нет сессии → 401; не админ (и гость) → 404; нет профиля кандидата → 404; не член компании → 404; член без нужной роли → 403.
3. Аудит в 1B пишет только входы админа (`auth.admin_sign_in`, 16.1) — паролем и по ссылке. Остальные события аудита появляются в подфазах, где появляются сами действия.

## D39 — ключи лимитов, CSP, заголовки (1B)

1. Ключи `rate_limit_counters` и `audit_logs.ip_hash` — HMAC-SHA256 от IP/email с секретом `PRIVACY_HASH_SECRET` (новая переменная окружения, только сервер). SHA-256 без ключа от IPv4 перебирается за минуты. В CI секрет одноразовый.
2. Лимиты 1B: login 5/15 мин (IP+email), magic link + сброс пароля + регистрация без пароля 3/час (общий счётчик на email), регистрация 10/час (IP). Лимит считается после валидации входа. Глобальный лимит 300/мин на IP — в 11A (ревизия лимитов), чтобы не добавлять запись в БД на каждый запрос до замера нагрузки.
3. CSRF-проверка `Origin` — в `src/proxy.ts` для всех мутирующих `/api/*`; запрос без `Origin` тоже отклоняется (403 `FORBIDDEN`). Cron-эндпоинты вызываются `GET` и защищены `Authorization: Bearer CRON_SECRET`; без секрета — 404.
4. CSP для страниц — в proxy, nonce на запрос: раздел 16.1 плюс `style-src 'self' 'nonce-…'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`; `'unsafe-eval'` только в dev. Для `/api/*` — `default-src 'none'; frame-ancestors 'none'`. HSTS, `nosniff`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy` — для всех ответов через `next.config.ts`; `X-Powered-By` выключен.
5. `audit_logs` для `app_rw` только на добавление и чтение (UPDATE отозван); DELETE остаётся для retention-cron (10C).
6. `/api/cron/rate-limit-gc` удаляет окна старше 48 часов. Расписание Vercel Cron настраивается при деплое (11B).
7. Исправление 1A: matcher в `src/proxy.ts` содержал `\.` в обычной строке (то есть «любой символ»), и proxy работал только на `/`. Исправлено на `\\.`; `src/proxy.test.ts` проверяет matcher.

## D42 — нормализация навыков (2A)

Раздел 11.1 задаёт порядок поиска, но не механику строки. LLM-маппинг в 2A не делается.

1. `toAliasNormalized` (так хранится `skills_aliases.alias_normalized`): lower, trim; `c++`→`cpp`, `c#`→`csharp`, `f#`→`fsharp`, `.net`→`dotnet`; суффикс `.js` снимается; прочая пунктуация становится пробелом; выбрасываются токены версий (`18`, `v18`, `3.11`) и версия, приклеенная к основе из не меньше чем 3 букв (`html5`, `react18`, `python3`); токены склеиваются без разделителя.
2. `normalizeSkillText` — ключ поиска: форма из п.1, затем хвостовое `js`, если основа ещё не короче 2 символов (`reactjs`→`react`, `nodejs`→`node`). Голое `js` остаётся `js`.
3. Поиск по активному навыку: точный алиас, затем точный `slug`, затем `public.skill_similarity` ≥ 0.85 и ровно один навык. Иначе `skill_suggestions`. Пустой ключ не пишется. Повтор того же `normalized` увеличивает `occurrences` и не меняет `raw_text`, `source` и `status`.
4. `public.skill_similarity(text, text)` — SQL-обёртка над `similarity` из `pg_trgm`, чтобы роль `app_rw` не зависела от `search_path`. Расширение ставится как `CREATE EXTENSION IF NOT EXISTS pg_trgm WITH SCHEMA extensions`.
5. `normalizeSkill(raw, source = "user")`. `source` — `user | bot | import`. В `raw_text` попадает trim не длиннее 500 символов.
6. Повторный seed обновляет `name_en`, `name_ru`, `category` и цель алиаса. `is_active` не перезаписывается, лишние строки не удаляются. В миграции seed выполняется до RLS, чтобы роль миграции вставила строки без политики.
7. `id` — uuid, как у `users`. `name_en` и `name_ru` — NOT NULL. Алиас удаляется вместе с навыком (`ON DELETE CASCADE`). `mapped_skill_id` при удалении навыка становится NULL.

## D40 — расширения на хостинге

Роль `migrator` на облачном проекте не может создавать схемы и расширения и выдавать права на схему `extensions` (её владелец — `postgres`). Расширения, которые нужны миграциям (`pg_trgm` для 2A), и `GRANT USAGE ON SCHEMA extensions TO app_rw` один раз выполняет роль `postgres` (дашборд или Supabase MCP). Миграции делают эти шаги условно — только если их ещё нет, поэтому одна и та же миграция проходит и в CI от суперпользователя, и на облаке от `migrator`. Так исправлена `0003_skills.sql` до её первого применения на облаке. Новое расширение в будущих подфазах — тем же способом: условный шаг в миграции + запись в MISSION_LOG о ручной установке на облаке.

## D41 — замер LCP и отметка сессии

1. Lighthouse в CI считает LCP в режиме simulate: если страница грузится быстрее первого кадра, весь JS попадает в расчётный путь до LCP, и на общих раннерах GitHub значение прыгает между прогонами (1.9–2.9 с при наблюдаемом LCP около 0.1 с). Бюджет 2500 мс (3.4) остаётся, но применяется к медиане трёх прогонов; в лог пишутся все три значения LCP и FCP.
2. Proxy уже спрашивает Supabase о сессии; ответ передаётся Server Components в заголовке запроса `x-intgetion-session`, который proxy всегда перезаписывает, чтобы клиент не мог его подделать. Шапка больше не делает второй `getClaims()`. Заголовок влияет только на отображение кнопок «Войти» и «Выйти»; права проверяются через `getUser()` в API и guards.
3. JS главной — около 153 КБ gzip без `noModule`-полифилов при бюджете 150 КБ (3.4); почти всё — React, рантайм Next.js и next-intl. Пересмотр — в 11A.

## D65 — правила tz: валидация зон и DST (4A-lib)

1. `isValidTimeZone` / `assertTimeZone` (`src/lib/tz.ts`) пропускают только то, что принимает `Intl.DateTimeFormat`, и дополнительно отклоняют записи с числовым смещением: `+03:00`, `+0300`, `UTC+3`, `GMT-5`, `Etc/GMT±h` — фиксированные смещения запрещены D6. Голые `UTC`, `GMT`, `Etc/UTC` остаются допустимыми ключами IANA. Хранить смещения вместо зоны запрещено разделом 24 ТЗ.
2. Несуществующее локальное время (переход «весной») интерпретируется смещением, действовавшим до перехода: часы перескакивают разрыв вместе с зоной (02:30 в Europe/Berlin 2026-03-29 → 01:30Z = 03:30 CEST; то же делает Java и Temporal «earlier»).
3. Повторяющееся локальное время («осенью») — первое вхождение, то же смещение до перехода (02:30 Berlin 2026-10-25 → 00:30Z).
4. Механика `localToUtc`: неподвижная точка t = wall − offset(t), стартовое смещение берётся с предыдущих суток и при несовпадении уточняется; если неподвижной точки нет — это разрыв, действует п.2. Смещение считается через `Intl.DateTimeFormat.formatToParts` на конкретный момент; кэш форматтеров по зоне.

## D66 — соглашения money (4A-lib)

1. DTO денег — строго раздел 6: `{ amountMinor, currency, period, basis }`. `amountMinor` — строка только из цифр (bigint сериализуется строкой), `currency` — 3 заглавные буквы ISO 4217. `parseMoneyDto` и конструкторы бросают `InvalidMoneyError` на мусоре: тихий ноль недопустим.
2. Ось конвертации — USD: `rate_to_usd` — единиц валюты за 1 USD, fixed point 8 знаков; numeric(18,8) приходит строкой (number для курса запрещён, D19). Курс USD — identity (10^8), строка за USD от функции не требуется. Порядок проверок нейтральности: basis → period → fx_missing → fx_stale; если у одной валюты курса нет, а у другой протух — сообщается `fx_missing`.
3. Свежесть курса: `now − as_of ≤ 7 суток` (ровно 7 суток — свежий, +1 мс — протух). История курсов (`fx_rates` ключуется по currency+as_of) разрешена: берётся самая свежая строка по валюте.
4. Все деления денег — `divRoundHalfEven` (банковское округление, x.5 к чётному). При period `hour` поля результата сравнения называются `jobMonthlyMinor`/`candMonthlyMinor` по разделу 6, но несут часовые минорные единицы: hour можно сравнить только с hour (D5).

## D67 — скор зарплаты, граничные случаи (4A-lib)

1. `salaryScore(J, C)` (10.4.4): J ≥ C → 1; иначе s = (10·J − 7·C) / (3·C) — то же, что max(0, (J/C − 0.7)/0.3), но как точное отношение BigInt; в number переводится один раз в конце (17 значащих цифр). При 10·J ≤ 7·C s = 0. Промежуточных float нет (D19).
2. Явные нейтральные случаи — `{ kind: "neutral", reason }`: нет J (`job_salary_missing`), нет C (`candidate_salary_missing`), C = 0 (`candidate_salary_zero` — нулевые ожидания считаются отсутствием данных, а не «устраивает всё»).
3. Выбор J = salary_max ?? salary_min вынесен в `jobSalaryReference`.

## D68 — механика workHoursOverlap (4A-lib)

1. Итерация — по календарным дням UTC от даты `from` включительно, длина `days ?? 14`. Календарный день UTC используется и как локальная дата кандидата для проверки `workDays` (ISO weekday этого дня), и как день привязки окон — так в 10.6: дни по UTC, workDays в зоне кандидата.
2. Окно вакансии по умолчанию 09:00–18:00. `end < start` — окно через полночь (end на следующем календарном дне); `end == start` — окно нулевой длины, а не 24 часа.
3. Если окно кандидата переходит полночь, оно может пересечься с окном вакансии следующего дня (ночная смена против 04:00–12:00): пересечение считается с окнами вакансии дня d и d+1. Дневные окна вакансии всегда не пересекаются между собой (каждое ≤ 24 ч и привязано к своему дню), поэтому сумма не задваивает.
4. Результат: среднее пересечение в минутах на рабочий день (если рабочих дней в диапазоне нет — 0) и разбивка по дням для отладки: дата UTC, ISO weekday, рабочий ли день, минуты.

## D69 — ошибки библиотек 4A-lib

`money.ts` и `tz.ts` сообщают о плохом вводе исключениями (`InvalidMoneyError`, `InvalidTimeZoneError`, `InvalidTimeError`; `RangeError` для длины диапазона и дней недели), а не тихими значениями. «Нейтральность» по D4/D5 — ответ только на семантическую несравнимость сумм (база, период, курс), не на мусор во входных данных: мусор должен падать, а не обнулять компонент скора.

## D55 — полнота профиля (2B)

Раздел 11.3 не говорит, что считать «подтверждёнными» часами и форматом: в таблице у этих колонок есть значения по умолчанию.

## D91 — hard-фильтры (6A-score)

1. `hardFilter` проверяет все 6 пунктов 10.2 и возвращает `{ pass: true } | { pass: false, reason }` с машиной причин: `work_format`, `country_restricted`, `employment_type`, `location`, `tz_overlap`, `hidden_by_user`, `already_applied`, `not_published`. Валюта и gross/net — не hard (D4, D5).
2. П.5 считается через `workHoursOverlap` из `src/lib/tz.ts` за 14 дней от `context.now`, среднее в часах сравнивается с `job.min_overlap_hours` (только вакансия, по 10.2; R = max(обе стороны) — это компонент 10.3).
3. П.6 (скрытия, активный отклик, статус) берётся из `FeedbackForScoring` (`hiddenJobIds`, `hiddenCompanyIds`, `activeApplicationJobIds`) и `job.status`; `hidden_company` исключает всю компанию — единственное место, где feedback-событие работает как hard-фильтр (10.5).

## D92 — компоненты, граничные правила (6A-score)

1. skills: `m_j` = 1 при уровне ≥ min_level, 0.5 при уровне ниже, 0 при отсутствии; нейтрально, если у вакансии нет навыков. Отсутствующий must-have для штрафа — навыка вообще нет у кандидата; «есть, но ниже уровня» отсутствующим не считается (он уже оштрафован через m_j = 0.5).
2. role: сходство считается только по `desired_titles`; категория даёт пол 0.7 (`max(·, 0.7)`). Нейтрально при пустых titles и categories.
3. salary: через `compareSalaries`/`salaryScore` из `src/lib/money.ts`; сторона с суммой, но без currency/period/basis, считается отсутствующей; C = 0 → нейтрально (`candidate_salary_zero`). Все нейтральные случаи D4/D5 не исключают вакансию.
4. experience: переопыт `cand > max + 3` даёт 0.7 поверх любого базового значения, включая 1.
5. languages: язык отсутствует у кандидата → 0; ровно на 1 ступень CEFR ниже → 0.5.

## D93 — сборка, штрафы, feedback (6A-score)

1. Веса 0.35/0.15/0.20/0.10/0.10/0.10; нейтральные компоненты исключаются из суммы, вес перераспределяется пропорционально; Σ активных весов < 0.4 → `lowData = true` (граница: ровно 0.4 — ещё не lowData). Пустая сумма (все нейтральны) даёт base = 0.
2. Штрафы: ×0.8 за каждый отсутствующий must-have (weight = 3); ×0.95, если у вакансии нет полной зарплаты (нет сумм или нет currency/period/basis) — это тот же критерий «без зарплаты», что и нейтральность компонента.
3. Feedback: ×0.9ⁿ по категории hidden/dismissed с полом 0.6; +0.03 за навык вакансии, встречавшийся в ≥ 2 сохранённых/откликнутых, потолок ×1.15; множители пишутся в `breakdown.feedback`. `hidden_company` в множитель не входит — он hard (D91.3). Флаг `suggestProfileUpdate` (salary|format|timezone) ставится при ≥ 3 скрытиях с этой причиной; функция ничего не меняет сама.
4. Итог: `score = clamp(base × штрафы × feedback, 0, 1)`; порог показа 0.55 (`shown`); `ALGO_VERSION = 1`. `scoreCandidate` = hard-фильтр + buildMatch (удобство для конвейера 10.1).

## D94 — explain и публичная форма (6A-score)

1. Explain строится детерминированно из breakdown, без LLM (D30): verdict по компоненту — matched при score = 1, failed при score = 0, partial между ними, neutral для нейтральных; порядок matched → partial → neutral → failed (ничья — по порядку критериев 10.3); карточка берёт `topExplain(…, 4)`.
2. `detail.key` — полный путь next-intl вида `explain.salary.partial` под своим ключом верхнего уровня `explain` в `en.json`/`ru.json`; params — только строки/числа; зарплата вакансии форматируется из минорных единиц целочисленным BigInt («4250 EUR/mo gross») — только для показа, арифметики денег нет.
3. `toPublicMatch(result)` отдаёт наружу только `{ score, explain }`: score округлён до 2 знаков (5.3), breakdown/веса/сырые компоненты не покидают бэкенд.
4. Semantic (10.9, D11): интерфейс `SemanticProvider` и `NoopSemanticProvider` (→ null) зарезервированы, компонент не используется.

## D75 — статус-машина отклика как данные (5A-rules)

Таблица раздела 4.2 хранится один раз: `TRANSITIONS` (`from`, `to`, `actor`, `via`). `checkTransition` ничего не пишет. В 5A `transitionApplication()` вызывает только её (D2). Успех — возврат без значения. Ошибка — `HttpError`.

1. Пары нет в таблице, в том числе любой переход из `hired`, `rejected` или `withdrawn` и переход в тот же статус → 409 `INVALID_TRANSITION`.
2. `to = shortlisted` при акторе `employer` и `from` `applied` или `viewed`, но `via` не `express_interest` → 422 `EXPRESS_INTEREST_REQUIRED`. В каталоге раздела 6 такого кода нет; `src/lib/http` не меняется. `via = patch` — это общий PATCH статуса.
3. `viewed` разрешён только `via = auto_view`, только из `applied`, только работодателю. Другой `via` → 409 `INVALID_TRANSITION`.
4. `withdrawn` разрешён только `via = withdraw` кандидату. Общий PATCH в `withdrawn` этим переходом не является.
5. Актор не тот (кандидат ставит `rejected`, работодатель — `withdrawn`, кандидат — `shortlisted`) → 409 `INVALID_TRANSITION`, не 403. Отклик этому актору виден. Скрытый объект был бы 404 (D16). Здесь объекта не прячут: у этого актора просто нет такого ребра.

## D76 — один повтор после отмены (5A-rules)

`checkReapply` читает историю пары вакансия+кандидат и строку не создаёт.

1. Истории нет → первый отклик. В 5A его пишут с `reapply_count` 0.
2. Любая строка не в `withdrawn`, включая `rejected` и `hired`, → 409 `ALREADY_APPLIED`. Частичный уникальный индекс D27 исключает только `withdrawn`. Активный повтор важнее лимита: это дубль, не исчерпанный лимит.
3. Ровно одна строка `withdrawn` с `reapply_count` 0 → один повтор разрешён. Новую строку в 5A пишут с `reapply_count` 1.
4. 409 `REAPPLY_LIMIT` в двух случаях, оба буквально из D27. «Вторая отмена» — в истории две или больше строк `withdrawn` (отозван и сам повтор). «Повтор сверх лимита» — среди `withdrawn` есть строка с `reapply_count` ≥ 1: единственный повтор уже учтён, даже если первой строки в переданной истории нет.

## D77 — допуск к отклику (5A-rules)

`checkApplyEligibility` вызывает `profileCompleteness` из `@/modules/candidates/service` и свою копию весов не держит.

1. Порог — 60. Формула 11.3 даёт только числа, кратные 5, поэтому снимок профиля не может дать 59. Сравнение всё равно `score < 60`. Тест на 59 подменяет результат функции полноты.
2. При полноте 60 и выше всё равно обязательны `timezone`, `skills` (не меньше 3) и `contact_email`. Нет любой из них → 422 `PROFILE_INCOMPLETE`.
3. `details.completeness` — число из функции полноты. `details.missing` — её `missing[]`, ключи `profile.missing.*`, они уже есть в `en.json` и `ru.json`. Отдельные строки под ключом `applications` не добавлялись.

## D78 — импортированная вакансия (5A-rules)

`checkApplyTarget` сначала смотрит `origin`. `imported` → 422 `EXTERNAL_APPLY` и `details.externalUrl`, даже если статус не `published` и даже если ссылка `null`. Иначе любой статус кроме `published` (`draft`, `closed`, `paused` и остальные) → 422 `JOB_NOT_PUBLISHED`. `internal` и `published` → успех. Строка `applications` здесь не создаётся (D8).

## D79 — срез без записи (5A-rules)

В 5A-rules нет таблиц, миграций, маршрутов и страниц. Наружу модуль отдаёт только `src/modules/applications/service/index.ts`. Запись статуса, history и reveal остаются на 5A и обязаны вызывать эти функции, а не повторять условия.

## D47 — лимит размера тела запроса

`src/lib/http/body-limit.ts`: тело читается потоком и обрывается, как только превышает лимит маршрута; заявленный `Content-Length` больше лимита отклоняется до чтения. Ответ — 413 `PAYLOAD_TOO_LARGE` с `details.maxBytes` (нового кода в каталоге раздела 6 не было; 413 точнее, чем 400). Первый пользователь — загрузка логотипа (лимит 2 МБ + 64 КБ на разметку multipart), закрывает замечание из интеграции 3A. Остальные маршруты с JSON ограничит ревизия 11A.

## D81 — блокировка компаний админом (10A)

1. `GET /api/admin/companies` (новые сверху, фильтр по статусу, поиск по названию с экранированием `%`/`_`) и `POST /api/admin/companies/:id/suspend|unsuspend`. Права — `requireAdmin()`, иначе 404 (P7).
2. Смена статуса идёт через `changeCompanyStatus` сервиса компаний, который пишет `company.status_changed` с админом как actor (P16); отдельной записи `admin.*` нет, чтобы не дублировать.
3. Разблокировка возвращает статус, который был до последней блокировки (поле `from` той записи аудита). Нет записи или в ней не восстанавливаемый статус — `unverified`: компания проходит верификацию заново. Повторная блокировка или разблокировка не заблокированной — 409 `INVALID_TRANSITION`.
4. Заблокированная компания и её вакансии не показываются публично: это фильтр публичных выдач (4A — Codex). Статусы вакансий при блокировке не меняются, чтобы разблокировка не требовала их восстановления.

## D48 — логи сервера (18.1)

1. `src/lib/logger.ts` — pino, JSON в stdout, поле `service`, время ISO. Ключи `email`, `phone`, `password`, `token`, `authorization`, `cookie`, `ip` (и на уровень глубже) заменяются на `[redacted]`. Свободный текст ошибок проходит `scrubText`: email, телефоны (9+ цифр — даты не трогаются), Bearer-токены и строки подключения к БД маскируются. Стек и сырые значения в лог не пишутся — только тип, очищенное сообщение и код драйвера.
2. `x-request-id`: proxy принимает id клиента, если он похож на id (8–64 символа `[A-Za-z0-9-]`), иначе создаёт UUID; id передаётся маршрутам и возвращается в ответе, чтобы пользователь мог назвать его в поддержке. Модуль `src/lib/request-id.ts` отделён от логгера, чтобы proxy не тянул pino.
3. `toErrorResponse` пишет в лог каждую непредвиденную ошибку и `HttpError` с кодом ≥ 500; ошибки 4xx — ожидаемое поведение, в лог не пишутся. Под vitest уровень `silent`; уровень задаётся `LOG_LEVEL`. Отправка в Sentry и алерты 18.1 — 11B.

## D100 — каталог событий и часовой батч (9A-lib)

1. Каталог раздела 15 — данные в `src/modules/notifications/lib/catalog.ts`: ровно 11 типов в порядке таблицы; для каждого — роль получателя, политика (`immediate`; `hourly_batch` только у `application.created`; `daily_digest` только у `matches.digest`) и email-умолчание по таблице; `inapp` у всех типов включён по умолчанию.
2. Payload — zod `strictObject`: только id и короткие поля (jobTitle, companyName, счётчики, enum-статусы). Email, телефон, telegram и любые лишние ключи отклоняются схемой (D16, D23). Id — непустые строки; uuid-валидация остаётся на уровне API.
3. Батч `application.created`: граница часа — по UTC, полуоткрытый интервал `[H:00, H+1:00)`: серверный cron живёт в UTC, локальные границы не добавляют информации, а хранить смещения запрещено (D6). Получатели не смешиваются; вакансии в письме дедуплицируются в порядке первого появления.

## D101 — дайджест совпадений (9A-lib)

1. «Утро по tz» = 08:00 local зоны получателя, инстанс считается через `localToUtc` из `src/lib/tz.ts`, поэтому переходы DST учитываются автоматически; час — константа `DIGEST_HOUR_LOCAL = 8` (до начала стандартного рабочего дня 09:00).
2. «Не чаще раза в сутки» — сравнение инстантов: утро должно наступать не раньше чем через 24 ч после `lastSentAt`. Весенний переход (23-часовые местные сутки) отодвигает дайджест на день, осенний (25 ч) правилу не противоречит. Если тик 08:00 пропущен, отправка разрешена позже в течение дня.
3. `shouldSendDigest`: score ≥ 0.65 (порог 22/9B, приходит параметром) И запланированное утро наступило И канал дайджеста не выключен в preferences.

## D102 — resolveDelivery и auth-письма (9A-lib)

1. Строка `notification_preferences` (type, channel, enabled) переопределяет умолчание; нет строки — умолчание каталога: `inapp` разрешён всегда, email — по таблице 15.
2. Auth-письма (подтверждение адреса, magic link, сброс пароля) — отдельный union `AuthEmailType`, в каталог не входят, в preference-механику не попадают по типу; отключить их нельзя (15). Ссылка отписки в auth-письмах не ставится.

## D103 — ссылка отписки (9A-lib)

1. Токен: `base64url(payload)` + `.` + `base64url(HMAC-SHA256(payload, secret))`, payload — JSON `{ userId, type, expiresAt }` (ISO). Секрет — параметр; переменную окружения подключит 9A.
2. Проверка по порядку: формат → подпись (обе стороны нормализуются SHA-256, затем `crypto.timingSafeEqual` — сравнение за постоянное время) → тип в каталоге (`auth.*` отвергается) → срок жизни: токен валиден строго до `expiresAt`, равенство уже просрочка.

## D104 — i18n писем (9A-lib)

1. Ключи под верхнеуровневым `notifications`: `unsubscribe.link` и `types.<camelCase>.{inapp.{title,body}, email.{subject,body}}`; email-ключи только у типов с email-умолчанием. Соответствие «тип → i18nKey» — поле каталога, содержимое payload подставляется в params.
2. Значения status/decision в params — сырые enum-строки; их человекочитаемые подписи — отдельные UI-ключи в полной 9A. Шаблоны React Email и отправка — в 9A; plural-формы ICU записаны прямо в строках en/ru.

## D105 — запись отклика (5A)

`transitionApplication` — единственный `UPDATE` колонки `applications.status`. Первый отклик — это `INSERT` со статусом `applied` и строка history с `from_status` null, не обновление. Нарушение частичного уникального индекса (SQLSTATE 23505) → 409 `ALREADY_APPLIED`: гонка двух apply не создаёт вторую активную строку. `enforceRateLimit("apply", userId)` вызывается после `checkApplyTarget`, `checkApplyEligibility` и `checkReapply`, поэтому неполный профиль и импортированная вакансия не тратят лимит 30/сутки. `GET /api/applications?as=employer` в 5A → 404: список работодателя — подфаза 5B. Без `as` и с `as=candidate` список — только отклики вызывающего.

## D106 — кто видит отклик (5A)

`GET /api/applications/:id` в 5A отдаёт отклик только кандидату-владельцу. Чужой id и не-uuid → 404. Автопросмотр (`applied` → `viewed`) не делается: это 5B. `PATCH /api/applications/:id/status` всегда идёт с `via = patch` в `transitionApplication`, поэтому `to = shortlisted` → 422 `EXPRESS_INTEREST_REQUIRED` (D75), а кандидат не может этим маршрутом поставить `withdrawn`. Актор PATCH: если `candidate_id` совпал с пользователем — `candidate`; иначе `findMemberRole`. Нет роли → 404, роль `member` → 403, `owner` / `admin` / `recruiter` → `employer`.

## D107 — счётчик повтора (5A)

Новая строка получает `reapply_count` 0, если истории пары нет, и 1, если единственная прошлая строка — `withdrawn` с нулём (D76). В базе `CHECK (reapply_count BETWEEN 0 AND 1)`. Вторая отмена не вставляет третью строку: `checkReapply` отвечает 409 `REAPPLY_LIMIT`.

## D108 — что видит кандидат (5A)

Публичный DTO отклика: `id`, `jobId`, `jobTitle`, `status`, `coverNote`, `reapplyCount`, `createdAt`. Полей риска и контактов нет. Страница `/[locale]/applications` группирует свои отклики по статусу и показывает отзыв, пока статус не `hired`, `rejected` или `withdrawn`. Строки интерфейса — только под ключом `applications`.

## D109 — номер миграции (5A)

Файл — `0009_applications.sql`, хотя `0007` (4A) и `0008` (8A) в этом дереве ещё нет. Скрипт миграций применяет файлы по имени, поэтому после `0006` выполняется `0009`. Пропуск номеров безопасен: отсутствующие файлы не требуются.

## D95 — публичный каталог вакансий (4A)

`GET /api/jobs` отдаёт только published-вакансии и исключает компании suspended/rejected. Непубликованную можно получить только участнику её компании либо администратору; чужой объект одинаково отвечает 404. DTO каталога строится allowlist-ом и не содержит риск-полей, создателя или email отклика.

## D96 — фильтры и курсор каталога (4A)

FTS использует сохранённый `tsvector` и GIN индекс. Каталог использует стабильный курсор `published_at,id`, с сортировочными значениями для relevance и salary; набор запросов ограничивается лимитом + lookahead. Фильтры salary/TZ применяются к ограниченному окну; несравнимые зарплаты остаются нейтральными.

## D97 — нейтральная зарплата в каталоге (4A)

Минимум пользователя сравнивается с `salary_max ?? salary_min` через `compareSalaries` из `money.ts`. Сравнимая ниже минимума вакансия исключается; без зарплаты, с иной базой/периодом или недоступным/устаревшим курсом вакансия остаётся с `salaryComparable=false`. Значения DTO сериализуются только `toMoneyDto`.

## D98 — часовой пояс поиска (4A)

Фильтр `tzOverlapWith` трактует введённый IANA-пояс как рабочий календарь пользователя 09:00–18:00 по будням; окно вакансии берётся из её временных полей, а при отсутствии — 09:00–18:00. Пересечение 14-дневного периода/DST считает только `workHoursOverlap` из `tz.ts`.

## D99 — ежедневные FX курсы и тестовые данные (4A)

Курсы берутся из официального ECB SDMX CSV без ключа и записываются в `fx_rates` как units-per-USD по D66, преобразование quote values выполняется точным `numeric` в PostgreSQL. Seed 5k (`src/db/seed/jobs-4a.mjs`) разрешён только для loopback DB и не запускается миграцией; perf harness и integration check измеряют server-side p95 каталога отдельно.

## D49 — источники импорта создаются в 4A

`import_sources` и `job_sources` (4.1) созданы миграцией 0007 (4A, Codex): публичная карточка импортированной вакансии отдаёт `source{name,url}` (раздел 7), и 4A первой читает эти таблицы. Подфаза 8A использует их как есть и добавляет только `import_runs`; менять их структуру — с записью в своём диапазоне D.

## D115 — список откликов работодателя (5B)

`GET /api/applications?as=employer&jobId=` отдаёт отклики вакансии любому члену её компании (`owner`, `admin`, `recruiter`, `member`). Нет вакансии или нет членства → 404, в том числе для чужой компании. Без `jobId` → 400. Ответ — курсор раздела 6: `{ items, nextCursor }`, `limit` по умолчанию 20 и не больше 50, ключ `(created_at, id)` по убыванию. Список кандидата (`as` пустой или `candidate`) остаётся `{ applications }` как в D105. В строке работодателя есть `candidateId` и `candidateName`, ключа `contacts` нет.

## D116 — автопросмотр (5B)

`GET /api/applications/:id`: кандидат-владелец получает отклик и статус не меняется. Член компании, если статус `applied`, вызывает `transitionApplication` с `actor: employer` и `via: auto_view`. Повторное открытие `transitionApplication` не вызывает: из `viewed` такого ребра нет. Роль `member` может открыть и тем самым поставить `viewed`, но PATCH по-прежнему только у `owner` / `admin` / `recruiter` (D106): для `member` это 403.

## D117 — кнопки статуса (5B)

Кнопки карточки — это `TRANSITIONS`, где `actor = employer` и `via = patch`. Отдельной таблицы нет. `shortlisted` в этот список не входит: PATCH туда → 422 `EXPRESS_INTEREST_REQUIRED` (D75). Дойти до `interview` можно только из уже стоящего `shortlisted`, а эту запись пишет 5C. 5B статус `shortlisted` не вставляет. Тест, которому нужно проверить `interview` / `offer` / `hired`, сам ставит `shortlisted` прямым SQL; продукт так не делает.

## D118 — профиль кандидата работодателю (5B)

`getCandidateForViewer` пускает не только владельца. Член компании видит профиль, если у кандидата есть любой отклик на вакансию этой компании. Проверка живёт в сервисе откликов (`employerCanSeeCandidate`); сервис кандидатов вызывает её, а не репозиторий откликов. Ответ — прежний allowlist `CANDIDATE_DTO_KEYS`: ключа `contacts` нет (не `null`), нет email входа и `auth_uid`. Остальным — 404.

## D119 — уведомления не отправляются (5B)

Миграции 5B нет: таблиц раздела 4.1 для этого пайплайна хватает. События 9A уже есть в каталоге `application.viewed` и `application.status_changed`. Вызов, когда появится отправка: после первого auto-view — `application.viewed` кандидату (`employerNotification` в `openApplication`); после успешного employer PATCH — `application.status_changed` тому же кандидату (комментарий в `patchApplicationStatus`). 5B очередь не ставит и писем не шлёт.

## D70 — конвейер импорта 8A

Адаптер источника только читает фикстуру (`loadFixture()`) и перекладывает поля в `RawImportedJob`; сетевого `fetch` в 8A нет вообще, а `IMPORT_LIVE_ENABLED=true` отклоняется ошибкой до 8B (D18). Все правила — в `service/`: нормализация (13.2), дедуп (13.3, чистые функции над строками из repo), решение по записи (`decideOutcome`), запись через сервис вакансий (`saveImportedJob`, `expireImportedJobs`); `repo/` содержит только запросы. Источник импортируется не чаще раза в час (по `import_runs.started_at`), не больше 500 записей за прогон; история `import_runs` чистится через 180 дней (17). Cron `/api/cron/import` каждый час в :30, без верного `Bearer CRON_SECRET` → 404.

## D71 — несколько источников одной вакансии

Ключ `job_sources` — `(import_source_id, external_id)`: одна вакансия может прийти из нескольких источников. Первая строка источника вакансии — основная (`is_primary`, уникальный частичный индекс по `job_id`); публичная карточка показывает только её. Дубль импортированной вакансии сливается в существующую (`merged`), дубль внутренней вакансии скрывается (`removed`, причина `duplicate_of_internal`): импорт никогда не перезаписывает внутреннюю вакансию и не связывается с внутренней компанией (компания ищется только среди `origin='imported'`: по домену, затем по сходству имени ≥ 0.9). Истечение по 13.4: вакансия становится `expired`, только когда каждый её источник пропустил её два прогона подряд.

## D72 — external apply

`POST /api/jobs/:id/apply-external` отдаёт `{ externalUrl }` для опубликованной вакансии с `application_method='external_url'`, иначе 404; гость тоже получает ссылку. Запись `user_job_feedback(action='applied_external')` идёт через интерфейс `ExternalApplyRecorder`; пока таблицы из 4B нет в `master`, используется `recordNothing` — **BLOCKED** до вливания 4B, тогда интеграция подставляет writer feedback и переводит кнопку «Apply» карточки на этот endpoint.

## D73 — нормализация без зарплаты и часовые пояса

В фикстурах нет зарплаты: импортированная вакансия идёт без неё, компонент зарплаты в матчинге нейтрален (D4/D5). Часовой пояс — явное IANA `Area/City`, `UTC` или однозначная аббревиатура из таблицы `src/lib/tz-aliases.ts` (CET, MSK, JST…); фиксированные смещения (`GMT+3`) и неоднозначные аббревиатуры (IST, EST, CST) дают `null` (D6). Неизвестная категория → `operations`, неизвестный тип занятости → `full_time`; нераспознанные навыки в вакансию не попадают и уходят в `skill_suggestions` с `source: 'import'`.

## D74 — автомодерация импорта

Scam-паттерны (`src/config/scam-patterns.ts`) проверяются по заголовку, описанию и ссылке отклика (сокращатели ссылок — сигнал). Совпадение → вакансия `removed` с `risk_score=4` и `risk_flags=['scam_pattern_rejected']`, счётчик `rejected` и одна строка `moderation_queue` в `pending` (без повторов при следующих прогонах), чтобы модератор мог проверить ложное срабатывание.

## D120 — express-interest одной транзакцией (5C)

`POST /api/applications/:id/express-interest` для `owner` / `admin` / `recruiter`. Нет членства → 404, роль `member` → 403. В транзакции строка отклика блокируется `SELECT … FOR UPDATE`, затем `transitionApplication` с `via: express_interest` и INSERT в `application_reveals` (`via = shortlisted`). Уже `shortlisted` и строка reveal есть → 200 без второй строки. Из статуса, откуда в `shortlisted` ребра нет → 409. Ответ 200 и в первый раз: тело — DTO отклика без ключа `contacts`. Два одновременных вызова сериализуются блокировкой и оставляют одну строку reveal. Тестовый `beforeReveal` бросает ошибку после UPDATE и до INSERT: транзакция откатывает оба.

## D121 — кто читает контакты (5C)

`GET /api/applications/:id/contacts`: любой член компании (включая `member`), только если статус `shortlisted | interview | offer | hired` и строка reveal есть. Иначе 404, в том числе для гостя, чужой компании и закрытого статуса. Тело — `ContactsDto` из `contactsService`, не вложенный ключ отклика. Каждый ответ 200 пишет `audit_logs(action='contacts.read', entity_type='application')`; в `diff` только статус, без email и телефона. `recordAudit` ходит своим соединением и вызывается после успешного чтения: пул `app_rw` один, а `src/lib/audit.ts` менять нельзя.

## D122 — закрытие доступа (5C)

`withdrawn` и `rejected` снова дают 404 на контакты. Строка `application_reveals` остаётся. `interview` / `offer` / `hired` доступ не закрывают. Удаление аккаунта — 10C. `shortlisted` без строки reveal контактом не считается: так продукт не пишет, а прямой SQL из тестов 5B контакты не открывает.

## D123 — страница контактов и кнопка (5C)

`/[locale]/contacts` перечисляет кандидатов, чьи контакты этому члену сейчас доступны по D23, и показывает поля контакта. Кнопка «Проявить интерес» на карточке отклика есть только из `applied` и `viewed`. Профиль и DTO отклика по-прежнему без ключа `contacts`.

## D124 — уведомление reveal не отправляется (5C)

Миграция — `0012_application_reveals.sql`. Номера 0008, 0010 и 0011 могут отсутствовать: файлы применяются по имени. Событие `mutual_interest.revealed` уже есть в каталоге 9A-lib. Вызов, когда появится отправка: после новой (не повторной) строки reveal — кандидату и членам recruiter+ (`revealNotification` в `expressInterest`). 5C очередь не ставит.

## D82 — очередь модерации (10A, вторая часть)

1. `GET /api/admin/queue` — `pending`-строки `moderation_queue`, старые первыми (SLA 24 ч считается от `created_at`, 14.4), курсор `(created_at, id)`; строка старше 24 ч помечена `overdue`. В строке — краткий вид объекта (название, статус, источник, `risk_score`, компания); удалённый объект — `subject: null`.
2. `POST /api/admin/queue/:id/decide` `{ decision: approved|rejected, note }`: отказ без `note` → 400. Строка сначала «забирается» условным UPDATE `pending → решение`; проигравший гонку админ получает 409 `ALREADY_DECIDED`. Если действие над объектом падает, строка возвращается в `pending`. Остальные `pending`-строки того же объекта закрываются тем же решением.
3. Действие над объектом (`planDecision`, чистая функция): внутренняя вакансия в `pending_moderation` — `approve`/`reject` через `transitionOwnedJob` (причина отказа пишется в историю статусов и видна работодателю); живая внутренняя вакансия при отказе снимается (`removed`, пост-модерация); импортированная вакансия, отклонённая scam-фильтром (D74), при одобрении возвращается в `published` с обнулённым риском, при отказе остаётся `removed`; компания (`possible_duplicate`) при отказе → `rejected`, при одобрении не меняется, заблокированная не трогается.
4. Каждое решение пишет `admin.queue_decided` (`itemId`, `decision`, `effect`, `note`) с админом как actor (P16). Уведомление `job.moderation_decided` — точка вызова отмечена комментарием, отправка появится с 9A.

## D83 — снятие вакансий и панель импорта (10A)

1. `GET /api/admin/jobs` — все вакансии любого источника и статуса, новые первыми, поиск по названию (экранирование `%`/`_`), фильтры статуса и источника. `POST /api/admin/jobs/:id/remove` `{ reason }` (3–500 символов) снимает вакансию любого источника; уже снятая → 409 `INVALID_TRANSITION`; запись `admin.job_removed`.
2. `GET /api/admin/import/sources|runs` и `/admin/import` — только чтение. `POST /api/admin/import/sources/:id/toggle` не сделан: фикстурные источники 8A создаются с `enabled=false` и всё равно запускаются, так что переключатель сейчас ничего бы не значил; он появится вместе с живым источником 8B, где `enabled` будет решать, ходит ли cron в сеть.
3. D84 зарезервирован за жалобами и авто-паузой (14.5), которые делаются после вливания 4B (`reports`).

## D130 — подтверждение домена (10B)

1. `POST /api/companies/:id/verification` `{ method, target }` — только owner (член без роли owner → 403, чужой → 404, импортированная компания → 404). Нужен `companies.domain`, иначе 422 `DOMAIN_REQUIRED`. Бесплатные почтовые домены (`src/config/free-email-domains.ts`, общий список для верификации и risk-флага 14.3) → 422 `FREE_EMAIL_DOMAIN`. Корпоративный email должен быть на домене компании или его поддомене (`a@team.example.com` для `example.com`), иначе 422 `DOMAIN_MISMATCH`. Для DNS цель — сам домен.
2. Токен — 32 случайных байта (base64url). В `company_verifications` хранится только SHA-256; сам токен уходит письмом (ссылка `/{locale}/employer/company/verify?company=…&token=…`) или возвращается один раз как значение TXT `intgetion-verify=<token>`. Срок — 72 ч. Новая заявка переводит прежние `pending` в `expired`. Лимит — `rateRules.verificationRequest`: 5 заявок на компанию в сутки.
3. `POST …/verification/confirm` `{ token }` — тоже только owner. Для email доказательство — владение токеном из письма; для DNS запись должна быть видна в `resolveTxt` домена (чанки TXT склеиваются), иначе 422 `DNS_RECORD_NOT_FOUND`, а заявка остаётся `pending`. Просроченный токен → 422 `TOKEN_EXPIRED`, заявка становится `expired`. Неизвестный → 404.
4. Повторная заявка после `rejected` — не раньше чем через 7 дней после прошлой (409 `REAPPLY_TOO_SOON`). После отказа старое подтверждение домена не засчитывается: нужно новое, сделанное позже отказа.

## D131 — письмо верификации без 9A

Отправка письма — интерфейс `VerificationMailer`. По умолчанию Resend через `fetch`, если заданы `RESEND_API_KEY` и `EMAIL_FROM`. Без них письмо не уходит, ответ содержит `emailSent: false`, страница советует способ через DNS, в лог пишется предупреждение без адреса и токена. Когда 9A введёт общий `EmailSender`, верификация переедет на него. Токен никогда не пишется в лог и не возвращается API для email-способа.

## D132 — от заявки к verified (14.1)

Шаги 1 (домен) и 2 (`legal_name`, `country`, `website_url` на домене компании, `www.` допускается) переводят компанию `unverified|rejected → pending_verification` и ставят в `moderation_queue` строку `company / verification_review`. Проверка запускается после подтверждения домена и после каждого PATCH компании. Одобрение этой строки в очереди 10A (`verify_company`) проверяет шаг 3 — у компании есть вакансия, которую админ перевёл `pending_moderation → published` (`job_status_history` с actor) — и только тогда ставит `verified`. Если чего-то не хватает — 409 `VERIFICATION_INCOMPLETE` с перечнем шагов, строка очереди остаётся `pending`. Отказ — `rejected`, как у остальных строк компании (D82).

## D133 — флаг Trusted (14.2)

`/api/cron/trusted` раз в сутки (03:45 UTC) пересчитывает флаг для `verified`-компаний и для любой компании, у которой он стоит. Условия: ≥ 5 вакансий, хоть раз бывших `published`; 0 подтверждённых жалоб за 90 дней; если откликов ≥ 10 — медиана времени от отклика до первого действия работодателя ≤ 7 дней (первое действие — первая смена статуса, сделанная не кандидатом; отклики без ответа считаются до текущего момента). Нарушение любого условия или уход из `verified` снимает флаг. Изменение пишет `company.trusted_changed` без actor. Пока в `master` нет таблицы жалоб (4B), счётчик жалоб возвращает «неизвестно», и флаг не ставится никому (fail closed). При вливании 4B сюда подключается подсчёт подтверждённых жалоб.

## D134 — страница верификации

`/[locale]/employer/company/verify` — только owner (иначе 404). На ней три шага 14.1 со статусом, форма реквизитов (PATCH компании), выбор способа и поле кода; `?token=` из письма подставляется в поле, подтверждение идёт отдельной кнопкой (POST), а не по GET-ссылке. Бейджи `verified` / `trusted` на публичных страницах уже есть с 4A. В отдельный список они не выносятся.

## D85 — оценка токенов и обрезка контекста (7-lib)

Токенизатора в проекте нет и не будет до 7A, поэтому оценка — верхняя: байты UTF-8 / 3, с округлением вверх, плюс 4 токена на сообщение. Английский текст в среднем ~4 байта на токен, кириллица (2 байта на букву) ~5–6 байт на токен, так что оценка завышает оба языка и бюджет 6 000 входных токенов не превышается на практике. `trimContext` оставляет не больше 12 последних сообщений и столько, сколько помещается вместе с system prompt и summary; выброшенные возвращаются вызывающему для summary. System prompt и summary сверх бюджета — ошибка программы, а не обрезка.

## D86 — провайдер и структурированный вывод

`LLMProvider.complete` — единственная точка вызова модели; адаптер Anthropic появится в 7A. Модели — `LLM_MODEL_CHAT` / `LLM_MODEL_EXTRACT`, по умолчанию D29. `maxTokens` проверяется до вызова: 1..800 (12.5). Структурированный вывод — принудительный вызов инструмента `record_result`, аргументы проходят zod-схему; если вызова нет или схема не прошла — `LLMOutputError`, данные «как есть» не возвращаются. Аргументы любых tool calls в чате тоже проходят схему инструмента, неизвестный инструмент — ошибка. Для тестов — `FakeLLMProvider` со сценарием ответов, записывающий запросы.

## D87 — недоверенные данные и редакция PII

`wrapUntrusted(source, text)`: `source` только `job:<id>`, `company:<id>`, `user_message` (иначе ошибка); из текста удаляются управляющие и bidi-символы, `&`, `<`, `>` экранируются, поэтому закрыть или открыть тег изнутри нельзя; обрезка до 2 000 символов по code points с атрибутом `truncated="true"`. `redactPii` заменяет email (в том числе `[at]`/`[dot]`), телефоны (9–15 цифр в типовых форматах) и ссылки (со схемой, `www.` и голые host/path вида `t.me/x`) на `[email]`, `[phone]`, `[link]`; названия технологий вроде `ASP.NET`, `Node.js`, `Socket.IO`, `C#` не трогаются. Номера документов (паспорт, SSN) отдельно не распознаются — бот не просит и не хранит их (adversarial-кейсы).

## D88 — allowlist полей на вход LLM

`pickLlmFields(input, spec)` оставляет только поля из спецификации, рекурсивно; строки по пути проходят `redactPii`, вложенные объекты в «плоских» полях отбрасываются. Спецификация, в которой встречается контактное или идентифицирующее поле (email, phone, telegram, ссылки, `applicationUrl`, ФИО, юр. название, id пользователя и т. п.), — ошибка программы. Готовые списки: `PROFILE_LLM_FIELDS` (12.3) и `JOB_LLM_FIELDS` (публичные поля вакансии; описание и название компании передаются отдельно через `wrapUntrusted`).

## D89 — деньги бюджета и evals

Стоимость — целые micro-USD (`BigInt`), цены — параметр (`PriceTable`, micro-USD за 1 млн токенов), округление вверх; бюджет `LLM_DAILY_BUDGET_USD` разбирается из строки точно, без float. Circuit breaker открыт, когда суточная стоимость строго больше бюджета; без бюджета закрыт. Аномалия — стоимость пользователя за сегодня строго больше 3× медианы его прошлых суток, при истории не меньше 3 дней. Evals: 20 golden-диалогов (10 en, 10 ru; зарплата в минорных единицах по D19; PII в репликах помечена и проверяется редакцией) и 18 adversarial-кейсов, покрывающих все 6 типов атак 19.3; схемы — `evals/schema.ts`. Раннер `pnpm eval` — 7B.

## D110 — модуль feedback и события (4B)

1. Модуль называется `src/modules/feedback` (раздел 22 называет фичу по таблице `user_job_feedback`). Чистые правила — `rules.ts`: действия — enum `feedback_action` (8 штук); `reason` допустим только для `hidden`/`dismissed` (4.1) и, если указан, только из списка salary|format|timezone|company|role|other; без причины скрывать можно (раздел 7: `reason?`), для остальных действий причина запрещена, включая `hidden_company`.
2. `recordJobFeedback({ userId, jobId, companyId, action, reason })` экспортируется через `service/index.ts`: её вызывают 5A (`applied`) и 8A (`applied_external`). Невалидная комбинация — 422 `VALIDATION_ERROR`.
3. Скрытие компании (`scope: "company"`) пишется как событие `hidden_company` на конкретной вакансии с заполненным `company_id` — без reason, потому что 4.1 даёт reason только для hidden/dismissed. Скрытие отдельной вакансии — `hidden` с reason по выбору пользователя.

## D111 — коды ошибок и идемпотентность (4B)

1. Повторная жалоба на тот же объект → 409 `ALREADY_REPORTED` (уникальный индекс `reports(reporter_id, entity_type, entity_id)`; нарушение 23505 маппится в сервисе). Код добавлен строкой, а не в `errorCodes`, потому что `src/lib/http/**` — чужой файл (PARALLEL_WORK п.5); строка следует конвенции каталога ошибок раздела 6.

3. Вакансия, невидимая в публичном листинге (не `published` либо компания `suspended`/`rejected`), даёт 404 для save/hide/report — проверка через `getJobForPublic`.

## D112 — скрытое не показывается (4B)

1. Фильтрация — в сервисе jobs, не в repo (замечание 3.2 из интеграции 3B): `searchJobs` и `listPublishedJobsForCompany` принимают `viewer.hidden` (наборы id скрытых вакансий и компаний) и фильтруют строки после выборки; репо 4A не менялся. Наборы собирает `getHiddenSetsForViewer` сервиса feedback.
2. Скрытие применяется только для залогиненного пользователя: GET `/api/jobs`, страница `/jobs` и страница компании подставляют viewer, если сессия есть; персонализированный ответ уходит с `Cache-Control: private, no-store` вместо публичного кэша.
3. Прямая ссылка `/jobs/[id]` на скрытую вакансию продолжает работать — раздел 7 требует исключения из листингов, а не запрета доступа; сохранение также остаётся доступным для unsave со страницы /saved-jobs через фильтр списка (D113), а не через 404.
4. Персонализированные страницы (`/jobs`, `/companies/[slug]`, `/saved-jobs`) объявлены `dynamic = "force-dynamic"`: попытка пререндера проглатывала сигнал `DYNAMIC_SERVER_USAGE` из `cookies()` (viewer в try/catch) и закрепляла статический гостевой листинг, из-за чего скрытие не было видно. `GET /api/jobs` остаётся обычным роутом; при viewer ответ помечается `Cache-Control: private, no-store`.

## D113 — /saved-jobs (4B)

1. Список сохранённых — published вакансии видимых компаний (через `listPublicJobsByIds` сервиса jobs), новые сверху; собственные hidden-вакансии/компании из списка исключаются, чтобы страница не показывала то, что пользователь просил скрыть.

## D114 — лимит жалоб (4B)

## D84 — жалобы и авто-пауза (10A, третья часть)

1. `GET /api/admin/reports` — жалобы по статусу (по умолчанию `open`), старые первыми, с названием вакансии и компании; id жалобщика админке не отдаётся. `POST /api/admin/reports/:id/decide` `{ decision: confirmed|dismissed, note }`: решение «забирается» условным UPDATE `open → …`, повтор → 409 `ALREADY_DECIDED`; запись `admin.report_decided` (note — только в аудите: в `reports` нет поля для неё).

## D144 — шрифты и бюджет LCP (UI-1)

Вошедший пользователь без профиля кандидата получает 200 `{ items: [], nextCursor: null, lowData: true, profileHints: [] }`, не 404. Так же отвечает `getMatches` в 6A (D151.3), и страница показывает EmptyState «Заполните профиль». Нет сессии — 401. Гость на `/matches` уходит на `/login`.

## D161 — очередь пересчёта это таблица, не pg-boss (6B)

D25 (pg-boss) для MVP заменён тем же приёмом, что очередь писем (D125): таблица `matching_jobs`, cron `GET /api/cron/matching` с `Bearer CRON_SECRET` (без секрета — 404). Пачка не дольше 45 с. Захват — `UPDATE … WHERE id = (SELECT … FOR UPDATE SKIP LOCKED)`. Повтор: `2^(attempts-1)` минут, после 5 попыток `failed`. Строка `running` старше 2 минут берётся снова. На открытую задачу вакансии (pending или running) — один ряд, `ON CONFLICT DO NOTHING`.

## D162 — когда ставится задача (6B)

Задача ставится, когда `transitionOwnedJob` заканчивается статусом `published` для действий `publish`, `approve` и `extend` (неподтверждённая публикация остаётся `pending_moderation` и в очередь не идёт). В `approve_job` очереди модерации — вторая, идемпотентная постановка. Импорт и повторная публикация импортированной вакансии этот хук не вызывают: их кэш кандидата обновится по правилу свежести 6A.

## D163 — вкладки и подсказки профиля (6B)

`?tab=all|new|hidden`, по умолчанию all. «Новые» — опубликованы меньше 48 часов. «Скрытые» — вакансии с `dismissed`, даже если после пересчёта score < 0.55; из «Все» и «Новые» они убраны. `GET /api/matches` по-прежнему отдаёт все показанные (score ≥ 0.55), в том числе ещё не выпавшие dismissed. `profileHints` — все поля `salary`, `format`, `timezone`, у которых за 90 дней ≥ 3 скрытия или dismissed с этой причиной, в этом порядке. Ссылки: `#salary`, `#preferences`, `#basics`. Пустой lowData на вкладке «Все» — EmptyState профиля; если совпадения есть, они показываются.

## D164 — курсор, лимит отказа и граница 6B (6B)

Курсор — `{ score, jobId }` в base64url, порядок score по убыванию, job id по возрастанию. `limit` по умолчанию 20, максимум 50. `rateRules` не менялся (файл Claude Code): отказ «Не подходит» ограничен 60 событиями `dismissed` за час по `user_job_feedback`, ответ 429 с `Retry-After: 3600`. Миграция `0016_matching_jobs.sql`. Кэш пользователя удаляется после записи feedback, следующий `GET` пересчитывает. Подписи карточки, счётчик вкладок, подвал и неактивный язык используют `--fg-muted`: `--fg-subtle` (#71717A) на `#000` даёт 4.34:1 и не проходит WCAG AA на 12–14 px, хотя DESIGN оценивает его как 4.6:1 и разрешает только от 14 px.

## D165 — экспорт данных (10C)

`GET /api/me/export` отдаёт один JSON-файл `intgetion-export-YYYY-MM-DD.json` с `Cache-Control: no-store`. Поле `exportVersion` (сейчас 1) растёт при изменении состава. Внутри: строка `users`, профиль кандидата с контактами, навыками, опытом, языками и предпочтениями, профиль работодателя, членства в компаниях, отклики, сохранённые вакансии, `user_job_feedback`, жалобы, уведомления и их настройки. Email входа берётся из Supabase Auth (D166), в базе его нет. Лимит — 5 выгрузок в сутки на пользователя (`dataExport`). Каждая выгрузка пишет аудит `user.data_exported`. Таблиц бота пока нет; они добавятся в выгрузку вместе с 7A.

## D166 — Auth Admin API без SDK (10C)

`src/lib/supabase/admin.ts` вызывает `/auth/v1/admin/users/{uid}` через `fetch` с `SUPABASE_SERVICE_ROLE_KEY` в `apikey` и `Authorization`. Таймаут 10 с. Ключ живёт только на сервере. Если ключа нет, вызовы возвращают `unavailable` или `null` и не бросают исключение. Тем же путём 9A теперь получает адрес получателя письма: `lookupLoginEmail` пишет только активным пользователям. В CI ключ берётся из `supabase status`.

## D167 — удаление аккаунта (10C, P13)

`DELETE /api/me { confirm: "DELETE" }` работает так. Одна транзакция:

- `users.status = deleted`, `deleted_at`;
- `marketing_opt_in = false`, `last_active_at = null`;
- удаляются профили кандидата и работодателя (каскадом контакты, навыки, опыт, языки), членства, сохранённые вакансии, уведомления, письма, настройки и `matching_results`;
- `cover_note` в откликах обнуляется.

Сами отклики остаются у работодателя как анонимный кандидат. Контакты дают 404, потому что строки `candidate_contacts` больше нет.

Компания, где пользователь был единственным владельцем, получает `suspended`. Её открытые вакансии закрываются, в `job_status_history` пишется реальный прежний статус и причина `owner_account_deleted`.

После транзакции удаляется пользователь Auth и сессия. Аудит `user.deleted` пишется без `actor_id`. Админ сам себя удалить не может: 422 `ADMIN_PROTECTED`. Повторное удаление даёт 404. Строка `users` остаётся как якорь внешних ключей.

## D168 — retention-cron (10C)

`/api/cron/retention` запускается ежедневно в 03:20 UTC (`vercel.json`) с `Bearer CRON_SECRET`, без секрета — 404. Он удаляет:

- `user_job_feedback` и `audit_logs` старше 365 дней (DELETE для `app_rw` разрешён, UPDATE отозван);
- `matching_results` старше 30 дней по `computed_at`;
- прочитанные уведомления старше 90 дней.

Тот же cron повторяет удаление Auth-пользователей, которые помечены `deleted` в последние 7 дней. Если Auth-пользователь уже удалён, это не ошибка. pg-boss не нужен: задача одна и идемпотентна.

## D190 — уведомления о решениях админа (после 9A)

Три события из каталога раздела 15 теперь отправляются через `safeNotify`. Сбой уведомления не откатывает решение (D127).

- `job.moderation_decided` получает создатель вакансии:
  - `approve_job` → `approved`;
  - `reject_job` или `remove_job` (снятие живой вакансии) → `rejected`.

  У импортированных вакансий создателя нет, им уведомление не отправляется. `admin_jobs` теперь отдаёт `createdBy`.

- `company.verification_decided` получают все владельцы компании:
  - `verified` отправляется из `approveCompanyVerification`;
  - `rejected` — из очереди при `reject_company`.

  Блокировка (`suspended`) этим событием не сообщается: в каталоге его решения только `verified` и `rejected`.

- `report.decided` получает автор жалобы, решение `confirmed` или `dismissed`. Жалоба на сущность вне `job | company | user` не уведомляется.

## D170 — таблицы бота (7A, миграция 0018)

`bot_conversations` и `bot_messages` повторяют раздел 4.1. Отличия:

- `channel` пока допускает только `web`;
- `last_message_at` обязателен и по умолчанию равен `now()`;
- у сообщений неотрицательные `tokens_*` и `cost_micro_usd`;
- частичный индекс по `created_at` для суточной стоимости.

Новая таблица `bot_confirmations` — одноразовые подтверждения из 12.3. В ней хранятся пользователь, беседа, инструмент, точные аргументы и их sha256-хеш, срок 10 минут, `decided_at` и `accepted`. Подтверждение берётся одним `UPDATE … WHERE decided_at IS NULL AND expires_at > now`, поэтому принять его дважды или после срока нельзя.

Все три таблицы закрыты RLS deny-all и доступны `app_rw`. Номер 0016 занят 6B, 0017 не используется.

## D171 — Anthropic через fetch, цены — конфигурация (7A)

Адаптер `AnthropicProvider` в `src/lib/llm/anthropic.ts` обращается к Messages API (`2023-06-01`) через `fetch` без SDK, таймаут 30 с. Схемы инструментов строятся `z.toJSONSchema`. Результаты инструментов и следующее событие уходят одним user-ходом.

Цены не зашиты в код: `LLM_PRICES_MICRO_USD` — JSON вида `{модель: {in, out}}` в микродолларах за 1M токенов. Бот включается, только если есть и `ANTHROPIC_API_KEY`, и цена для `LLM_MODEL_CHAT`: без цены нельзя посчитать бюджет и circuit breaker. Если чего-то нет, чат отвечает `BOT_UNAVAILABLE` и предлагает обычный поиск.

## D172 — сессия бота (7A)

Cookie `bot_session` хранит 32 случайных байта (base64url), в базе лежит только sha256 (`session_token_hash`). Свойства cookie: HttpOnly, `SameSite=Lax`, `Path=/api/bot`, 30 дней; `Secure` — когда `NEXT_PUBLIC_SITE_URL` на https (production-сборка CI работает по http).

Беседа выбирается только по cookie. `conversationId` из тела запроса принимается ради формы из ТЗ, но не используется. Если cookie указывает на чужую беседу (гостевую после входа или другого пользователя), начинается новая. Привязка гостевой беседы при регистрации — в 7B.

## D173 — слой инструментов (7A, P8, P11)

`src/modules/bot/service/tools.ts` — единственный путь модели к данным. Инструменты: `search_jobs`, `get_job`, `get_my_profile`, `propose_profile_update`, `save_job`, `hide_job`, `apply_to_job`, `get_my_applications`. `get_matches` появится в 7B после 6B.

Права:

- гостю модель даже не предлагает пользовательские инструменты;
- `runTool` всё равно проверяет права заново: гость получает 403 (P11);
- запись профиля и отклик пользователя требуют подтверждения, без совпадающего подтверждения (инструмент, пользователь, хеш аргументов) — 422 `CONFIRMATION_REQUIRED` (P8).

Правки профиля проходят через allowlist `candidatePatchInput` из 12.3: контактов, имени, summary и опыта в нём нет. `patchCandidateProfile` накладывает патч на сохранённый профиль и сохраняет обычным путём с той же валидацией. Предложение гостя остаётся в `state.draft`.

Данные для модели:

- вакансии — через `JOB_LLM_FIELDS`, обёрнутые в `<untrusted_data source="job:…">`, описание отдельно;
- профиль — через `PROFILE_LLM_FIELDS`.

## D174 — SSE-протокол чата (7A)

`POST /api/bot/message` всегда отвечает потоком `text/event-stream`. События:

- `token` — текст ответа целиком за раунд; поток по токенам — позже;
- `tool_result` — карточка для UI (`jobs`, `draft`, `saved`, `hidden`, `applied`, `profile_saved`);
- `confirm_request` — `confirmationId`, инструмент, аргументы, срок;
- `error` — код;
- `done`.

Ошибки после начала потока, включая лимиты, приходят событием `error` с кодом (`RATE_LIMITED`, `BOT_UNAVAILABLE`, `BOT_BUDGET_EXCEEDED`, `BOT_TRY_LATER`), а не HTTP-статусом. За одно сообщение модель делает не больше 3 раундов инструментов. Инструмент записи останавливает ход карточкой подтверждения.

## D175 — бюджеты (7A)

Лимиты:

- гость — `botGuest`, 30 сообщений в сутки по ключу IP + сессия;
- пользователь — `botUser`, 200 в сутки.

Стоимость каждого ответа модели пишется в `bot_messages`. Circuit breaker суммирует стоимость с начала UTC-суток и сравнивает с `LLM_DAILY_BUDGET_USD`; при превышении — отказ `BOT_BUDGET_EXCEEDED` и алерт в лог.

Аномалия: стоимость пользователя за сегодня больше 3× медианы его прошлых дней (окно 14 дней, минимум 3 дня истории). Тогда — алерт и дополнительный лимит 30 сообщений по ключу `anomaly:<user>`. На ответ — не больше 800 токенов. Контекст — не больше 12 сообщений и 6 000 оценочных токенов (`trimContext`), начинается с хода пользователя.

## D176 — история и summary (7A)

Из базы читаются последние 24 сообщения, затем обрезаются `trimContext`. Сообщения пользователя хранятся уже отредактированными (`redactPii`: email, телефон, ссылка) и уходят модели в `<untrusted_data source="user_message">`. Системные события («пользователь подтвердил…») уходят модели как `[event] …`. Поле `summary` в 7A не заполняется: сжатие старой истории потребует отдельного вызова модели и войдёт в 7B вместе со сценариями.

## D215 — сид в миграции под FORCE RLS

Миграция 0019 упала в облаке: `enable_rls_deny_all` включает `FORCE ROW LEVEL SECURITY`, и вставка навыков от роли миграций (`migrator`, владелец таблиц, не суперпользователь) отклонялась политикой. В CI это не видно — там миграции идут от суперпользователя `postgres`. Правило для миграций с данными в таблицах под RLS: в той же транзакции `ALTER TABLE … NO FORCE ROW LEVEL SECURITY`, вставка, `ALTER TABLE … FORCE ROW LEVEL SECURITY`; файл выполняется одним запросом, при ошибке откатывается целиком, и защита не остаётся снятой. `pnpm db:verify` после применения проверяет, что `FORCE` включён на всех таблицах. Следующий шаг (за Claude Code): в CI применять миграции от роли без прав суперпользователя, как в облаке.

## D181 — экстракция профиля из диалога (7B)

## D213 — OpenRouter и бесплатные модели для бота

По решению основателя бот может работать через OpenRouter (`src/lib/llm/openrouter.ts`): API в формате OpenAI Chat Completions поверх `fetch`, тот же контракт `LLMProvider`, вызовы инструментов как `function`, аргументы — JSON-строка (сломанная строка не пропускается: её отвергает `parseToolCalls`). OpenRouter может вернуть ошибку апстрима как 200 с `error` — это `LLMProviderError`. Выбор — `src/lib/llm/select.ts`: `LLM_PROVIDER=openrouter` + `OPENROUTER_API_KEY`, иначе Anthropic как раньше (D171). Модель по умолчанию для OpenRouter — `qwen/qwen3.8-27b:free` (бесплатная, поддерживает инструменты и `tool_choice`, на 2026-10-04); меняется через `LLM_MODEL_CHAT`/`LLM_MODEL_EXTRACT`. Модели с суффиксом `:free` получают нулевую цену, поэтому `LLM_PRICES_MICRO_USD` для них не нужен; дневные лимиты сообщений на пользователя и гостя (`botUser`, `botGuest`) действуют как прежде. Платная модель без цены по-прежнему выключает бота. Ограничения бесплатных моделей: лимиты OpenRouter (около 20 запросов в минуту, 50–1000 в день в зависимости от баланса), качество вызова инструментов ниже, провайдеры бесплатных моделей могут сохранять запросы — PII до модели не доходит (D179). Для продакшена — платная модель с ценой.

## D217 — вход через Telegram

Заменяет заглушку Telegram из D200; Google и X остаются заглушками. Supabase Auth не знает Telegram, поэтому вход свой. Кнопка ведёт на `oauth.telegram.org/auth` (`bot_id` — число до двоеточия в `TELEGRAM_BOT_TOKEN`, `return_to` — `/{locale}/auth/telegram`), без скрипта виджета: CSP остаётся `script-src 'self'`. Telegram возвращает подписанный профиль во фрагменте `#tgAuthResult`, страница отправляет его в `POST /api/auth/telegram` и стирает из адресной строки. Сервер проверяет HMAC-SHA256 (ключ — SHA-256 токена бота) и возраст данных не больше часа, лимит — корзина `login` по IP.

Пользователь Supabase создаётся через Admin API с подтверждённым адресом-заглушкой `tg<id>@telegram.intgetion.com` и метаданными условий (продолжая через Telegram, человек принимает условия — строка под кнопкой). Сессия открывается одноразовым токеном `generate_link` (`magiclink`) и `verifyOtp` на сервере; письмо при этом не уходит. `getAuthUserEmail` для адресов-заглушек возвращает null, поэтому уведомления таким пользователям по почте не идут, пока нет настоящего адреса. Привязка Telegram к уже существующему аккаунту с почтой — позже; сейчас это отдельный аккаунт.

Кнопка активна только при `TELEGRAM_BOT_TOKEN` и `SUPABASE_SERVICE_ROLE_KEY`, иначе остаётся заглушкой «Скоро». У бота в @BotFather нужен `/setdomain` на домен сайта; локально (localhost) Telegram вход не отдаёт, проверка — на проде или preview с доменом.

## D218 — базовая защита от парсинга (первая часть P-SCRAPE)

Сайт открыт, поэтому первая часть P-SCRAPE (docs/PLANS.md) идёт сразу. Страницы людям и поисковикам по-прежнему доступны без ограничений (D210–D211).

- `robots.txt`: краулерам SEO-сервисов (AhrefsBot, SemrushBot, MJ12bot, DotBot, BLEXBot, DataForSeoBot, serpstatbot, Barkrowler, PetalBot) запрещён весь сайт. Поисковики не в списке. - JSON-API каталога (`GET /api/jobs`, `GET /api/jobs/:id`) для гостя — 120 запросов в минуту на IP (корзина `publicApi`, D26). Наш фронтенд эти маршруты для гостя не вызывает: каталог и страница вакансии рендерятся на сервере. Ответы из кэша CDN (`s-maxage=30`) лимит не тратят. Вошедшие не ограничены. - Лимиты на HTML-страницы каталога — не в приложении: счётчик в БД на каждый просмотр страницы добавил бы запрос к базе на каждый показ. Это правило Vercel Firewall (rate limit по IP на `/*/jobs*`), включается в панели Vercel.

## D185 — когда приходит дайджест (9B)

Cron `/api/cron/digest` раз в час (в `:00` UTC). Кандидату дайджест положен, когда по его часовому поясу из профиля сейчас час 08:00–08:59 (`isDigestDue`, смещение через `src/lib/tz.ts`). Ежечасный запуск в `:00` попадает в этот час для любого пояса, включая +5:30 и +5:45. Без часового пояса и у неактивных пользователей дайджеста нет. После первого дайджеста следующий — не раньше утра, до которого прошло 24 часа (`nextDigestAt`, D101): день перехода на летнее время может сдвинуть дайджест на сутки, но не сократить интервал.

## D186 — что попадает в дайджест (9B)

Вакансии из той же ленты, что «Подходящие» (`loadMatchScreen`, вкладка «Все»): без отклонённых «не подходит» и без скрытых компаний — фильтры 6B не дублируются. Порог score ≥ 0.65 (`DIGEST_MIN_SCORE`), не больше 5, по убыванию score.

## D187 — только новое и не чаще раза в сутки (9B)

«Новое» — вакансия опубликована позже прошлого дайджеста; для первого дайджеста — за последние 7 дней. Новых нет — ничего не шлём и `last_digest_at` не трогаем: дайджест придёт, когда новое появится, в ближайшее утро. Отправка начинается с захвата слота: `update candidate_profiles set last_digest_at = now where last_digest_at is null or < now − 20 ч` в одной транзакции с записью уведомления и письма. Повторный или параллельный запуск cron слот не получает — второго дайджеста нет.

## D188 — каналы (9B)

Уведомление в приложении (`matches.digest`, payload 9A: число и до 5 id) и письмо — по настройкам 9A. Письмо не отправляется напрямую: оно встаёт в очередь `notification_emails`, его рендерит, шлёт, повторяет и пропускает диспетчер 9A — в том числе адреса-заглушки Telegram-аккаунтов (D217). Текст письма — шаблон каталога с перечнем «вакансия — компания» и кнопкой «Открыть подборку» на `/{locale}/matches` в оболочке `siteEmailHtml`, которая экранирует текст. В чат бота — `system_event` в последнюю беседу пользователя через `postSystemEvent` модуля бота, без вызова модели; ошибка этой заметки дайджест не отменяет.

## D219 — согласие на куки по категориям (P-COOKIES, первая часть)

Расширяет D201. Необходимые куки (вход, язык, сессия агента, сам выбор) включены всегда. Дополнительные — две категории: «предпочтения» и «аналитика»; маркетинговых нет и не будет. Выбор категорий записывается как `necessary`, `all` или разрешённые категории через `+` (`preferences`, `analytics`); формат куки — в D220. Любой необязательный код проверяет `consentAllows(consent, category)`.

Баннер: три кнопки одного веса — «Только необходимые», «Принять все», «Настроить»; «Настроить» раскрывает два флажка (по умолчанию выключены) и «Сохранить выбор». Текст баннера — одна короткая строка (D201, LCP). В `/settings/privacy` — три строки: необходимые (всегда, неактивна) и два переключателя, применяются сразу.

Отзыв удаляет собранное: у каждой категории список своих кук (`OPTIONAL_COOKIES`), `writeConsent` удаляет куки отозванных категорий. Сейчас:

- «предпочтения» — кука `last_catalog_query` (30 дней, ≤ 1000 символов): каталог запоминает последние фильтры и при заходе без фильтров предлагает ссылку «Вернуть последние фильтры». Без согласия каталог ничего не читает и не пишет. Последние просмотренные вакансии и перенос в подбор после регистрации — позже.
- «аналитика» — категория есть, сбора нет. Своя аналитика (события в своей БД или self-hosted Plausible/Umami) появится отдельной подфазой и будет включаться только этой категорией.

## D220 — версия политики, журнал согласий, GPC и выбор на новом устройстве

Дополняет D219.

- **Версия политики.** Кука `cookie_consent` = `<выбор>~<версия политики>~<id записи>`, версия — `CONSENT_POLICY_VERSION` в `src/lib/consent.ts` (сейчас `2026-10-05`). Выбор под другой версией и значения до D220 считаются отсутствующими: баннер спрашивает снова. Поэтому после выкладки баннер один раз увидят и те, кто уже выбирал по D201 — их выбор касался других категорий.
- **Журнал согласий** (GDPR, ст. 7 — согласие нужно уметь доказать). Каждый выбор в баннере и в настройках — строка `consent_records` (миграция `0021`): id (тот же, что в куке), пользователь (если вошёл; при удалении аккаунта — null), выбор, версия политики, сигнал GPC, источник, хеш IP (`privacyHash`). User-Agent и сам IP не храним. `POST /api/consent`, лимит 30 в час на IP, повторный id игнорируется. Строки старше 3 лет удаляет `/api/cron/retention`. Свои записи пользователь получает в экспорте данных (`cookieConsents`).
- **Global Privacy Control.** Заголовок `Sec-GPC: 1` и `navigator.globalPrivacyControl` — постоянное «нет» аналитике: флажок «Аналитика» выключен и неактивен с пояснением, «Принять все» сохраняет аналитику выключенной, в журнал пишется уже применённый выбор. На «предпочтения» GPC не влияет.
- **Новое устройство.** Если куки нет, баннер сначала спрашивает `GET /api/consent`: для вошедшего это последняя запись журнала под текущей версией политики. Нашлась — она ставится в куку без новой записи и баннер не показывается; нет — баннер. Гостю запрос отвечает без обращения к Supabase Auth: без куки `sb-…-auth-token` пользователя не ищем (proxy не ставит метку сессии на `/api/*`), с ней решает `getCurrentUser`.

## D225 — своя аналитика без кук для всех

Без Google Analytics и сторонних скриптов. Каждая страница шлёт один `POST /api/a` (`navigator.sendBeacon`, запасной путь — `fetch keepalive`) с путём, query и — только на первой странице визита — `document.referrer`. Сервер сам выводит из этого события `page_view`, `job_view` (путь `/{locale}/jobs/{id}`), `search` (каталог или страница тега с `q` или фильтрами: запрос в нижнем регистре до 60 символов, фильтры — только названия). `signup` и `apply` пишут маршруты регистрации и отклика после успеха; ошибка записи не ломает запрос. Боты, превью ссылок, headless-браузеры и скрипты отбрасываются по User-Agent. Больше 600 сигналов в час с одного IP молча отбрасываются (корзина `beacon`), чтобы скрипт не засыпал таблицу.

Уникальный посетитель за день — `day_visitor` = HMAC(`PRIVACY_HASH_SECRET`, день + IP + User-Agent), 32 hex. Его нельзя развернуть и нельзя связать между днями; IP и User-Agent не хранятся, хранится только класс устройства (телефон / планшет / компьютер), хост внешнего реферера и `utm_*`. Такой подсчёт не ставит кук и не требует согласия; GPC его не отключает — это не продажа и не передача данных.

## D226 — кука аналитики `_ia` только с согласием

С согласием на «аналитику» (D219) и без GPC (D220) браузер ставит `_ia` — случайный UUID на 13 месяцев (максимум, который допускает CNIL). Сервер пишет его в `visitor_id`, только если кука согласия под текущей версией политики разрешает аналитику и запрос без `Sec-GPC: 1`; иначе `_ia` игнорируется. Это даёт вернувшихся посетителей и воронку через несколько визитов. При отзыве согласия браузер вызывает `POST /api/a/forget` с этим id, и события теряют `visitor_id`, а кука удаляется. Пользователь (`user_id`) с событиями не связывается никогда.

## D227 — отчёт и срок хранения

`/admin/metrics` — блок «Посетители за 30 дней»: посетители, просмотры, посетители с согласием, вернувшиеся; воронка «зашли → искали → открыли вакансию → зарегистрировались → откликнулись» за день (по `day_visitor`, все) и через визиты (по `visitor_id`, только с согласием); по дням; популярные страницы, запросы, вакансии, источники (`utm_source`, иначе хост реферера, иначе «прямой заход»), устройства. Полосы — нативный `<progress>`: инлайн-стили запрещает CSP. События старше 395 дней удаляет `/api/cron/retention`.

## D228 — «Вы смотрели»

С согласием на «предпочтения» страница вакансии кладёт её id в куку `recent_jobs` (до 6 id, новые первыми, 30 дней). Каталог без фильтров показывает над результатами «Вы смотрели»: названия и компании этих вакансий, только опубликованные. Без согласия кука не пишется и не читается; отзыв согласия её удаляет (`OPTIONAL_COOKIES`).

## D229 — настройки прода в админке

`/admin/metrics` — таблица «Настройки прода»: подключение к базе (режим пулера по порту: `session:5432` помечается «проверить» — с ним кончаются соединения, `EMAXCONNSESSION`), адрес сайта, админ-ключ Supabase, почта Resend (ключ и отправитель), вход через Telegram (токен и его формат), модель агента (провайдер), секреты сервера, Sentry. Показываются только «задано / проверить / не задано» и безопасные подробности (режим, порт, имя провайдера, адрес сайта) — значения ключей не выходят с сервера.

## D230 — Telegram привязан к аккаунту, а не к адресу

Связь «Telegram-id → пользователь» хранится в `telegram_accounts` (миграция `0023`: telegram_id PK, user_id UNIQUE, username, linked_at). Вход через Telegram сначала ищет эту связь и открывает сессию для текущей почты аккаунта (`getAuthUserLoginEmail` + одноразовый токен), какой бы она ни была. Нет связи — как в D217: аккаунт с адресом-заглушкой, затем запись связи; так же связь получают аккаунты, созданные до D230, при следующем входе. Один Telegram — один аккаунт и наоборот: привязать занятый Telegram — 409 «Этот Telegram уже привязан к другому аккаунту».

В `/settings/account` блок «Способы входа»: почта и Telegram. «Привязать Telegram» ведёт на `oauth.telegram.org` с возвратом на `/{locale}/auth/telegram?link=1`; страница возврата шлёт `mode: "link"` и возвращает в настройки. «Отвязать» работает, только если у аккаунта есть настоящая почта, иначе 409 — нельзя остаться без способа входа. Удаление аккаунта удаляет связь (`anonymizeUser`).

## D231 — почта для Telegram-аккаунта

Аккаунт с адресом-заглушкой добавляет почту в «Способах входа»: `POST /api/me/email` (лимит `emailLink`) отправляет через Resend письмо со ссылкой на `/{locale}/settings/email/confirm?token=…`, токен — HMAC (`PRIVACY_HASH_SECRET`, назначение `email-add`, 24 часа, `src/lib/signed-token.ts`). Пока ссылку не открыли, ничего не меняется. Ссылка открывает страницу с кнопкой «Подтвердить почту», и только `POST /api/me/email/confirm` по нажатию меняет адрес: почтовые сканеры (Outlook Safe Links и т. п.) сами открывают ссылки из писем и не должны подтверждать за человека. По кнопке Admin API ставит почту как подтверждённую; занята другим аккаунтом — «Эта почта уже принадлежит другому аккаунту. Войдите в него и привяжите Telegram там» (слияние аккаунтов не делаем). После этого по почте можно входить (ссылка или сброс пароля), уведомления и дайджест доходят, а Telegram продолжает входить в тот же аккаунт через `telegram_accounts`. Без Resend — 503 «Почта сейчас недоступна».

## D232 — статистика вакансии для работодателя

Третья вкладка вакансии в кабинете — «Статистика» (`/employer/jobs/{id}/stats`, только участникам компании-владельца, иначе 404): просмотры и посетители за 30 дней (события `job_view` своей аналитики, D225), откликнувшиеся из посетителей, просмотры по дням, источники (`utm_source`, иначе хост реферера), устройства и отклики по статусам. Работодателю уходят только суммы — ни ключей посетителей, ни времени отдельных визитов. Просмотры считаются для всех посетителей без кук, поэтому цифры полные независимо от согласий.

## D233 — сохранённые поиски

Вошедший пользователь с активными фильтрами каталога видит «Сохранить поиск». Хранится строка запроса (`saved_searches`, миграция `0024`) без курсора и сортировки, параметры по алфавиту — один и тот же поиск даёт одну строку; повторное сохранение только переименовывает. Название — подписи активных чипов фильтров (до 80 символов). Не больше 10 поисков на человека (409 и подсказка удалить старый). Список — `/{locale}/saved-searches` (ссылка со страницы «Сохранённые» и из сообщения после сохранения): открыть поиск, оповещение вкл/выкл, удалить. Страница закрыта в `robots.txt`.

## D234 — оповещения по сохранённым поискам

`/api/cron/search-alerts` раз в день в 07:00 UTC. Для каждого поиска с включённым оповещением — каталог тем же запросом (сортировка «новые», опубликованные за 30 дней, со скрытыми пользователем вакансиями и компаниями, как он видит каталог), из них — опубликованные после прошлого оповещения (или после сохранения поиска), до 10. Пусто — ничего не шлём и не отмечаем. Иначе в одной транзакции: захват слота (`last_alert_at`, не чаще раза в 20 часов) и доставка через `deliverInTransaction` — уведомление в приложении и письмо в очереди 9A по настройкам пользователя. Новый тип уведомления `search.alert` (вне таблицы раздела 15, письмо по умолчанию включено, отписка — как у остальных). Письмо — «По сохранённому поиску «…» появились N новых вакансий: вакансия — компания, …» и кнопка «Открыть поиск» на каталог с этим запросом.

## D235 — общий способ доставки по расписанию

`deliverInTransaction(tx, …)` в модуле уведомлений — одна запись уведомления и одно письмо в очереди в транзакции вызывающего, по настройкам пользователя. Им пользуются оповещения о поисках; дайджест 9B делает то же самое у себя и переедет на эту функцию при следующей правке.

## D236 — Telegram как канал уведомлений

Третий канал рядом с «в приложении» и «почтой»: `notification_channel` получает значение `telegram` (миграция `0025`). Умолчание как у почты (`emailDefault` типа), пользователь меняет его в «Настройки → Уведомления»; переключатели Telegram видны, только если к аккаунту привязан Telegram (D230). Webhook и `/start` не нужны: при входе и привязке через Telegram человек уже разрешает боту писать (`request_access=write`).

## D237 — рассылка в Telegram

`/api/cron/telegram` каждые 5 минут. Берёт уведомления в приложении не старше суток у активных пользователей с привязанным Telegram и отмечает каждое `telegram_checked_at` (захват `for update skip locked`) — отправлено или нет, повторно не берётся. Если канал `telegram` этого типа выключен — пропуск. Текст — заголовок и текст уведомления из каталога 9A на языке пользователя и ссылка на страницу, к которой оно относится (отклики, подборка, сохранённые поиски и т. п.), без разметки. Не отправилось — не повторяем; 403 (бот заблокирован) пишется в лог. Без `TELEGRAM_BOT_TOKEN` маршрут отвечает `disabled`. Поэтому все события — отклики, взаимный интерес, дайджест 9B, оповещения по поискам — доходят в Telegram без правок в местах, где уведомления создаются; если человек выключил уведомления в приложении для типа, в Telegram этот тип тоже не придёт.

## D238 — что дальше по Telegram

Пока бот только пишет. Команды (`/stop`, «показать подборку») и ответы на сообщения — через webhook, когда понадобится; тогда же `TELEGRAM_WEBHOOK_SECRET` для проверки входящих запросов.

## D239 — подписка на компанию

Кнопка «Следить» на странице компании (гостя ведёт на вход), повторное нажатие — «Не следить». `company_follows` (миграция `0026`: пользователь, компания, last_alert_at). Не больше 50 компаний на человека. Список — на странице «Сохранённые поиски и компании» (`/saved-searches`) с «Не следить». Работодатель видит число подписчиков компании (только активные пользователи) во вкладке «Статистика» вакансии (D232) — без имён.

## D240 — оповещения о новых вакансиях компании

Тот же ежедневный cron, что оповещения по поискам (`/api/cron/search-alerts`, 07:00 UTC). Для каждой подписки — опубликованные вакансии компании после прошлого оповещения (или после подписки), со скрытыми пользователем вакансиями, до 10; пусто — ничего. Иначе в одной транзакции захват слота и `deliverInTransaction`: уведомление `company.new_jobs` (вне таблицы раздела 15, письмо по умолчанию включено) — в приложении, письмом и в Telegram (D237) по настройкам. Кнопка письма и ссылка в Telegram ведут на вкладку вакансий компании (`notificationPath`, общий для письма и Telegram).

## D241 — пользовательское соглашение и политика конфиденциальности на сайте

Тексты — `docs/content/legal-terms.md` и `docs/content/legal-privacy.md` (русский и английский в одном файле, разделитель `<!-- en -->`): их правят основатель и юрист. `pnpm legal:sync` переносит их в `src/content/legal/legal.json`, который рендерят `/{locale}/terms` и `/{locale}/privacy`; unit-тест падает, пока файлы расходятся. Рендер — свой разбор узкого подмножества Markdown (заголовки, списки, абзацы, таблицы, жирный, ссылки) в React-элементы, без HTML. Юридические данные, которые знает только основатель (юрлицо, адрес, право и суд, почты, срок бэкапов, условия поставщика ИИ), — поля `{{…}}` из `LEGAL_DETAILS` в `src/config/legal.ts`; пока поле пустое, на странице «уточняется». Политика описывает фактическую обработку на 2026-10-05: регион базы — ЕС (Франкфурт), таблица всех кук со сроками, подрядчики, сроки хранения, права и где их реализовать в интерфейсе.

Связки: в подвале «Пользовательское соглашение · Политика конфиденциальности · Настройки куки»; в баннере куки ссылка «Подробнее» на раздел о куках; на странице политики под текстом — тот же блок выбора кук, что в настройках, и для гостей; в форме регистрации и под кнопкой Telegram — ссылки на оба документа. `TERMS_VERSION` → `2026-10-05`: новые регистрации принимают эти тексты; повторное принятие для существующих пользователей — по `docs/ADMIN.md` раздел 7, когда тексты станут окончательными.

## D242 — похожие вакансии

Под вакансией — до 4 опубликованных вакансий той же категории: сначала с главным (первым) навыком вакансии, затем добор по одной категории; сама вакансия и скрытые пользователем вакансии и компании исключены (тот же поиск каталога, что и `/jobs`). Нет похожих — блока нет.

## D243 — поделиться вакансией

Кнопки «Telegram», «LinkedIn», «Скопировать ссылку» и «Ещё» (системное меню телефона, `navigator.share`, только где оно есть) — обычные ссылки на страницы шаринга сетей, без сторонних скриптов и кнопок-виджетов, которые следили бы за посетителями. Ссылка получает `utm_source=share&utm_medium=<канал>`, поэтому в своей аналитике (D227) и в статистике вакансии работодателя (D232) видно, откуда пришли по ней. На телефоне блок стоит под описанием, на компьютере — в боковой колонке.

## D244 — сайт как приложение (PWA)

`src/app/manifest.ts` (`/manifest.webmanifest`): название, `display: standalone`, чёрная тема, иконки 192 и 512 px и маскируемая 512 px (сгенерированы из `icon.svg`, `public/icons/`), `apple-icon.png` 180 px для iPhone, ярлыки «Вакансии · Подходящие · Отклики»; `start_url` помечен `utm_source=pwa`, поэтому установки видны в своей аналитике. Service worker `public/sw.js` нарочно минимальный: страницы и ответы API не кэшируются (в них личные данные и они быстро меняются); кэшируются только офлайн-страница и иконка, и при пропаже сети вместо ошибки браузера показывается `public/offline.html` (без скриптов, стили — отдельным файлом, CSP не нарушается). Регистрируется только в продакшене. Push-уведомления — позже, отдельным решением.

## D245 — нижнее меню кандидата на телефоне

У вошедшего кандидата (есть профиль) на экранах уже `md` внизу панель из пяти разделов: Вакансии · Подходящие · Отклики · Агент · Профиль, с иконками и отметкой текущего раздела, с отступом под «чёлку» iPhone. На странице вакансии панели нет — там своя нижняя панель отклика. `body` получает нижний отступ, только когда панель есть (`has-[[data-bottom-nav]]`), чтобы она ничего не закрывала. Гостям и работодателям без профиля кандидата — обычное меню.

## D246 — вход через Telegram заморожен

По решению основателя вход через Telegram переделывается (Cursor). Вариант D217/D230 (виджет `oauth.telegram.org`) остаётся в коде, но выключен флагом `TELEGRAM_LOGIN_ENABLED` (по умолчанию выключен): на `/login` и `/register` кнопка Telegram — заглушка «Скоро», в «Способах входа» нет «Привязать Telegram», `POST /api/auth/telegram` отвечает 503 `TELEGRAM_DISABLED` в обоих режимах. ## D275 — направление курса валют и валюты без копеек

`fx_rates.rate_to_usd` — **сколько долларов стоит одна единица валюты** (1 EUR = 1.1204 USD → `1.12040000`). Так его и читает `convertToUsd` в `src/lib/money.ts` (умножение), и так было написано в тестах; `refreshFxRates` считал наоборот (`per_eur(X) / per_eur(USD)`, то есть единиц валюты за доллар), из-за чего 1 000 EUR превращались в 860 USD, а 500 000 JPY — в миллионы. Исправлено на `per_eur(USD) / per_eur(X)` с округлением до 8 знаков; комментарий к `FxRate` приведён в соответствие.

Минорные единицы разных валют не равны: у JPY и KRW их нет, у BHD их тысяча. Перевод между валютами теперь сдвигает сумму на разницу показателей (`currencyExponent`, из `Intl.NumberFormat`; неизвестный код — 2 знака). Раньше 500 000 JPY сравнивались как 5 000 USD.

Две почасовые вилки в разных валютах раньше сравнивались вообще без перевода (50 USD/час против 5 000 JPY/час как 50 против 5 000). Теперь почасовые остаются почасовыми, но проходят тот же перевод в доллары; одна почасовая против месячной по-прежнему несравнима (D5).

Проверка: интеграционный тест `src/modules/jobs/__tests__/fx-rates.integration.test.ts` скармливает `refreshFxRates` настоящий ответ ЕЦБ, читает записанные курсы из базы и прогоняет их через `compareSalaries`.

## D256 — вход через Telegram ботом

Виджет `oauth.telegram.org` (D217) требовал номер телефона и ломался на мобильных, поэтому заморожен (D246). Новый вход идёт через самого бота:

1. «Войти через Telegram» → `POST /api/auth/telegram/start`: сервер делает одноразовый код (24 случайных байта), кладёт его в httpOnly-куку `tg_login` на 10 минут, а в базу — только `sha256` этого кода, и возвращает ссылку `https://t.me/<бот>?start=login_<код>`.
2. Человек открывает бота и жмёт «Войти» под сообщением. Приходит `callback_query` на вебхук, строка отмечается подтверждённой вместе с Telegram-профилем.
3. Страница тем временем опрашивает `POST /api/auth/telegram/pending` раз в 2 секунды; как только строка подтверждена — `signInWithTelegramProfile` открывает сессию Supabase по тому же placeholder-адресу, что и раньше (`tg<id>@…`), и строка удаляется вместе с кукой.

В базе нет ничего, чем можно войти: код есть только у браузера (кука) и у Telegram (ссылка), в базе — его хеш. Повторное нажатие ничего не меняет (`confirmed_at` ставится один раз, `WHERE confirmed_at IS NULL AND expires_at > now()`), просроченная строка не подтверждается. Чужой или выдуманный код получает тот же ответ, что неизвестный, — без кнопки.

Вебхук `POST /api/telegram/webhook` доверяет только заголовку `X-Telegram-Bot-Api-Secret-Token`; секрет выводится из токена бота (`sha256("tg-webhook:" + токен)`), поэтому отдельной переменной не нужно. Нет токена — маршрут отвечает 404. `setWebhook` вызывается лениво при первом входе и кешируется на время жизни процесса.

Миграция `0028_telegram_login.sql` (таблица `telegram_login_challenges`) идемпотентна: в облачной базе эта таблица уже была создана вручную во время разработки.

## D259 — вход в мини-аппе Telegram

Когда сайт открыт как Telegram Mini App, Telegram кладёт подписанные данные о человеке в адрес страницы (`#tgWebAppData`). Клиентский компонент читает их прямо из адреса и отдаёт на `POST /api/auth/telegram/miniapp`; сервер проверяет подпись (HMAC-SHA256 токена бота под ключом `WebAppData`) и возраст (тот же час, что у виджета) и открывает сессию тем же `signInWithTelegramProfile`, что и бот (D256). Человек не нажимает ничего.

Скрипт Telegram (`telegram-web-app.js`) не подключается: данные берутся из адреса, поэтому CSP не ослабляется ради чужого скрипта. После входа подписанная строка стирается из адреса (`history.replaceState`) — это ключ на час, ему нечего делать в истории браузера.

Флаг `TELEGRAM_MINI_APP_ENABLED` выключен по умолчанию, потому что включение меняет защиту от встраивания: в Telegram Web мини-апп показывается во фрейме, поэтому `frame-ancestors` начинает пускать `web.telegram.org` и `*.telegram.org`, а жёсткий `X-Frame-Options: DENY` перестаёт выставляться (его заменяет CSP). На хосте админки фрейм не разрешается никогда (D251). Остальные правила CSP не меняются.

Включать после того, как мини-апп заведён в BotFather: `/newapp` у бота, адрес — `https://intgetion.com`, затем `TELEGRAM_MINI_APP_ENABLED=true` в Vercel.

## D311 — агент отвечает в Telegram-боте

Бот умел только подтверждать вход: любое другое сообщение он молча терял. Теперь вебхук сначала пробует шаг входа (`handleTelegramWebhook` возвращает, взял ли он обновление), а всё остальное уходит агенту — тому же, что и на сайте, с теми же инструментами и теми же лимитами.

Разговор чата выводится из его id: `HMAC(PRIVACY_HASH_SECRET, "tg:<chat>")` даёт тот же токен сессии при каждом сообщении, поэтому нить помнится без отдельной таблицы и без миграции, а id чата по токену не угадать. `/reset` подмешивает время и начинает новую нить.

Если агент просит подтверждение на запись (отклик, правка профиля), бот не изображает карточку подтверждения, а зовёт на сайт: согласие на действие должно быть явным там, где видно, что именно подтверждают.

Гость без привязанного аккаунта тоже может спрашивать — ровно как гость на сайте. Лимиты для него считаются по ключу `tg:<chat>` вместо адреса.

## D313 — вебхук Telegram и правило CSRF

Проверка CSRF (раздел 6, P12) отклоняет любой изменяющий запрос без заголовка `Origin`. Серверы Telegram шлют вебхук вообще без `Origin`, поэтому прокси отвечал `403 FORBIDDEN` раньше, чем маршрут успевал проверить секрет: на проде `POST /api/telegram/webhook` возвращал «Cross-origin request». Значит бот не работал совсем — ни подтверждение входа (D256), ни агент (D311).

`/api/telegram/webhook` выведен из-под проверки `Origin` (`needsOriginCheck` в `src/lib/origin.ts`). Это не ослабляет защиту: маршрут по-прежнему требует точного совпадения `x-telegram-bot-api-secret-token`, секрет выводится из токена бота, а без токена маршрут отвечает 404. Исключение — ровно один путь, подпути под него не попадают.

Почему так, а не «разрешить запросы без Origin для всех вебхуков»: правило без Origin защищает формы и API от межсайтовых запросов, и ослаблять его целиком ради одного внешнего отправителя нельзя. Список исключений проверяется тестом, а e2e теперь шлёт вебхуку запрос без `Origin` и требует не-403 — если кто-то вернёт правило назад, CI это поймает.

## D314 — сессия переживает окно, вкладку и перезапуск

«Остаться в системе» для человека значит: закрыл браузер, вернулся — всё ещё внутри. Поэтому куки сессии пишутся с явными правилами (`authCookieOptions` в `src/lib/supabase/cookie-options.ts`) и одинаково в обоих местах, где они появляются: в серверном клиенте и в обновлении сессии в прокси. Срок — 400 дней, это максимум, который браузер вообще хранит; заканчивают сессию только выход или отказ Supabase обновлять токен.

`httpOnly: true` — отличие от библиотечного умолчания. Supabase по умолчанию оставляет эти куки открытыми для скриптов, потому что обычно их читает браузерный клиент. Здесь браузерного клиента нет вовсе: все вызовы Supabase идут с сервера (страницы, маршруты, прокси). Значит токен можно закрыть — внедрённый скрипт больше не прочитает и не скопирует сессию.

`secure` выводится из адреса сайта: прод по https получает флаг, а прод-сборка по обычному http (CI, локальная разработка) без него продолжает получать куки обратно.

Обновление токена при этом работает как раньше: прокси зовёт Supabase перед отрисовкой, а тот сам обновляет истёкший токен по refresh-токену. Маршруты API в прокси не обновляются намеренно — они пишут куки сами, когда библиотека решит обновить.

Проверяется e2e, а не на слово: после входа проверяются срок и флаги каждой куки `sb-*`, затем вход переживает перезагрузку, переход, вторую вкладку и новый контекст браузера с теми же куками (перезапуск). Отдельный тест — что разговор гостя с агентом возвращается после перезагрузки.

## D315 — сессия внутри окна Mini App

Mini App на Telegram Web — это наш сайт в чужом фрейме. Браузер не сохранит там куку с `SameSite=Lax`: она просто отбрасывается. Значит, с включённым Mini App человек выглядел бы вышедшим при каждом открытии, сколько бы раз он ни входил.

В таком запросе сессия пишется иначе: `SameSite=None; Secure; Partitioned`. `Partitioned` (CHIPS) держит её в отдельной банке для каждого сайта-носителя, поэтому сессия в Telegram не смешивается с сессией на самом intgetion.com и не превращается в обычную стороннюю куку для слежки. Без https послабление не включается никогда: `None` без `Secure` браузеры всё равно отвергают.

Что считается «во фрейме»: документ сообщает об этом сам (`Sec-Fetch-Dest: iframe`), а запросы, которые страница делает потом, узнаются по метке `tg_frame` — её ставит маршрут входа в Mini App. Метка `HttpOnly` и живёт по тем же правилам, что и сессия.

Обычный сайт не затронут: там по-прежнему `SameSite=Lax`, то есть защита от межсайтовых запросов остаётся прежней.

## D316 — из Mini App в своё приложение, с тем же аккаунтом

Mini App живёт в чужом окне: его сессия не может перейти вместе с человеком в его собственный браузер, а именно там ставится PWA. Просить войти заново — значит потерять половину людей на ровном месте, поэтому Mini App отдаёт одноразовый адрес, который открывает тот же аккаунт снаружи.

Адрес — обычный переход по магической ссылке (`/{locale}/auth/callback?token_hash=…&type=magiclink`), тот же механизм, которым уже открывается сессия при входе через Telegram (D217, D256). Он одноразовый, живёт по расписанию Supabase и стоит ровно одной сессии. Новой таблицы и миграции не понадобилось.

Выдаётся он только вошедшему и только на его собственный аккаунт: маршрут `/api/auth/handoff` требует сессию, берёт почту входа этого самого пользователя и ограничен по частоте. В журнал и в историю адрес не попадает — страница переходит и чистит адресную строку.

Рядом с кнопкой — ссылка на привязку почты. Аккаунт из Telegram живёт с подставной почтой (D230), и пока настоящей нет, человек не восстановит доступ, если потеряет Telegram. Поэтому предложение стоит сразу, а не прячется в настройках.

Полоса показывается только вошедшему и только во фрейме: `TelegramMiniApp` молча открывает сессию, когда человек ещё не вошёл, а `MiniAppBar` появляется уже после входа. Первая версия ошибочно жила внутри `TelegramMiniApp`, который рендерится лишь для невошедших, — полоса исчезала бы ровно в тот момент, когда становится нужна.

## D317 — из Mini App в браузер, если окно не открылось

Кнопка «Открыть в браузере» вызывала `window.open` после `await fetch`. Для браузера это уже не нажатие, и он окно отбрасывает: на Telegram Web вкладка не появлялась бы никогда. Окно резервируется в обработчике нажатия, до запроса, и только потом получает одноразовый адрес.

Телефонный webview и приложения Telegram через `window.open` наружу не выходят: окно остаётся внутри Telegram, а одноразовая ссылка сгорает не в том браузере, где ставится приложение. Там окно не открывается. Если клиент сам отдал `Telegram.WebApp.openLink` (скрипт с telegram.org мы не грузим: его режет CSP), адрес уходит во внешний браузер через него. Иначе адрес показывается текстом, его можно выделить и скопировать. Чужой адрес, не наш `/auth/callback`, не открывается и не показывается.

Полоса остаётся в потоке страницы, под футером, и на узком экране получает нижний отступ `safe-area`, чтобы не залезать под панель вкладок и под домашнюю полоску. Кнопки на узком экране стоят столбиком на всю ширину. Рядом — одна строка, как поставить приложение: на iPhone «Поделиться» → «На экран Домой», в остальных браузерах пункт «Установить» в меню.

Подписанные данные для входа читаются из фрагмента адреса, как и раньше. Если фрагмент уже стёрт, а клиент оставил их на своём объекте, берётся эта копия. Внешний скрипт по-прежнему не подключается.
