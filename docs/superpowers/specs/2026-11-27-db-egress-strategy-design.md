# Стратегия экономии трафика Supabase: три потока выдачи вакансий

Дата: 2026-11-27. Статус: на согласовании у владельца.

## 1. Зачем

Бесплатный тариф Supabase даёт 5 ГБ исходящего трафика (egress) в месяц. За период 12.11–12.12.2026 израсходовано 70,6 ГБ, организация ограничена, вход на сайт отвечает 402.

Что уже известно:

- Импорт перечитывал и перезаписывал вакансии целиком. Исправлено в PR #58 (в проде с 25.11): пропуск неизменённых вакансий по md5 описания, лёгкие выборки, импорт раз в час.
- Основной оставшийся расход — публичное чтение вакансий: страница вакансии (~1 млн чтений с начала статистики) и списки каталога (~2,3 млн строк). Каждая строка шла целиком: описание (~6 КБ) и поле `fts` (~9 КБ), которое на страницах не используется. PR #59 убирает `fts` из публичных выборок и читает вакансию на странице один раз (не влит).
- По Vercel Firewall за сутки ~14 тыс. запросов, почти все — боты: Reflectionbot 4,2 тыс., Claude-SearchBot 3,5 тыс., vercel-cron 2,4 тыс., Applebot 2,1 тыс., meta-externalagent 1,3 тыс.
- На Vercel (Pro) израсходовано $8 из $20 за период — запас есть. Узкое место — Supabase.

Задача шире, чем борьба с ботами: сайт должен как можно реже ходить в Supabase за одними и теми же вакансиями и при этом показывать людям актуальную подходящую работу. Лимит — повод изменить схему выдачи.

**Одна база на всё.** Проект Supabase `hwcdscobnmxatmjbmect` (в PROJECTS.md назван dev) обслуживает и прод intgetion.com, и тесты, и локальные серверы агентов. Поэтому сейчас вход на проде не работает, а измерения 5.7 до разделения тестов смешивают прод и агентов.

**Цель по объёму.** Целимся в бесплатные 5 ГБ в месяц (около 150 МБ в день). Если после внедрения и измерений не укладываемся, решение о Pro принимается по цифрам. Работа считается законченной, когда измеренный расход по прод-потокам укладывается в цель или владелец выбрал Pro по измерениям.

## 2. Цели, не-цели, анти-цели

**Цели**

1. Разделить выдачу на три потока с разными данными, частотой обновления и ценой обращения к базе: гостевая подборка, полный каталог, личные рекомендации.
2. Повторные просмотры одних и тех же публичных данных не обращаются к Supabase.
3. Вакансии остаются доступными людям, поисковикам и ИИ-поиску.
4. Свежесть: новая вакансия — в каталоге сразу, в гостевой подборке в течение 10–15 минут; закрытая внутри INTGETION — пропадает из подборки и перестаёт предлагать отклик в течение 1–5 минут; импортированная, подтверждённо закрытая на источнике — в течение 24 часов.
5. Измерить расход Supabase по каждому потоку и по фоновым задачам; решения о блокировке ботов и тарифе Pro принимать по измерениям.

**Не-цели**

- Отдельное хранилище снимка (файл в Vercel Blob) на первом этапе.
- Переезд с Supabase на другой сервис.
- Полная переделка подбора — только проверка качества и стоимости и исправление слабых мест.

**Анти-цели (провал, даже если трафик упал)**

- Гостевая подборка ограничивает доступ к поиску работы.
- Закрытая вакансия продолжает предлагать отклик.
- ИИ получает от нас «подходящие вакансии», которых нет или которые закрыты.
- Личные данные попадают в общий кэш или в гостевую подборку.
- Ложное закрытие импортированной вакансии из-за ошибки или блокировки внешнего сайта.

## 3. Ограничения

- Next.js 16.3.8 на Vercel Pro. Кэш с метками в проекте сейчас не используется — это новое.
- В Next.js 16 обычный `revalidateTag` может сначала отдать устаревшие данные. Для закрытия нужен режим немедленного истечения, при котором следующий запрос ждёт свежие данные. Нужно убедиться, что ни страница, ни кнопка отклика не остаются в другом слое кэша.
- Кэш Vercel не бесплатен: чтения, обновления и вызовы функций учитываются в расходе Vercel. Измеряем обе стороны.
- `expire-jobs` запускается раз в час; срок окончания вакансии (`expires_at`) нужно учитывать прямо при выдаче.
- Импорт: раз в час обрабатывается один источник, самый давно не обновлявшийся; источников больше сорока, каждый перепроверяется примерно раз в 1,5–2 суток. Для импортированных вакансий нужна отдельная проверка (раздел 5.4).
- **Замороженные модули (решение владельца).** Правки делаются в репозитории модуля, которому принадлежит логика; затем отдельным PR новая версия подключается к платформе. Одну реализацию не копируем в обе стороны. В объёме: `intgetion-jobs` и `intgetion-ingestion` — публичная выдача и проверка источника; `intgetion-matching` — личные рекомендации. `mcp` меняем, только если существующий публичный поиск нельзя направить на готовую подборку. `feedback` остаётся личным слоем поверх страницы без изменений. `notifications` не трогаем. Код самой платформы (страницы `src/app`, кэш, `robots.txt`, `src/modules/seo`) не заморожен и правится в платформе.
- **Миграции (решение владельца).** Проектируются в ТЗ и проверяются локально; на облачную базу применяются только на этапе согласованного выпуска.
- Без push в `master`, без миграций на облачной базе и платных действий без явного «да» владельца.

## 4. Подходы

|                | Подход                                                                                                                                          | Плюсы                                                                                                   | Минусы                                                                                                |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **А (выбран)** | Кэш данных Next.js на Vercel с метками: гостевая подборка, страницы вакансий, частые поиски каталога. Немедленное истечение меток при закрытии. | Меньше нового кода; уже в Vercel Pro; данные вне Supabase; страницам и поиску кэш нужен в любом случае. | Снимок не виден как отдельный файл; внешние потребители читают его через тот же кэш.                  |
| Б              | Снимок-файл JSON в Vercel Blob, пересборка по расписанию и по событиям.                                                                         | Один явный снимок, его легко проверить и измерить.                                                      | Больше деталей (запись, пересборка, блокировки); страницы и поиск всё равно нужно кэшировать как в А. |
| В              | Edge Config.                                                                                                                                    | Очень быстрые чтения.                                                                                   | Малый размер и лимит частоты записи; при частых закрытиях упрётся в лимиты. Отброшен.                 |

Выбран А, потому что кэш для страниц и поиска нужен в любом случае, а метки с немедленным истечением закрывают требование «1–5 минут» без отдельного хранилища. Б можно добавить позже поверх А, если снимок понадобится внешним потребителям как файл.

## 5. Что решено

### 5.1. Гостевая подборка

- Отдельный небольшой набор опубликованных вакансий в кэше Vercel (не закэшированный ответ каталога).
- Показывается блоком на главной и первым экраном `/jobs`, пока человек не ввёл запрос и не выбрал фильтры.
- Его же читает публичный поиск для подключённого ИИ (5.5).
- Только поля для карточек: без личных и служебных данных.
- Не каждая новая вакансия обязана попасть в подборку, но в полный каталог она попадает сразу.
- Обновление: по расписанию (каждые 10–15 минут) и немедленное истечение при закрытии вакансии из подборки.
- При выдаче отсекаются вакансии с прошедшим `expires_at`, не дожидаясь `expire-jobs`.

### 5.2. Полный каталог и страницы вакансий

- Поиск, фильтры и следующие страницы — полный каталог с лёгкими выборками (без `fts`, PR #59) и кэшем для повторяющихся поисков.
- Страница вакансии: общая часть кэшируется с меткой `job:<id>`; личные блоки («сохранено», «почему подходит» и т. п.) подгружаются отдельно и только для вошедших.
- Закрытие вакансии (работодатель, модерация, импорт, истечение срока, проверка 5.4) немедленно истекает `job:<id>` и метку подборки. После закрытия страница не предлагает отклик.
- Гостевая подборка не ограничивает доступ к каталогу.

### 5.3. Личные рекомендации

- Отдельный поток для вошедших. Учитывает анкету, навыки, желаемую роль, зарплату, ограничения вакансии и действия человека (скрыл, сохранил, откликнулся), показывает причины подбора.
- Основа — существующий подбор (`src/modules/matching`, результаты в `matching_results`). Сначала проверить качество и стоимость пересчёта, затем исправить слабые места и лишнюю нагрузку.
- Результат хранится и пересчитывается по понятным поводам: изменилась анкета, появилась подходящая вакансия, изменились действия человека. Не при каждом открытии.

### 5.4. Проверка импортированных вакансий

- Цель: подтверждённо закрытую на источнике вакансию убрать не позже чем через 24 часа.
- Отдельная лёгкая фоновая проверка жизни вакансии у источника, обходящая все опубликованные импортированные вакансии за сутки.
- Закрытием считается только подтверждённый признак: источник явно сообщает, что вакансии нет, или она исчезла из его выдачи. Ошибка, тайм-аут или блокировка — не закрытие; вакансия остаётся и проверяется позже.
- Для каждой импортированной вакансии хранятся время и результат последней проверки (миграция в репозитории модуля-владельца, проверка локально).
- Подтверждённое закрытие меняет действующий статус вакансии и убирает её из публичной выдачи; затем — немедленное истечение кэша (как в 5.2): вакансия пропадает из подборки и из ответов ИИ, страница не предлагает отклик.
- Нажатие «Откликнуться» не ждёт проверки; человек сразу уходит на внешний сайт.
- **Не в первом выпуске:** фоновая проверка в первую очередь после нажатия «Откликнуться». Если ей нужна новая очередь, это отдельная часть миграции и отдельное улучшение.

### 5.5. Поиск через ИИ

- Публичные страницы вакансий понятны поисковикам и ИИ-поиску (разметка уже есть, `src/modules/seo`).
- Для подключённого ИИ — публичный поиск по опубликованным вакансиям через MCP (`src/modules/mcp`). Он читает подготовленные публичные данные (гостевую подборку и кэшированный каталог) и никогда не запускает личный подбор.
- Ответ должен позволять ИИ сказать «на INTGETION есть подходящие вакансии, вот ссылки» только когда найдены действующие вакансии; при пустом результате — явно сообщать, что подходящих нет.
- Личный подбор по анкете — только после входа или с отдельного разрешения человека (существующие OAuth-инструменты MCP).
- Успех измеряется появлением вакансий в ответах ИИ и переходами людей по ссылкам, а не конкретной фразой.

### 5.6. Политика для ботов (`robots.txt`)

Текущий прод (`src/modules/seo/site.ts`): общее правило пускает всех на публичные страницы и закрывает `/api/` и личные разделы; закрыты SEO-боты и GPTBot, ClaudeBot, anthropic-ai, Google-Extended, CCBot.

Изменения:

- Добавить в запрет как обучающих: `Reflectionbot`, `meta-externalagent`, `Applebot-Extended`.
- Оставить доступными через общее правило: Claude-SearchBot, OAI-SearchBot, PerplexityBot, Applebot, Meta-WebIndexer. Отдельные `Allow` не добавлять.
- `Google-Extended` пока оставить закрытым (обычный Google Search это не затрагивает). Решение владельца; пересмотреть, если понадобятся ИИ-продукты Google вне поиска.
- После запуска гостевого кэша проверить реальный `robots.txt`, доступность вакансий для поисковых ботов и расход Supabase.

### 5.7. Измерение

- Расход Supabase по потокам: гостевая подборка, каталог, страницы вакансий, рекомендации, MCP, каждая фоновая задача.
- Источники: `pg_stat_statements` (вызовы и строки по запросам) и дневной график Egress в Supabase Usage; для Vercel — Usage и Firewall Traffic.
- Процедура: `pnpm egress:report --save before.json` до выкладки (топ-20 запросов по `rows` с метками потоков: `job-page`, `catalog`, `company`, `live-state`, `import`, `matching`, `other`); через 24 часа `pnpm egress:report --diff before.json` показывает приращение за сутки по потокам. Рядом смотреть дневной график Egress в Supabase Usage. Критерий успеха — около 150 МБ в день. Команда читает `DATABASE_MIGRATION_URL` и только выбирает из `extensions.pg_stat_statements`.
- Ежедневная сводка (трафик за сутки и крупнейшие запросы) в Telegram владельцу. _Решение исполнителя._
- Решения о блокировке остальных ботов и о тарифе Pro — по измерениям после внедрения.

## 6. Решения исполнителя (предложены мной, не обсуждались — проверьте)

- **Этап 0, срочный:** до работы над тремя потоками — обновить `robots.txt` (5.6, код платформы) и снизить объём публичных выборок. PR #59 сделан прямо в замороженном `src/modules/jobs` платформы; по решению владельца о модулях его нужно перенести в `intgetion-jobs` и подключить к платформе отдельным PR, либо влить как срочное исключение — решает владелец.
- `billing`-cron каждую минуту перепроверяет отправленные оплаты (`recheckSubmittedOrders`); частота влияет на то, как быстро человек видит подтверждение оплаты. Частоту не меняем; вместо этого пустой запуск (нет ожидающих оплат) должен стоить один лёгкий запрос. `telegram` и `matching` — проверить так же.
- Тесты и локальные серверы агентов переводятся с облачной базы на локальную (`supabase start`) или отдельный проект.
- Начало описания (~300 символов) вместо полного текста в списках каталога и в гостевой подборке. Страница вакансии и её разметка для поисковиков (JobPosting) сохраняют полный текст.
- Вошедший пользователь на главной и первом экране `/jobs` видит тот же общий закэшированный блок, а над ним — свой блок рекомендаций, который подгружается отдельно из `matching_results`. Одна общая закэшированная страница плюс личная часть, без двух вариантов страницы.
- Личные рекомендации в этом проекте: проверка стоимости пересчёта и устранение лишней нагрузки. Улучшение качества подбора и причин — отдельный следующий проект с собственными критериями.
- Сводка расхода раз в сутки в Telegram.
