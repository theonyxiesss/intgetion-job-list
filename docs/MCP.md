# MCP-сервер INTGETION — предложение

Версия 2 от 2026-10-18. План согласован основателем, фаза 0 (решения) сделана. Фаза 1 реализована в ветке `claude/mcp-phase1` (не в master, не выложено); описание кода — [how-it-works/mcp.md](how-it-works/mcp.md). Каждая фаза ниже — отдельная подфаза по команде основателя (AGENTS.md, «одна подфаза»). Решения — D480–D486 в [DECISIONS.md](DECISIONS.md); D484–D486 уточняют D481 и D482. План в общем списке — P-MCP в [PLANS.md](PLANS.md).

## 1. Цель

Слова основателя (2026-10-17): платформа доступна не только через сайт и Spoki, но и через внешних ИИ-ассистентов (Claude, ChatGPT, Cursor и другие). Человек подключает INTGETION к своему ассистенту и прямо из чата получает информацию и делает действия в рамках выданных прав. Четыре направления: работа, биржа услуг, ИИ-сервисы, автоматизация. MCP работает поверх существующих сервисов, авторизации, данных и бизнес-логики, без дублирования. Spoki и внешние ассистенты пользуются одной экосистемой.

## 2. Что уже есть в коде

### 2.1 Общий реестр инструментов

`TOOLS` в `src/modules/bot/service/tools.ts` — 74 инструмента: 16 базовых, 14 на аккаунте (`account-tools.ts`), 1 письмо (`pitch.ts`), 3 напоминания (`reminders.ts`), 23 UGC (`src/modules/ugc/service/bot-tools.ts`), 17 фриланс (`src/modules/freelance/service/bot-tools.ts`).

У каждого инструмента есть:

- вход на zod;
- `access`: `guest` (кто угодно) или `user` (только вошедший);
- `confirm(ctx)`: нужна ли карточка подтверждения;
- `preview`: называет цель из базы до карточки, чужое — 404 без карточки (D472);
- `cardFields`: поля, которые человек вводит в карточку мимо модели (D460);
- `run(ctx, input)`.

`runTool` сам проверяет инструмент, вход, права и подтверждение. Подтверждение — hash аргументов, без него 422 `CONFIRMATION_REQUIRED` (D173, P8, P11). Модель не решает, кто что может. Контекст инструмента — `userId`, `conversationId`, `locale`, `state`. Поэтому MCP достаточно подставить `userId` из токена и вызвать тот же `runTool`.

### 2.2 Карточки подтверждения

Таблица `bot_confirmations`: `conversation_id` (обязателен), `tool`, `args`, `args_hash`, `expires_at` (10 минут, `CONFIRMATION_TTL_MS`). `confirmAction` выполняет ровно сохранённые аргументы один раз. Из Telegram карточка открывается на сайте по `/chat?confirm=<id>` (D460), а `POST /api/bot/confirm` принимает карточку из другой нити (`findConfirmationConversation`) — это готовый путь подтверждения вне ассистента. У `bot_conversations` есть поле `channel`, но проверка в базе разрешает только `web` (`bot_conversations_channel_check`, `0018_bot.sql:15`). Сами инструменты `conversationId` не читают, он нужен только карточкам.

### 2.3 Вход, лимиты, безопасность

- Вход: Supabase (почта, magic link, Google, X, Telegram), сеанс в cookie, `getCurrentUser` читает его через `auth.getUser()`. Вход Telegram открывает обычный сеанс Supabase (`signInWithTelegramProfile`). `userIdForAuthUid` и `userIdForTelegramId` в `src/modules/auth/service/index.ts` переводят внешний id во внутренний.
- `supabase/config.toml` (зеркало облака): `[auth.oauth_server] enabled = false`, `secure_password_change = false`, `jwt_expiry = 3600`.
- Лимиты записей уже внутри: `apply` в `applyToJob` (`apply-service.ts:92`), `freelanceRequest` в `send_service_request` (`freelance/service/bot-tools.ts:523`). Через MCP они действуют так же.
- zod-вход переводится в JSON Schema через `z.toJSONSchema` (`src/lib/llm/openrouter.ts:79`) — то же нужно для `inputSchema` MCP.
- `src/proxy.ts`: любой не-GET на `/api/*` без Origin нашего сайта получает 403 (CSRF, P12). Исключения — `SECRET_AUTHENTICATED` в `src/lib/origin.ts`.
- Лимиты: `rate_limit_counters`, правила в `src/lib/rate-limit.ts` (`publicApi` 120 в минуту, `apply` 30 в сутки, `freelanceRequest` 5 в час и другие).
- Короткие подписанные токены — `src/lib/signed-token.ts`. Аудит — `recordAudit` в `src/lib/audit.ts`. Хеш идентификаторов для логов — `privacyHash`.
- БД: роль `app_rw`, RLS deny-all на всех публичных таблицах.
- Пакета MCP в зависимостях нет.

### 2.4 Чего нет

- Описания инструментов написаны для Spoki («then call offer_step», `MEMORY`, `KNOWN PROFILE`). Внешнему ассистенту нужны свои описания.
- Инструменты `offer_step` и `focus_ugc` рисуют карточки в чате сайта. Вне сайта они не нужны.
- `search_jobs` подмешивает фильтры из черновика Spoki (`state.draft`); в MCP черновика нет.
- Атрибуции нет: Spoki получает вакансию по `JOB_LLM_FIELDS` без источника, события — без источника. Для MCP нужны оба (D484).
- Инструментов `get_company` и `list_job_categories` нет; есть функции `getPublicCompany` и `SKILL_CATEGORIES`.
- В облачной базе сейчас нет фриланс-услуг (MISSION_LOG, D479).

## 4. Архитектура

### 4.1 Где живёт

- Маршрут Next.js `src/app/api/mcp/route.ts` на Vercel. Адрес `https://intgetion.com/api/mcp`: без нового DNS и мимо локалей proxy.
- Транспорт Streamable HTTP, без состояния. Спецификация 2026-07-28 убрала сессии и `initialize`, каждый запрос самодостаточен. Это подходит serverless. Клиенты на 2025-11-25 ещё массовые: поддерживаем обе версии через официальный SDK.
- SDK: `@modelcontextprotocol/server` (2.3.1 на 2026-10-17), без `mcp-handler` (D486). Новая зависимость ставится в начале фазы 1 после «да» основателя (AGENTS.md, безопасная зона). Поддержку 2026-07-28 и 2025-11-25 проверяет первый шаг фазы 1.
- Метаданные защищённого ресурса (RFC 9728) — `/.well-known/oauth-protected-resource`, ссылка из `WWW-Authenticate` на 401 (фаза 2). Proxy пути с точкой не трогает (`matcher` в `src/proxy.ts`), Next 16 поддерживает маршруты `.well-known` (`node_modules/next/dist/docs/01-app/02-guides/backend-for-frontend.md`).

### 4.2 Один реестр, два канала

- Новый модуль `src/modules/mcp/`: адаптер протокола, проверка токена, гранты, журнал вызовов. В другие модули ходит только через `@/modules/bot/service` (index), как требует правило 6 AGENTS.md. Логики инструментов в нём нет.
- К `BotTool` добавляются метаданные канала: `channels` (`spoki`, `mcp`), `scope`, `mcp.title`, `mcp.description`, `annotations` (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`). Новый инструмент пишется один раз и включается в нужные каналы.
- `ToolContext` получает `channel` и `clientId`. Инструменты, которые читают `state` (черновик Spoki), в MCP получают пустое состояние.
- Ответ MCP: `structuredContent` и короткий текст. Тексты вакансий и услуг по-прежнему в `wrapUntrusted`. Вместо `offer_step` — ссылки на страницы сайта.
- Spoki получает те же новые инструменты. `pnpm eval` проверяет и описания Spoki, и описания MCP.

### 4.3 Авторизация

Выбран вариант B — свой слой OAuth 2.1 поверх существующих аккаунтов (D485). В фазе 1 входа нет: только публичные инструменты.

**Почему не Supabase OAuth 2.1 Server (вариант A).** Он выдаёт клиенту обычный JWT сессии Supabase. При `secure_password_change = false` таким токеном пароль меняется без повторного входа. Токен во внешнем клиенте — путь к захвату аккаунта. Ещё у A только стандартные scope (`openid`, `email`, `profile`, `phone`), и он в бете.

**Как устроен B (фаза 2):**

- Аккаунты те же, параллельной системы нет. Человек входит на сайте своим способом (почта, magic link, Google, X, Telegram), страница согласия `/oauth/consent` читает его сеанс через `getCurrentUser` и показывает клиента и запрошенные права.
- Код авторизации с PKCE (только S256), точное совпадение redirect URI, одноразовый короткий код, refresh с ротацией; повторное использование refresh отзывает всю цепочку.
- Токены непрозрачные, в БД только хеш (как сессия бота, D172). Годятся только для `/api/mcp`; cookie сеанса маршрут MCP не читает.
- Регистрация клиентов: Client ID Metadata Documents (основной путь в 2026-07-28; загрузка документа с защитой от SSRF) и DCR для совместимости (claude.ai, ChatGPT), с лимитом по IP. Регистрация сама прав не даёт.
- Метаданные: `/.well-known/oauth-protected-resource` и `/.well-known/oauth-authorization-server`.
- Личный токен из настроек для Cursor, Claude Code и клиентов с заголовком: хеш, показ один раз, scope, отзыв.
- Миграция фазы 2 (сейчас свободен `0060`): клиенты, коды, токены и `mcp` в `bot_conversations_channel_check`.
- Supabase Auth не меняется. Включить `secure_password_change` стоит ради самого сайта, отдельно от MCP и по отдельному «да» основателя.

**Права (scope):**

| Scope                     | Что открывает                                                  |
| ------------------------- | -------------------------------------------------------------- |
| без scope                 | публичные инструменты (раздел 5, фаза 1)                       |
| `profile:read`            | свой профиль, тариф и остаток, подбор                          |
| `applications:read`       | свои отклики                                                   |
| `applications:write`      | отклик и отзыв отклика                                         |
| `saved:write`             | сохранённые, скрытые, сохранённые поиски, оповещения, подписки |
| `freelance:read`          | свои заказы и услуги                                           |
| `freelance:write`         | запрос, ответ, шаги заказа, отзыв                              |
| `freelance:sell`          | свои услуги: создать, править                                  |
| `ugc:read` / `ugc:write`  | брифы, отклики, работы                                         |
| `reminders:write`         | напоминания                                                    |
| `memory:read` / `write`   | память Spoki (позже, отдельное решение)                        |
| `employer:read` / `write` | свои вакансии и отклики на них без контактов (позже)           |

Никогда через MCP: оплата, почта, пароль и способы входа, удаление аккаунта, админка, контакты до взаимного интереса.

### 4.4 Подтверждение действий

- Чтение — сразу.
- Обратимые мелочи, у которых в Spoki нет карточки (`save_job`, `hide_job`), — сразу, если выдан scope.
- Всё, у чего `confirm` вернул `true`: сервер создаёт строку `bot_confirmations` в нити канала `mcp` и отвечает ассистенту ссылкой на карточку на сайте. Где клиент умеет, ссылка идёт как URL-запрос (URL-elicitation в 2025-11-25, `input_required` в 2026-07-28), иначе текстом. Человек нажимает на сайте под своим входом, видит название цели из базы (`preview`). Ассистент узнаёт итог новым инструментом `get_action_status`.
- Ответу клиента «пользователь согласился» сервер не верит: хост может отвечать сам.
- Деньги не двигаются никогда: ассистент даёт ссылку на кассу.

### 4.5 Лимиты, аудит, данные

- Новые бакеты (D486): `mcpGuest` — 60 вызовов в минуту с одного IP (фаза 1), `mcpUser` — 600 в сутки на человека (фаза 2). Записи делят существующие бакеты (`apply`, `freelanceRequest`).
- Расхода LLM нет: думает модель ассистента. Лимиты Spoki на сообщения к MCP не относятся.
- Каждая запись — `recordAudit`. Журнал вызовов: инструмент, клиент, статус, время, без аргументов и персональных данных (`privacyHash`). В фазе 1 — строка лога на вызов (хеш IP), без таблицы.
- В настройках страница «Подключённые ассистенты»: клиент, права, последний вызов, «Отключить».
- Контакты кандидатов — никогда (D3). Описания — только в `get_job` и `get_service`, в списках нет (P-SCRAPE). Импортированные вакансии — только через `canSyndicateJob` (D484, D412): свои всегда, импорт — из `SYNDICATED_IMPORT_SOURCES` (сейчас Jobicy), с именем источника и ссылкой на оригинал. Закрытый источник не отдаётся и по id: только ссылка на нашу страницу. `republish_allowed` — разрешение импортировать вообще, не передачу третьим лицам. События — с указанием источника (MIT).

### 4.6 Proxy и заголовки

- `/api/mcp` попадает в proxy. Нужно исключение из проверки Origin: запрос без Origin проходит (серверные клиенты его не шлют), чужой браузерный Origin получает 403 — так спецификация MCP требует защищаться от DNS rebinding. Cookie сеанса маршрут не читает. Изменение делается в фазе 1 после «да» основателя («стоп и спроси» по скиллу безопасности).
- Маршрут отдаёт JSON и поток событий; CSP страниц не меняется.

### 6.1 Тесты по фазам

- **Фаза 1.** Unit:
  - список инструментов детерминирован и без пользовательских;
  - JSON Schema входа;
  - вакансия из закрытого источника не проходит ни в поиске, ни по id;
  - в ответах нет полей контактов;
  - у импорта и событий есть атрибуция;
  - правило Origin.

  Integration: вызов маршрута отдаёт результат поиска и 429 после лимита. `pnpm eval` зелёный (описания Spoki не тронуты).

- **Фаза 2:**
  - PKCE только S256, точный redirect URI;
  - одноразовый код, повтор refresh отзывает цепочку;
  - отзыв действует со следующего вызова;
  - без scope — 403, чужой id — 404;
  - в БД только хеши;
  - `/security-review`.
- **Фаза 3:**
  - без нажатия на сайте запись не выполняется (422);
  - подмена аргументов, просрочка (410), повтор и чужое подтверждение отклоняются;
  - e2e: вызов MCP → карточка на сайте → нажатие → `get_action_status`.
- **Фаза 4:** работодатель не получает контакты до интереса; исполнитель не видит чужие заказы.

Интеграционные тесты идут против облачной базы, общей с продакшеном: только читают или удаляют своё. Миграции и e2e — в CI.

### 6.2 Подключение клиентов

- Claude Code: `claude mcp add --transport http intgetion https://intgetion.com/api/mcp`.
- claude.ai: пользовательский коннектор по адресу.
- ChatGPT: режим разработчика, коннектор по адресу.
- Cursor: `mcp.json` с адресом.
- MCP Inspector — через `npx`, после «да» основателя.
- Каждый клиент проверяется на обеих версиях протокола, если клиент их различает.

## 7. Spoki

Spoki уже уточняет потребности (разговор вместо анкеты, D386), помнит факты (D469), действует на аккаунте с карточкой (D472), напоминает (D473), заступается за кандидата письмом (D475) и предлагает следующий шаг в UGC (D467). Предложение:

- Обобщить «следующий шаг» из `ugc-next.ts` (D467) на вакансии и фриланс: после отклика, после запроса исполнителю, при простое заказа Spoki сам предлагает одно действие строкой-шаблоном и карточкой.
- Один реестр и одни карточки: всё, что умеет внешний ассистент, умеет и Spoki, и наоборот.
- Память Spoki внешним ассистентам — только по отдельному scope и отдельному решению.
- Позже — подбор под задачу по всем направлениям сразу: вакансия, услуга исполнителя, управляемая команда `/services`, событие.

## 8. Риски

- Внедрение подсказок через тексты вакансий и услуг во внешний ассистент. Меры: `wrapUntrusted`, короткие ответы, записи только через карточку на сайте.
- Кража токена и «запутанный заместитель». Меры: хеш токена, scope, проверка аудитории, короткий срок, отзыв, журнал.
- Парсинг через публичный MCP. Меры: малый `limit`, без описаний в списках, лимит по IP, `canSyndicateJob` (D484).
- Быстрые изменения спецификации MCP (две версии за год). Меры: официальный SDK, поддержка двух версий, проверка в начале фазы 1.
- Ошибки в своём коде OAuth (фаза 2). Меры: тесты 6.1, ревью безопасности до выкладки.
- Мало данных: в MCP только свои вакансии и Jobicy, фриланс-услуг в базе пока нет. Первая версия честно отвечает «ничего не найдено» и даёт ссылку на сайт.
- Хост ассистента сам «подтверждает» действия. Мера: подтверждение только на сайте.
- Данные уходят к стороннему поставщику ИИ по выбору человека. Нужны строки в политике приватности на 7 языках (юрист).
- Одна облачная база и для localhost, и для продакшена: интеграционные тесты MCP только читают или удаляют своё.

## 9. Открытые вопросы основателю

Решено 2026-10-18 и больше не спрашивается: v1 — кандидаты и заказчики услуг, публичные инструменты без входа (D486); импорт — `canSyndicateJob` (D484); авторизация B с CIMD и DCR (D485); подтверждение только на сайте, срок карточки 10 минут; v1 бесплатна.

Открыто, фазу 1 не блокирует:

1. Нужна ли позже настройка «доверять этому ассистенту для X»?
2. «ИИ-сервисы» и «Автоматизация» — это категории фриланса, каталог инструментов (чей, откуда данные, партнёрские ссылки) или управляемые услуги `/services`? (D483)
3. Политика приватности и условия: кто пишет строки про внешних ассистентов (7 языков)? Нужно до фазы 2.
4. Публиковать ли сервер в каталогах (MCP Registry, каталоги Claude и ChatGPT)? Это внешняя публикация.
5. Включить ли `secure_password_change` в Supabase Auth ради самого сайта (вне MCP)?
