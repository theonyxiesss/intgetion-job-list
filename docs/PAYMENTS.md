# ТЗ: приём платежей — Stripe (карты), WalletConnect (USDC/USDT на кошелёк компании), заглушка

Порядок работ — [docs/tz/23-billing.md](tz/23-billing.md) (D351): сначала WalletConnect на один EVM-адрес компании, карты позже. Этот файл — как деньги проверяются.

Что продаём и почему — `docs/PRICING.md` (раздел 1A главный). Где это видно — `docs/PRICING_UX.md`. Здесь — **как деньги приходят, как это проверяется и что может пойти не так.**

Статус: задание, код не начат. Номера решений и миграции — следующие свободные на момент вливания (последний занятый номер решения — смотреть конец `docs/DECISIONS.md`, файл ведётся в порядке вливания).

---

## 0. Главные правила

1. **Сервер — единственный источник правды о деньгах.** Цена, тариф, сумма и статус никогда не берутся из браузера. Браузер говорит «хочу тариф X», сервер сам знает, сколько это стоит.
2. **Тариф включается только по подтверждённому событию**: подписанному вебхуку Stripe или транзакции, которую сервер сам нашёл и проверил в блокчейне. Редирект «оплата прошла» ничего не включает.
3. **Каждое событие — ровно один раз.** Повтор вебхука, повтор хеша, двойной клик — не создают второго платежа и второго продления.
4. **Мы не храним то, что опасно хранить**: номера карт (только у Stripe), приватные ключи кошелька (нигде на сервере).
5. **Всё, что меняет деньги, — в аудит** (`audit_logs`, append-only) и в `payments` (append-only).
6. **Флаг `BILLING_ENABLED`** выключен по умолчанию. Пока выключен — работают заглушки (раздел 5) и ручная выдача тарифа из админки.

Миграция — одна, следующий свободный номер. RLS — deny-all на всех таблицах (`enable_rls_deny_all`), запись только сервером; `db:verify` должен это подтвердить.

| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `purchases`        | `id`, `subject_*`, `plan_code`, `job_id`, `status` (`pending`/`paid`/`refunded`), `valid_until`, `provider`, `provider_ref`                                                                                                                                                | `job_id` только у `source = internal` (проверка в сервисе + тест)                                                                                                          |

| `crypto_orders`    | `id`, `subject_*`, `plan_code`, `amount_minor`, `token`, `chain`, `recipient`, `payer_address`, `status` (`open`/`submitted`/`confirmed`/`expired`/`frozen`), `tx_hash`, `expires_at`                                                                                      | `tx_hash` уникален; срок жизни 30 минут                                                                                                                                    |

## 3. Stripe (карты)

### 3.1 Что используем

- **Stripe Checkout** (страница Stripe) — для подписок кандидатов и «Команды» и для разовых «Наймов». Карта вводится только у Stripe.
- **Billing Portal** — смена карты, счета, отмена.
- **Stripe Tax** — по решению основателя (зависит от юрлица).
- Цены — `Price` в Stripe с `lookup_key = plans.code`. Сервер при создании Checkout берёт цену по `lookup_key`, сумма из браузера не принимается.

### 3.2 Поток подписки

1. `POST /api/billing/checkout` `{ planCode, period }` (вход обязателен, Origin сайта, лимит частоты).
2. Сервер: проверяет, что `planCode` существует и подходит аудитории; для компании — что вызывающий `owner`; что нет живой подписки этого же вида; создаёт или переиспользует `Customer` (id храним в `subscriptions.provider_ref`/отдельном поле); создаёт Checkout Session с `client_reference_id = subject`, `metadata.plan = code`, `success_url`, `cancel_url`; заголовок `Idempotency-Key` = хеш(subject, plan, минута).
3. Браузер уходит на Stripe. По возвращении `/billing/return` **только показывает** «ждём подтверждение» и опрашивает `GET /api/billing/me` до 20 секунд.
4. Активация — по вебхуку (3.3).

### 3.3 Вебхук

`POST /api/billing/webhook/stripe`:

- **Вне проверки `Origin`** — добавить путь в `needsOriginCheck` (как D313), иначе прокси вернёт 403.
- Тело читается **сырым** (`await request.text()`), подпись проверяется `stripe.webhooks.constructEvent(body, header, STRIPE_WEBHOOK_SECRET)` с допуском по времени 5 минут. Без подписи — 400, без логирования тела.
- Идемпотентность: `INSERT INTO billing_events … ON CONFLICT DO NOTHING`; если строка уже была — 200 без действий.
- События и действия:

| Событие                                     | Действие                                                                                                                                     |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `checkout.session.completed`                | разовая покупка → `purchases.paid`, `payments` charge; подписка → ждём `customer.subscription.*`                                             |
| `customer.subscription.created` / `updated` | статус и `current_period_end` из события; **порядок не гарантирован** — применяем, только если `event.created` новее последнего применённого |
| `customer.subscription.deleted`             | `expired`                                                                                                                                    |
| `invoice.paid`                              | продление, `payments` charge                                                                                                                 |
| `invoice.payment_failed`                    | `past_due`, письмо                                                                                                                           |
| `charge.refunded`                           | `payments` refund, при полном возврате — отозвать покупку                                                                                    |
| `charge.dispute.created`                    | заморозить продвижение/подписку, алерт владельцу                                                                                             |

- Обработка — в транзакции БД. Ошибка → 500, Stripe повторит.
- Раз в сутки cron сверяет все живые подписки со Stripe (`subscriptions.retrieve`) и чинит расхождения — на случай потерянных вебхуков.

### 3.4 Возвраты

- Гарантия «Найма» не выполнена → `refunds.create` на `payment_intent`, строка refund в `payments`, письмо.
- Возврат «нашёл работу» — пропорционально остатку периода, через тот же путь.
- Ручной возврат из админки — только `owner`, с причиной, в аудит.

## 4. Крипта через WalletConnect — прямо на кошелёк компании

### 4.1 Сети и токены

`src/lib/billing/chains.ts` — белый список:

```ts
{ chain: "base", chainId: 8453, tokens: { USDC: "0x…", USDT: "0x…" } }
{ chain: "polygon", chainId: 137, tokens: { USDC: "0x…", USDT: "0x…" } }
{ chain: "arbitrum", chainId: 42161, tokens: { USDC: "0x…", USDT: "0x…" } }
{ chain: "ethereum", chainId: 1, tokens: { USDC: "0x…", USDT: "0x…" } }
```

Покупатель выбирает USDT или USDC и сеть (D352). Оба токена на каждой сети, где есть официальный контракт. Новая сеть добавляется в этот список тем же правилом, а не отдельным разрешением. Сеть не из EVM (Tron, Solana) тем же решением принимается, но не этим адресом `0x` и не этой проверкой квитанции.

**Адреса контрактов не вписывать по памяти.** Брать только с официальных страниц эмитентов (Circle для USDC, Tether для USDT) и сверять с обозревателем сети; в репозитории рядом — ссылка на источник и дата проверки. Тест сверяет `decimals() == 6` и `symbol()` по RPC в отдельной проверке перед запуском. Подделка токена с тем же названием — самая частая атака, поэтому проверяется **адрес контракта**, а не название.

Tron (USDT TRC-20) и другие не-EVM сети — отдельные адрес и проверка, не этот поток WalletConnect (D352).

### 4.2 Поток

1. **Подключение кошелька** (Reown AppKit / WalletConnect) — только на странице `/billing/crypto`. Библиотека грузится динамически только там.
2. **Подтверждение владения адресом (SIWE, EIP-4361):** сервер выдаёт nonce, кошелёк подписывает сообщение с доменом `intgetion.com`, nonce, chainId и сроком 10 минут. Сервер проверяет подпись и привязывает `payer_address` к сессии пользователя. Без этого шага нельзя создать заказ.
3. **Заказ:** `POST /api/billing/crypto/order` `{ planCode, token, chain }` → сервер считает сумму из `plans`, берёт адрес получателя из настроек (`COMPANY_WALLET_ADDRESS`, один на все сети EVM), создаёт `crypto_orders` (`open`, срок 30 минут, `payer_address` из SIWE) и возвращает **сумму в единицах токена, адрес контракта и адрес получателя**.
4. **Перевод:** браузер вызывает у кошелька `transfer(recipient, amount)` на контракте токена. Пользователь видит в кошельке **адрес получателя и сумму** — страница рядом показывает тот же адрес, укороченный по-человечески (первые 6 и последние 4 символа), с подсказкой «сверьте адрес в кошельке».
5. **Хеш:** кошелёк возвращает `txHash` → `POST /api/billing/crypto/confirm` `{ orderId, txHash }` → заказ `submitted`.
6. **Проверка** (4.3) — сразу и затем cron раз в минуту для `submitted`, до 60 минут. Успех → `confirmed`, `payments` charge, покупка `paid`, письмо. Клиент видит этот статус опросом и получает тариф только тогда ([tz/23-billing.md](tz/23-billing.md) §5). Надпись в браузере тариф не включает.
7. Заказ, по которому за 30 минут не пришёл хеш, → `expired`. Хеш, пришедший позже на истёкший заказ, всё равно проверяется (деньги могли уйти) — если перевод верный, заказ засчитывается.

### 4.3 Проверка перевода (`verify-transfer.ts`, чистая функция + RPC)

Сервер сам, по своему RPC, берёт **квитанцию** транзакции (`eth_getTransactionReceipt`) и считает перевод верным, только если **всё** выполнено:

1. `receipt.status == 1` (транзакция не откатилась).
2. В логах есть событие `Transfer(from, to, value)` **от контракта токена из белого списка** для этой сети (сравнение адресов в нижнем регистре).
3. `to` == адрес компании.
4. `from` == `payer_address` заказа (адрес, подтверждённый SIWE). Защищает от кражи чужого хеша: кто-то не может подать хеш чужого перевода на свой заказ.
5. `value` ≥ сумма заказа в единицах токена. Переплата засчитывается, излишек фиксируется в заметке для ручного возврата; недоплата → заказ остаётся `submitted` с причиной «недоплата», владельцу — в админку.
6. Блок транзакции не раньше создания заказа (по `block.timestamp`, с допуском 2 минуты) — нельзя засчитать старый перевод.
7. Подтверждений ≥ порога сети (Ethereum 12, Polygon 64, Arbitrum и Base — по финализации L2; значения вынести в `chains.ts`). До порога — ждём.
8. `(chain, tx_hash)` ещё не засчитан нигде (уникальный индекс в `payments` — последняя линия защиты от гонки).
9. Адрес отправителя не в санкционном списке (4.5).

Засчитывание — в одной транзакции БД: вставка в `payments` (уникальность хеша) + смена статуса заказа + активация. Два параллельных `confirm` с одним хешем — второй упирается в уникальный индекс и получает «уже засчитано».

### 4.4 Ключи и кошелёк компании

- На сервере — **только публичный адрес** `COMPANY_WALLET_ADDRESS`. Приватного ключа нет ни в коде, ни в env, ни в логах.
- Кошелёк компании — мультиподпись (Safe), 2 из 3 подписей у основателя на разных устройствах. Возвраты делаются из Safe вручную.
- Смена адреса получателя — только переменной окружения и передеплоем; в админке адрес **только показывается**, не редактируется (иначе захват админки = кража платежей).
- `WALLETCONNECT_PROJECT_ID` — публичный по природе, но привязать к домену `intgetion.com` в настройках Reown.
- RPC-ключи — только сервер, по одному на сеть, с ограничением по домену/IP у провайдера.

### 4.5 Санкции

Перед засчитыванием адрес отправителя сверяется со списком санкционных адресов (открытый список OFAC SDN с крипто-адресами; обновление cron раз в сутки, хранить в таблице). Совпадение → заказ `frozen`, тариф не включается, алерт владельцу, деньги — решение основателя с юристом. Пользователю — нейтральное «оплата на проверке».

### 4.6 Что увидит пользователь при ошибках

| Ситуация              | Сообщение                                                          |
| --------------------- | ------------------------------------------------------------------ |
| Кошелёк в другой сети | «Переключите кошелёк на сеть Base» + кнопка переключения           |
| Не хватает токена     | «На кошельке недостаточно USDC» (проверка `balanceOf` до перевода) |
| Нет газа              | «Нужно немного ETH на Base для комиссии сети»                      |
| Отклонил в кошельке   | «Перевод отменён, деньги не списаны»                               |
| Ждём подтверждений    | «Перевод найден, ждём подтверждения сети: 3 из 12»                 |
| Недоплата             | «Пришло 4.00 из 5.00 USDC. Мы напишем, как доплатить»              |

## 5. Заглушка (пока провайдеры не подключены)

- `BILLING_CRYPTO_PROVIDER=stub` (по умолчанию). Кнопка «USDT / USDC» открывает форму: почта (если не вошёл), тариф, токен, сеть → `billing_interest`. Ответ: «Сообщим, когда включим. Если хотите оплатить сейчас — запросите счёт».
- «Запросить счёт» создаёт заявку в админке «Платежи». Владелец отправляет адрес Safe, после поступления **вручную** включает тариф: форма требует сеть, токен, хеш транзакции; хеш проходит ту же проверку 4.3 (без SIWE-пункта 4 — отправитель вписывается вручную), и уникальность хеша соблюдается.
- `BILLING_CARD_PROVIDER` не задан → кнопка «Картой» пишет «Скоро» и тоже ведёт на `billing_interest`.

## 7. Угрозы и защита

| #   | Угроза                                                                   | Защита                                                                                                                |
| --- | ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |

## 9. Интеграция по шагам

| Шаг    | Что                                                                                                                                                  | Проверка «готово»                                                                                        |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **P1** | Миграция таблиц, `entitlement()`, перевод лимитов (`botUser`/`botGuest`, сохранённые поиски, срок вакансии, число вакансий), ручная выдача в админке | `db:verify`; юнит-тесты лимитов; e2e: выданный вручную Plus даёт 100 сообщений                           |

| **P6** | Боевые ключи, `BILLING_ENABLED=true`, одна покупка основателем самому себе и возврат                                                                 | живая проверка по чек-листу 10                                                                           |
