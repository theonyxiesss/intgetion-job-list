# Где держать базу INTGETION (сверено 2026-10-29)

**Исправление после проверки Auth 2026-10-29:** прямые запросы к Supabase Auth `/auth/v1/health` и `/auth/v1/settings` вернули HTTP 402 `exceed_egress_quota`. База PostgreSQL при этом отвечает, но вход на сайт заблокирован. Вывод ниже «платить сейчас не требуется» относился лишь к объёму БД и миграциям и оказался неверным для **доступности входа**. [Supabase подтверждает](https://supabase.com/docs/guides/platform/manage-your-usage/egress), что egress включает Auth и shared pooler, а ограничение снимается при новом биллинговом цикле или сразу после upgrade на Pro. Точную дату цикла и расход надо проверить в кабинете владельца.

Сравнение для решения о тарифе и возможной смене платформы. Цены и лимиты ниже взяты из официальных страниц на дату сверки; перед оплатой их нужно проверить снова. Фактический счёт Supabase и расход Auth, Storage и трафика недоступны без владельческого кабинета. Никаких планов, ключей и данных в рамках исследования не меняли.

## Наше фактическое состояние

- Один облачный проект Supabase Free обслуживает и localhost, и production. Сервер обращается к PostgreSQL через Drizzle и роль `app_rw`; Supabase Auth обеспечивает вход, Supabase Storage хранит файлы. Прямые браузерные чтения таблиц заблокированы RLS, а права на данные проверяются в сервисах ([проектный навык](../.claude/skills/intgetion-supabase/SKILL.md), [модель данных](tz/04-data.md)).
- Read-only запрос 2026-10-29: `pg_database_size(current_database()) = 163 288 755` байт (около 156 MiB), 87 таблиц в `public`. Это размер всей PostgreSQL БД, не отдельный показатель платёжного кабинета. `/api/health` в production ответил `{ "ok": true }`.
- Миграции `0071`–`0073` в облаке отсутствуют; страница `/ru/freelance/tasks` даёт 404, поскольку код ещё не выложен. Оплата тарифа сама по себе не применит миграции и не выложит код. Причина блокировки выпуска — отсутствие обязательного Supabase MCP `execute_sql` для пути D438.

## Вывод и критерии решения

1. **Сейчас оставаться на Supabase.** Для текущей архитектуры это самый дешёвый путь по времени и риску. Проверенный объём БД меньше лимита Free; общий сбой БД не обнаружен. Cloudflare D1 дешевле по некоторым метрикам, но смена движка и Auth/Storage стоила бы отдельного миграционного проекта, а текущий выпуск это не ускорит.
2. **Для самих миграций `0071`–`0073` Pro не нужен**, но сейчас Auth заблокирован превышением egress Free. Для немедленного восстановления входа по [документации Supabase](https://supabase.com/docs/guides/platform/manage-your-usage/egress) требуется upgrade на Pro; без оплаты ограничение снимается при следующем биллинговом цикле. Миграции и deploy остаются отдельными шагами. Проверить в Supabase Dashboard разрез egress по сервисам и дату цикла.
3. **Supabase Pro теперь имеет непосредственную причину для production:** помимо снятия текущего ограничения он даёт ежедневные резервные копии и отсутствие автоматической паузы. Платный upgrade требует согласия владельца; после него нужно подтвердить ответ Auth и выполнить реальные проверки входа. Бесплатный план не даёт автоматических резервных копий ([тариф](https://supabase.com/pricing), [правило паузы](https://supabase.com/docs/guides/platform/free-project-pausing)).
4. **Сравнить Neon на практике**, если Supabase станет дорогим или его ограничения действительно мешают: тестовая копия схемы и обезличенных данных, замер отклика, стоимости, входа и восстановления. Не переносить production только по табличной цене.

Открытый вопрос: фактическое использование Supabase по MAU, Storage и Egress, состояние резервных копий и требуемый уровень доступности. Без этих данных нельзя честно утверждать, что платный тариф уже необходим или что другой провайдер дешевле для реальной нагрузки.
