Локальные исходники уже содержат `src/lib/http/errors.ts`, `handler.ts`, `src/components/ui/feedback.tsx`, `src/app/[locale]/error.tsx`, `src/proxy.ts` с `x-request-id`, `src/instrumentation.ts` с отправкой серверных ошибок в Sentry без SDK (D197). Их следует расширять, а не создавать второй слой ошибок.

## Что сейчас теряется

1. `toErrorResponse` возвращает код и текст, но не связывает тело ошибки с `x-request-id`. `ErrorState` умеет показывать ID, однако вызывающая форма должна передать его сама.
2. `apiErrorCode` в форме входа сводит незнакомый код к `generic`. Перехват сетевого `fetch` в форме отсутствует: при обрыве сети сообщение пользователю может вообще не появиться.
3. OAuth перенаправляет почти все ошибки на `oauth_unavailable`. При текущем ответе Supabase Auth `402 exceed_egress_quota` пользователь видит предложение войти другим способом, хотя тот же Auth блокирует и эти способы.
4. `/api/health` проверяет только PostgreSQL (`select 1`) и остаётся зелёным при недоступном Supabase Auth. Такой результат нельзя трактовать как здоровье входа.
5. Страница `error.tsx` показывает `error.digest` с подписью «Request ID». Это идентификатор ошибки Next.js, не обязательно `x-request-id`; в диагностике их надо различать.

## Предлагаемый путь ошибки

```text
действие пользователя
  → UI: ожидание / явный timeout / обработка сетевого отказа
  → API: проверка входа и данных, стабильный код ошибки
  → сервис: классификация ошибки БД/провайдера без утечки внутренних данных
  → лог/мониторинг: root cause + request_id + маршрут + стадия, без секретов и PII
  → API: безопасный код + HTTP статус + request_id + при необходимости retryAfter
  → UI: заголовок «что случилось» + «что делать» + повтор/исправление + ID для поддержки
```

Не показывать пользователю SQL, stack trace, Supabase key, email другого человека, внутренний URL или сырой текст провайдера. Не называть точную причину, если она не подтверждена. Причина вроде «сервис входа временно ограничен провайдером» допустима только после отдельной проверки Auth, а не по одному неудачному входу.

| Класс                            | API                                              | Сообщение и действие в интерфейсе                                                                            |
| -------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| Неверное поле                    | `400`/`422`, `VALIDATION_ERROR`, безопасные поля | «Проверьте отмеченные поля», фокус на первом поле.                                                           |
| Нет входа / прав                 | `401`/`403`                                      | «Войдите» или «Нет доступа» с корректным переходом. Для чужого объекта сохранить существующее правило `404`. |
| Конфликт состояния               | `409`, предметный код                            | «Данные изменились», обновить состояние и повторить действие.                                                |
| Лимит                            | `429`, `Retry-After`                             | Показать время следующей попытки; не предлагать бесконечный повтор.                                          |
| Сеть пользователя                | запрос не дошёл до API                           | «Нет соединения», кнопка «Повторить»; сохранить ввод.                                                        |
| БД или внешний сервис недоступен | `503`, стабильный `*_UNAVAILABLE`                | «Сейчас действие недоступно», повторить позже, показать ID обращения. Не обещать, что данные сохранились.    |
| Неизвестный сбой                 | `500`, `INTERNAL`                                | Нейтральное сообщение, безопасный повтор, ID обращения; подробности только в журнале.                        |

Пример для сегодняшнего сбоя входа: внутренний лог `auth_provider_quota` с ответом Supabase `402`, безопасный API-код `AUTH_UNAVAILABLE`, в UI: «Вход временно недоступен из-за ограничения сервиса авторизации. Попробуйте позже. Если ошибка повторяется, сообщите код обращения». Это иллюстрация будущего поведения; сейчас оно не реализовано.

## Как внедрять по одной подфазе

1. Сначала зафиксировать контракт ошибки и связь `request_id` с журналом, сохранив текущий формат API. Проверить, что 4xx не шумят в Sentry, а 5xx попадают в диагностику.
2. На одном полном сценарии входа различить неверные данные, лимит, сетевой сбой и недоступность Supabase Auth; убрать ложную подсказку про альтернативный способ входа при общей блокировке Auth.
3. Отдельно расширить диагностику здоровья: БД и Auth как разные компоненты, без секретов в публичном ответе. Внутренний мониторинг должен сообщать об отказе Auth даже при здоровом PostgreSQL.
4. После проверки сценария распространить тот же контракт на формы вакансий, фриланса и кабинет. Все строки — через `src/messages/*.json`, с сохранением введённых данных и доступным `role="alert"`/фокусом.

Для каждого сбоя навык `systematic-debugging`: воспроизвести → найти границу отказа (браузер, API, сервис, БД/провайдер) → записать одну гипотезу → минимально проверить → исправить первопричину → подтвердить сценарий и регрессию. Пользовательское сообщение должно описывать подтверждённое состояние и действие, а не выдавать догадку разработчика за факт.
